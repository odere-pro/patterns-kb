Principle

Single Responsibility Principle

A module should answer to exactly one actor — one stakeholder group whose changing needs are its single reason to be rewritten. Gather the things that change together; separate the things that change for different reasons.

Principle

What it says

A class should have only one reason to change. It is the “S” in SOLID, sharpened by Robert C. Martin from an older instinct toward cohesion. The word that trips everyone is responsibility: it does not mean “do one small thing,” it means answer to one source of change.

Martin's later gloss is the clearer one — a responsibility is an actor: a single person, or group of people, whose evolving needs are the reason a module gets rewritten. An axis of change. Gather the things those people care about into one place; keep the concerns of different actors apart.

Explained at three levels

Basic

One class holds both the report layout the finance team asks for and the interest calculation the auditors sign off on. Finance asks to move a column, the edit touches a helper the calculation also uses, the rounding shifts by a penny, and nobody notices until an audit fails. Give each group of people its own class and a change made for one of them can no longer reach the other.

Advanced

Find the axes by asking who signs off on a change. Two groups requesting edits to the same module is two responsibilities sharing one place; one group requesting edits to five methods is still one responsibility, whatever the class weighs. Commit history is the cheapest evidence you have — group past changes by who asked for them, and the real seams appear as the files that keep moving together.

Expert

Prefer the who-signs-off test to any structural heuristic, because seams that mirror the org chart survive — that is where change requests originate and where review already sits. The bill is that actors are not static: a reorg or a new regulator adds an axis your classes do not have, and a split made two years ago now runs across the grain. Pay it by re-cutting as soon as two teams queue on one file, and by keeping each split shallow enough that merging the halves back is a morning's work rather than an interface migration. Where an axis genuinely cannot be separated — a calculation finance formats and audit certifies — put the shared rule in one owned module and give each actor a thin adapter over it, so the collision is confined to a boundary you can test.

Why it helps

Two masters in one module means every edit must satisfy an audience it was not written for. A request from one of them cannot be reviewed by that group alone, because the same lines carry a rule the other depends on, so the change waits on a second sign-off and a second test suite. The cost of owning a module rises with the number of groups it answers to, not with its size.

Split along the axes of change and each edit stays local: the finance request touches finance code, the audit rule touches audit code, and neither can silently break the other. The seams then line up with the org chart, which is where change actually originates. Code that mirrors who asks for changes is code that is safe to change.

Applying it

Group by reason to change, not by superficial similarity:

  • Ask of each module: who requests changes to this? If two different actors do, that is two responsibilities living in one place.
  • Separate the axes that move independently — policy from mechanism, formatting from calculation, persistence from domain logic.
  • Watch for the tell: a class named with an “and,” or a vague Manager/Util, is usually holding more than one job.
  • Keep together what changes together — cohesion is the other half. Do not split code that a single actor always edits in lockstep.

The test: describe the class in one sentence without using “and.” If you cannot, it is probably answering to more than one actor.

Taken too far

Read as “do one tiny thing” and the principle shatters a system into a swarm of anemic one-method classes, each too small to carry meaning. Now behaviour that belongs together is scattered across a dozen files, and following a single request means hopping between them — the cohesion the principle exists to protect is the very thing you have destroyed.

Responsibility is measured in reasons to change, not in lines of code or method count. A class that does five things which always change together, for one actor, honours the principle; splitting it buys nothing but ceremony and indirection. Separate what changes apart; keep together what changes as one.
