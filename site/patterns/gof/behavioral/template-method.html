Template Method

Locks the shape of an algorithm in a base class — the steps and their order never change — while subclasses supply the parts that vary.

GoF Behavioral

What it is

Template Method defines the skeleton of an algorithm in one method of a base class and defers the varying parts to subclasses. That method — the template — calls a fixed sequence of operations: some are concrete and shared, some are abstract and left blank, some are hooks with a default. Subclasses override the blanks and hooks to fill in behavior without ever touching the sequence.

The forces it resolves are duplication and drift. You have several procedures that share the same overall shape but differ in a step or two. Copy the whole procedure once per variant and you copy the invariant scaffolding with it — and those copies quietly diverge over time. Template Method factors the invariant part into a single place and isolates the variant steps behind overridable operations.

Control is inverted: the base class owns the flow and calls down into the subclass at the right moments. A subclass cannot reorder, skip, or wrap the steps — it only supplies them. This is the Hollywood Principle, "don't call us, we'll call you," expressed through inheritance.

Explained at three levels

Basic

When several jobs follow the same steps in the same order and differ only in one or two of them, write the whole order down once and leave blanks where they differ, then let each version fill in just its blanks. Like a recipe for bread that fixes mixing, rising and baking, and lets each loaf choose its own flour and topping. Nobody can reorder or skip a step — only fill the gaps.

Advanced

A base class defines one method that fixes the sequence of an operation and calls a set of named steps: some concrete and shared, some abstract, some hooks with a do-nothing default. Subclasses supply only the varying steps and cannot reorder, skip or wrap the sequence — the frame calls down into them at the moments it chooses. Binding is by inheritance, fixed when the subclass is declared rather than per call, one variant per class. It is the backbone of framework base classes, test fixture setup and teardown, and abstract request handlers.

Expert

Reach for it when the sequence itself is worth protecting and the variation is small, closed and known up front — it buys one authoritative copy of the flow that no variant can get wrong. What you pay is inheritance: each variant spends its single base class, the set of overridable steps hardens into a contract you cannot change without breaking every subclass, and the flow is split between base and subclass so no one file shows what actually runs. Grant a new hook every time a subclass author asks for one and you arrive at the fragile base class. Where steps must vary independently or at runtime the hierarchy is the wrong shape, and unwinding one later costs far more than the composition you could have written instead.

How it works

Variations

Abstract primitive operations
Steps with no default that subclasses must implement — the compiler enforces that every variant fills them in.
Hook methods
Steps with a default (often empty) body; overriding is optional, so subclasses opt into an extension point only when they need it.
Non-Virtual Interface (NVI)
Keep the template method itself non-overridable and expose only the steps as virtual/protected — callers get one stable entry point.
Factory Method
When a varying step's whole job is to create an object, that step becomes a factory method the subclass supplies.

Trade-offs

Pros

  • Removes duplication by keeping the shared, unchanging steps in one place.
  • The base class owns the sequence, so no variant can get the order wrong.
  • A new variant only has to fill in the steps that actually differ.
  • Optional hook methods give named extension points, so you never edit the fixed skeleton.

Cons

  • Built on inheritance, so each variant is locked to one base class and its lifecycle.
  • The set of overridable steps hardens into a contract that is painful to change later.
  • Behavior is split between the base class and its subclasses, so the real flow is hard to trace.
  • Deep hierarchies and many hooks leave the skeleton rigid and brittle.

When to use it

Reach for it when

  • Several procedures follow the same overall structure but differ in a couple of steps.
  • You want to enforce one fixed sequence of steps across every variant.
  • The varying steps are known up front and stable in number.

Avoid when

  • The varying parts must swap independently at runtime — reach for Strategy.
  • Composition would serve better than locking behavior into a class hierarchy.
  • There is only one variant today — the abstraction is premature.

Code sketch

TypeScript — a report skeleton with overridable steps 
interface Row {
  readonly name: string;
  readonly value: number;
}

abstract class ReportBuilder {
  // the template method: the fixed skeleton, not overridable
  build(): string {
    const body = this.loadRows()
      .map((row) => this.formatRow(row))
      .join("\n");
    return this.header() + body + this.footer();
  }

  // required steps: every variant must supply these
  protected abstract loadRows(): readonly Row[];
  protected abstract formatRow(row: Row): string;

  // hooks: sensible defaults, override only if needed
  protected header(): string { return ""; }
  protected footer(): string { return ""; }
}

class CsvReport extends ReportBuilder {
  protected loadRows(): readonly Row[] {
    return [{ name: "ada", value: 1 }, { name: "bob", value: 2 }];
  }
  protected formatRow(row: Row): string {
    return `${row.name},${row.value}`;
  }
  protected override header(): string { return "name,value\n"; }
}

In the wild

javax.servlet.http.HttpServletIts service() method owns the request-dispatch skeleton, reads the HTTP method, and calls down into the doGet/doPost/doPut steps a subclass overrides. Steps left unimplemented return a 405 Method Not Allowed by default, so the skeleton stays intact even when a variant fills in only one.
JUnitThe runner owns a fixed setup-test-teardown sequence and invokes the @BeforeEach and @AfterEach hooks you fill in around each @Test, never letting a test reorder the skeleton; @BeforeAll and @AfterAll bracket the whole class once.
