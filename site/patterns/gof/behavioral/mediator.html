Mediator

Replaces a tangle of objects calling each other directly with a single coordinator that owns how they interact — colleagues talk to the mediator, never to one another.

GoF Behavioral

What it is

A mediator is an object that encapsulates how a set of other objects — its colleagues — interact. Instead of each colleague holding references to the others and calling them directly, every colleague knows only the mediator. When something happens, a colleague notifies the mediator, and the mediator decides who else needs to react.

The problem it resolves is tangled coupling. Let a group of objects talk to each other freely and you get a many-to-many web: every object references every other, the number of connections grows with the square of the count, and the rules governing their interaction end up smeared across all of them. Changing one interaction means editing several classes, and no single object can be reused without dragging its neighbours along.

The mediator turns that web into a hub-and-spoke. Colleagues depend only on the mediator; the mediator depends on the colleagues. The interaction logic lives in exactly one place and can be changed without touching the colleagues at all.

The canonical GoF example is a dialog box: a director coordinates widgets so that toggling a checkbox enables a button, or selecting a list item fills a text field — without any widget knowing the others exist.

Explained at three levels

Basic

When every part of a screen has to know about every other part — tick this box and that button wakes up, pick this row and that field fills in — the wiring turns into a mess. Give one object the job of watching them all: each part tells it what just happened, and it decides what everyone else should do. Like a control tower: pilots never arrange things themselves; the tower holds the rules and decides who lands next.

Advanced

Colleague objects hold a reference to one mediator and none to each other. A colleague reports a local event upward — value changed, item selected — and the mediator, which does hold references to all of them, applies the interaction rules and drives the others. The many-to-many graph collapses to hub-and-spoke, so an interaction rule changes in one class rather than several, and a colleague can be lifted into another context alone. The canonical instance is a dialog director coordinating widgets; the same role appears as a controller, a session coordinator, or a workflow engine over services.

Expert

Reach for it when the interaction rules themselves are the complicated part and they are currently smeared across the participants — centralising them buys one place to read, change and test the protocol. The rule is that it must own logic, not relay calls: a mediator that only forwards has added a hop that hides who triggered what and bought nothing, and two peers that talk one way should just talk. The failure mode is gravity. Every new rule has an obvious home, so it lands there, and the hub accretes into the god object the pattern was meant to prevent — now a single point of failure, a merge-conflict magnet, and the least testable class you own.

How it works

Variations

Message / event bus
A fully decoupled mediator: colleagues publish typed messages and subscribe to the ones they care about, so senders and receivers never name each other.
Request dispatcher
An in-process mediator that maps a request object to exactly one handler (the MediatR style), keeping controllers thin and handlers isolated.
GUI director
The classic dialog mediator: one object owns the rules that link widgets, so each widget stays dumb about its siblings.
Hub / broker
A network-scale mediator — a chat server or air-traffic controller — where clients coordinate only through the central hub, never peer-to-peer.

Trade-offs

Pros

  • The objects depend on one mediator instead of on each other, so they stay independent.
  • The rules for how they interact live in one place, not smeared across many classes.
  • It turns tangled many-to-many links into a single hub, cutting connections from roughly n² toward n.
  • Each object gets simpler and easier to reuse elsewhere.

Cons

  • The mediator can swell as it soaks up every rule, until it does too much.
  • Putting control in one place makes it a bottleneck and a single point of failure.
  • The indirection hides who actually triggers what, making the flow harder to trace.
  • It's overkill when the objects barely interact, or only talk one way.

When to use it

Reach for it when

  • A group of objects reference each other in complex, tangled ways.
  • Reusing one object is hard because it's wired directly to many others.
  • The rules for how they interact are scattered across classes and hard to change.

Avoid when

  • The objects barely interact, or only in one direction — a simple broadcast fits better.
  • There's a natural one-way flow that needs no central coordinator.
  • The mediator would only relay calls without owning any real logic.

Kept lean, it stops scattered coordination from congealing across your classes — but a mediator that hoards every rule becomes exactly the God Object it was meant to prevent.

Code sketch

TypeScript — a signup form where one hub owns the widgets' rules 
type WidgetEvent = "toggled" | "changed";

interface Mediator {
  notify(sender: Component, event: WidgetEvent): void;
}

abstract class Component {
  constructor(protected readonly mediator: Mediator) {}
}

class Checkbox extends Component {
  checked = false;
  toggle(): void {
    this.checked = !this.checked;
    this.mediator.notify(this, "toggled");   // tell the hub, not the button
  }
}

class SubmitButton extends Component {
  enabled = false;
  setEnabled(on: boolean): void { this.enabled = on; }
}

class SignupForm implements Mediator {
  constructor(
    private readonly terms: Checkbox,
    private readonly submit: SubmitButton,
  ) {}

  notify(sender: Component, event: WidgetEvent): void {
    // one place owns the rule: submit follows the terms checkbox
    if (sender === this.terms && event === "toggled") {
      this.submit.setEnabled(this.terms.checked);
    }
  }
}

In the wild

MediatRControllers call ISender.Send(request); MediatR resolves the single IRequestHandler for that request type from the DI container and invokes it, so neither side names the other. Cross-cutting concerns slot in as IPipelineBehavior wrappers that run around every handler, and INotification with Publish() is the multi-handler broadcast variant.
