Null Object

Replaces a null reference with an object that honours the same interface but quietly does nothing — so callers drop the guards and treat "absent" as just another valid collaborator.

GoF Also Essential

What it is

A null object is a real object that implements the same interface as the thing it stands in for, but whose methods do nothing — or return a neutral, harmless value. Instead of handing back null to signal "there is nothing here," a factory or default returns this do-nothing instance. Callers invoke it exactly like the real thing and get safe, empty behaviour. It is not one of the original twenty-three design patterns: it was catalogued separately, first as Void Value and then under this name, and it reached most working programmers through the refactoring literature rather than the design-patterns book.

The problem it resolves is the null check that metastasises through a codebase. Every place that might receive a missing collaborator grows an if (x != null) guard; forget one and you get a NullPointerException at runtime. The checks add noise, hide the real logic, and drift out of sync as the code changes.

The null object collapses all of that into one code path. There is only ever a valid object to call, so the guards disappear and "absent" becomes an explicit, testable behaviour rather than a special case sprinkled across every caller.

Explained at three levels

Basic

When something is optional, code fills up with checks for whether it is there, and one forgotten check crashes the program. Instead, hand out a harmless stand-in that accepts every request and quietly does nothing. Callers just use it, and the checks disappear. Like a mute button on a speaker: you still send it sound, it still behaves normally, you simply hear nothing come out.

Advanced

A do-nothing implementation of the collaborator's interface is supplied wherever a real one might be absent, so the reference a caller holds is never empty. Its methods return neutral values — zero, an empty collection, itself — and its commands have no effect. The substitution happens at wiring time, in a factory, a default field value, or the container, not at each call site, so every caller runs the same unconditional path. Because it carries no state, one shared immutable instance serves the whole process. It pairs naturally with strategy defaults and with test doubles.

Expert

Choose it when absence is a legitimate, well-defined state and the correct response to it really is to do nothing — its value is one unconditional code path instead of a guard replicated at every call site. That condition is narrower than it looks. Outside it the pattern converts a genuine failure into silence: the request that writes nowhere, the notification nobody receives, the report with no rows and no error to explain why. Such bugs cost far more to find than the crash they replaced, because there is no stack trace and no signal. It also multiplies types — one empty variant per collaborator — to remove a check that a single guard, or a language-level optional type, would have handled outright.

How it works

Variations

Do-nothing vs. safe-default
Some null objects are pure no-ops; others return neutral values — an empty collection, a zero, an unchanged input — so downstream arithmetic and iteration still work.
Special Case
Fowler's generalisation: instead of one "nothing" object, return a dedicated object per known condition — UnknownCustomer, MissingUser — each with its own sensible behaviour.
Shared singleton instance
Because a null object holds no state, one immutable instance can be reused everywhere rather than allocating a fresh one at each call site.
Strategy
Wire a do-nothing implementation as the default strategy, so a component behaves harmlessly before anyone configures the real algorithm in.

Trade-offs

Pros

  • Gets rid of the repetitive null checks scattered across every caller.
  • Leaves a single code path with no branches — just call the object and move on.
  • One unchanging instance can be shared and reused everywhere at no cost.
  • Turns "nothing here" into real, testable behaviour instead of a special case.

Cons

  • Can hide real errors — a missing value quietly turns into a do-nothing call.
  • Needs a new class for every interface you want a do-nothing version of.
  • The do-nothing behaviour can surprise callers who expected a failure.
  • It's the wrong choice when a missing value genuinely needs different handling.

When to use it

Reach for it when

  • A collaborator is optional, and when it's missing the right response is simply to do nothing.
  • The same null check is copy-pasted across many call sites.
  • You want a safe default in place before the real dependency is wired in.

Avoid when

  • A missing value is an error the caller must notice and handle.
  • The do-nothing behaviour would mask a bug or silently drop data.
  • There's only one call site, where a single plain guard is simpler and clearer.

Code sketch

TypeScript — a null logger as a safe default 
interface Logger {
  info(message: string): void;
  warn(message: string): void;
}

class ConsoleLogger implements Logger {
  info(message: string): void { console.log(`[info] ${message}`); }
  warn(message: string): void { console.warn(`[warn] ${message}`); }
}

// The do-nothing stand-in: same shape, every method an empty body.
// It holds no state, so one frozen instance is shared everywhere.
const NULL_LOGGER: Logger = Object.freeze({
  info(_message: string): void {},
  warn(_message: string): void {},
});

// Logging is optional, so it defaults to the null object.
function processOrder(id: string, logger: Logger = NULL_LOGGER): void {
  // No `if (logger)` guard anywhere below — just call it.
  logger.info(`processing order ${id}`);
  // ... work ...
}

processOrder("A-1");                       // silent — uses NULL_LOGGER
processOrder("A-2", new ConsoleLogger());  // logs to the console

In the wild

Python logging.NullHandlerA stdlib handler whose emit() does nothing, discarding every record. The documented convention is for a library to attach it to its top-level logger so the library can log unconditionally without emitting the "No handlers could be found" warning or forcing logging config on the host application.
SLF4J NOPLoggerThe slf4j-nop binding supplies NOPLogger, whose level checks all return false and whose log methods are empty, so every call is a no-op. Dropping the slf4j-nop jar on the classpath silences all SLF4J output without any backend present or any code change at the call sites.
/dev/nullThe Unix null device: every write() succeeds and is discarded, and every read returns EOF. It stands in wherever a real file or stream would go — redirecting a noisy command to it silences output while keeping the program writing normally.
