Copy-on-Write

Readers never lock — writers publish a new copy: a writer clones the shared structure, edits the clone, and swaps in one reference, so every reader gets a complete version instead of a half-updated one.

Concurrency

What it is

Copy-on-write keeps one shared reference to a structure that nobody edits in place. A writer clones the structure, changes the clone, and publishes the result by swapping that single reference. A reader follows the reference to whichever version it named at the moment it looked, and reads that version to the end — so readers take no lock at all, and no reader ever meets a half-updated structure.

That is Immutability narrowed to a systems technique. Immutability says never change a value in place; copy-on-write adds when the copy gets paid for — lazily, on the first write, with everything shared until then. The kernel hands a forked child the parent's own pages and copies one only when a side writes to it, and a filesystem snapshot costs nothing until a block diverges. The rule is not "never share", it is "share until someone writes".

Skip it and a reader and a writer on one structure give you two bad outcomes. If the writer inserts an element while a reader is halfway through a loop, the reader sees state that satisfies no invariant — a count that no longer matches the contents, or an index pointing past the end — a race condition that surfaces as a crash far from the write that caused it. If you close that hole with a lock instead, every reader pays for the writer's rarity, and threads that only look at the data queue behind one another. A read-write lock softens that second cost by letting readers share; copy-on-write removes it, because there is nothing on the read path left to acquire.

Explained at three levels

Basic

One thread walks a list while another adds to it, and the walker sees something that was never true: an item counted but not there yet, or the same item twice. The usual fix makes everyone take turns, so threads that only look at the list end up waiting on each other even though looking breaks nothing. Instead, let the changer work on its own private copy, and when it has finished, point everyone at the new one. Whoever is already reading finishes the old copy, which is still complete and still correct, and the next reader gets the new one.

Advanced

The shared state is a single reference to a value nobody edits in place, so publishing is one pointer swap and a reader synchronises on nothing beyond reading that reference once. The copy is lazy, and how little of it you pay for is the variant: whole-value copying reallocates the structure on every write, page-level copying (fork) duplicates only the page somebody wrote to, a snapshotting filesystem duplicates only the blocks that diverge, and a persistent data structure copies only the path from the root to the changed node. That last one is what makes the technique affordable on large structures, turning a cost proportional to the size of the structure into one proportional to its depth. Writers are not free of synchronisation, though: they must exclude each other, or one clone-and-publish overwrites another.

Expert

Choose it when reads vastly outnumber writes and readers are on the latency-critical path, which is why routing tables, feature flags and listener registries are its home ground; at anything close to balanced traffic a lock or a purpose-built concurrent structure costs less than the copying. The bill has three lines and each has a move. A small edit pays for a whole copy, so use structural sharing and pay for the depth instead of the size. Both versions are resident across the swap, so peak memory roughly doubles: batch several edits into one publication rather than publishing per field, and watch the write burst rather than the steady state. A long-running reader pins the version it captured, delaying reclamation and widening its staleness, so bound reader lifetimes and treat a snapshot held across an I/O wait as a bug. Then operate on the ratio: watch write rate against structure size, expect memory pressure long before you expect corruption, and gate adoption on a measurement showing reads really do dominate.

How it works

Variations

Whole-value copy
Clone the entire structure on every write. It is the simplest form and the hardest to get wrong, and the cost is exactly what it sounds like: each write allocates the structure again, and both versions stay resident until the old one is released. Fine for a config map of a few hundred entries, ruinous for a million-element index.
Structural sharing
Copy only the path from the root to the node that changed, and point the rest of the new version at the old version's nodes. A write into a tree of a million nodes then costs the depth of the tree rather than its size, which is what makes copy-on-write affordable on large structures. Persistent maps and vectors are built this way, and the price is a data structure far more intricate than an array.
Page-level copy-on-write
The kernel does it for you. After a fork(), parent and child share the same physical pages, marked read-only in both page tables; the first write from either side traps, the kernel copies that one page, and both carry on. A process that forks and immediately execs copies almost nothing, which is why forking a large process is cheap until one side starts writing.
Snapshot filesystems
A copy-on-write filesystem never overwrites a live block: a change writes new blocks and updates the tree to point at them. Retaining a reference to the old tree is therefore a snapshot, created in constant time and costing storage only as the two trees diverge. You pay in fragmentation, and in space you cannot reclaim while any snapshot still names those blocks.
Copy-on-write collections
The library form: a list or set whose mutating operations copy the backing array under a lock, and whose iterators are snapshots taken at creation. Iteration needs no synchronisation and cannot fail midway because of a concurrent change — but the iterator will not show writes that landed after you obtained it, and it cannot support removal through the iterator, because the array it walks is nobody's live state.

Trade-offs

Pros

  • Readers take no lock, so read throughput scales with core count and never contends with a writer.
  • A reader cannot observe a half-updated structure — the version it captured is complete and frozen for as long as it holds it.
  • Iteration needs no defensive copy: the writer takes one copy for everyone, instead of every reader taking one for itself.
  • Publication is a single reference swap, so rollback is keeping the previous reference and swapping it back.
  • Old versions are snapshots you already paid for — a consistent view for a backup, an audit, or a long-running job.

Cons

  • Write amplification: changing one field pays for a copy of the whole structure. Structural sharing cuts that to the changed path, at the cost of a much more intricate data structure.
  • Peak memory roughly doubles, because both versions are live across the swap. A burst of writes on a large structure spikes well above its steady size — batch several edits into one publication instead of publishing per change.
  • A long-running reader pins the version it captured, delaying its reclamation and widening how stale that reader's view is. Bound reader lifetimes, and never hold a snapshot across an I/O wait.
  • It only pays when reads vastly outnumber writes. Near-balanced traffic spends more on copying than the lock it replaced, and a purpose-built concurrent structure beats it on both sides.
  • Writers still need mutual exclusion. Two writers that clone the same version concurrently both publish, and the second silently discards the first's change — serialise them with a mutex, or publish with a lock-free compare-and-swap that retries when it loses the race.

When to use it

Reach for it when

  • Reads vastly outnumber writes on the same structure — a routing table, a feature-flag set, a listener registry, a config map.
  • Readers sit on the latency-critical path and must neither block nor contend with each other.
  • A reader needs one stable view for the whole of a long operation — iterating, serialising, computing a total.
  • The structure is small enough, or shares structure well enough, that a copy is cheap against the read traffic it saves.

Avoid when

  • Writes are frequent, or reads and writes arrive at similar rates — a lock or a concurrent structure costs less.
  • The structure is large and copied whole, so a single write allocates more than the machine has headroom for.
  • Readers must see a change the instant it is published; a captured version is stale by construction.
  • Readers need to change what they read — copy-on-write hands them a frozen version, not shared state.

Code sketch

TypeScript — a lock-free-to-read routing table 
type Route = { readonly host: string; readonly weight: number };

class RouteTable {
  // The only shared cell: one reference to a frozen array nobody edits in place.
  private current: ReadonlyArray<Route> = Object.freeze([]);
  // Writers exclude each other, so no update is silently discarded.
  private writes: Promise<void> = Promise.resolve();

  // Readers: one read of one reference. No lock, no contention, no waiting.
  snapshot(): ReadonlyArray<Route> {
    return this.current;
  }

  add(route: Route): Promise<void> {
    this.writes = this.writes.then(() => {
      const next = [...this.current, route];      // 1. clone
      next.sort((a, b) => b.weight - a.weight);   // 2. edit the private clone
      this.current = Object.freeze(next);         // 3. publish: one swap
    });
    return this.writes;
  }
}

// The whole trick is here: capture the reference ONCE, then read it to the end.
const routes = table.snapshot();
for (const r of routes) {
  send(r.host);        // a concurrent add() cannot touch `routes`
}

// Calling table.snapshot() inside the loop would throw that away: two turns of
// the loop could land on two different versions and send to one host twice.

In the wild

java.util.concurrent.CopyOnWriteArrayListEvery mutating operation — add, set, remove — copies the backing array under a lock, so reads synchronise on nothing. An iterator holds the array that existed when it was created: it never throws ConcurrentModificationException, it never shows a later write, and its own remove, set and add throw UnsupportedOperationException. CopyOnWriteArraySet is backed by one.
Linux fork()The child does not receive a copy of the parent memory. It receives page tables pointing at the same physical pages, with the writable ones marked read-only on both sides; the first write from either process takes a page fault and the kernel copies that one page. Forking a large process is therefore cheap until one side starts writing.
ZFS and BtrfsNeither filesystem overwrites a live block: a change writes new blocks and rewrites the tree above them to point at the new locations. Keeping the old tree root is what makes a snapshot near-instant and initially free, and the space it holds is reclaimed only when the snapshot is destroyed.
Redis BGSAVERedis forks a child process to write the point-in-time snapshot while the parent keeps serving requests. The child sees a consistent dataset because the kernel copies pages only as the parent modifies them — so a write-heavy workload during the save dirties pages faster and pushes the process memory above the size of the dataset.

In production

Tuning knobs

  • Copy granularity — Whether a write copies the whole value or only the path from the root to the node that changed. Whole-value copying is simpler and correct; structural sharing turns a cost proportional to the size of the structure into one proportional to its depth, and is the only affordable choice once the structure is large.
  • Publication batching — How many logical edits go into one published version. Publishing per field keeps readers freshest and allocates the most; coalescing a run of edits into one swap trades a little staleness for far fewer copies.
  • Writer serialisation — A mutex around clone-and-publish, or a compare-and-swap on the reference that retries when it loses. The mutex wastes no clones and blocks writers; the CAS loop blocks nobody and redoes the copy on every lost race.
  • Snapshot lifetime — How long a reader may hold a captured version before releasing it. It sets both the staleness ceiling for that reader and how long the old version stays unreclaimable.

Signals to watch

  • Write rate against structure size — Their product is the allocation the pattern costs per second, and it is the number that decides whether copy-on-write is still paying for itself.
  • Peak resident memory during publication — Both versions are live across the swap, so the peak is what has to fit — not the steady-state size of the structure.
  • How long readers hold a version — Time from capturing the reference to releasing it. Rising hold times mean staler reads and old versions that cannot be reclaimed.
  • Allocation rate and collector pause time — On a managed runtime every publication becomes garbage, and the pause is the latency that copying costs your readers.

Failure modes under load

  • Memory spike on a write burst — A run of writes allocates a full version each, and any that readers still hold cannot be reclaimed. Memory climbs far above the steady-state size and hits the ceiling before throughput does.
  • Lost update between writers — Two writers clone the same version and both publish; the second swap discards the first change and nothing raises an error. It looks like a save that silently did not happen.
  • One slow reader pinning the chain — A consumer holding a snapshot across an I/O wait keeps every version since then alive, and acts on state that is minutes old.
  • Write amplification overtaking the saving — As the write rate rises, the copying costs more than the read contention it removed. Throughput falls while the code looks unchanged.

Readiness checklist

  • Measure the read-to-write ratio before adopting it; copy-on-write only pays when reads clearly dominate.
  • Size memory for the peak, not the average — both versions are resident across the swap, and versions readers still hold add to it.
  • Serialise writers with a mutex or a compare-and-swap loop; a clone-and-publish with no exclusion loses updates silently.
  • Make readers capture the reference once per operation, and never hold a snapshot across an I/O wait.
  • Use structural sharing for any structure large enough that a whole-value copy shows up in the allocation rate.
