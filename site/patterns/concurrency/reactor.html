Reactor

A single event loop watches every open socket, timer, and signal at once, and the instant one is ready it dispatches straight to the handler that registered for it — no thread parked per connection, no one blocked waiting.

Concurrency Lens

What it is

A reactor is a single-threaded event loop that owns one job: ask the OS which of many registered event sources is ready — a socket that can be read, a timer that has fired, a signal that arrived — and dispatch each ready one to the handler that registered interest in it. The asking is done through a demultiplexer (select, poll, epoll, kqueue); the loop blocks there, wakes with a list of ready descriptors, and calls each handler in turn, synchronously, on the loop's own thread.

The force it resolves is the cost of thread-per-connection concurrency. Give every connection its own OS thread and each idle one still pins a stack and a scheduler entry — thousands of connections mean thousands of threads mostly doing nothing but costing context-switches and memory. Reactor decouples "wait for something to happen" from "do work when it happens": one thread (or a handful, one per core) can watch tens of thousands of descriptors for the price of a single blocking call, and only pays for CPU when there is real work to dispatch.

The catch is exactly what makes it cheap: there is one loop. A handler that blocks — a slow disk read, a synchronous DNS lookup, a tight CPU loop — stalls every other connection sharing that thread. The pattern trades away preemption; it demands that handlers give control back quickly.

Doug Schmidt formalized it in the ACE framework in the mid-1990s, and it now sits underneath most high-concurrency network servers: nginx's worker processes, Redis's single command-processing thread, and Node.js's event loop over libuv are all reactors.

Explained at three levels

Basic

One thread sits in a loop and asks the operating system which of the things it is watching are ready — this connection has data, that timer went off — then runs the small piece of code registered for each one. It is a receptionist serving whoever reaches the desk next, instead of hiring one clerk per visitor and paying them all to stand around. The rule that keeps it working: no piece of code may take long, because everyone else waits behind it.

Advanced

The waiting is a single blocking call into a demultiplexer — select, poll, epoll, kqueue — which returns the set of ready descriptors, and the loop then dispatches them synchronously, one handler at a time. Memory per connection becomes a registration instead of a stack, and because two handlers never overlap on that thread, state the loop owns needs no lock. The variants differ in what actually runs the handler: the worker-pool form hands slow work to a bounded pool so the loop keeps ingesting, the thread-per-core form runs N loops that share nothing, and a proactor hands you a completed read rather than telling you a descriptor is readable.

Expert

Choose it when thread-per-connection overhead across many idle, I/O-bound connections is the measured bottleneck — not for CPU-bound work, which one loop merely serializes, and not when your runtime already offers cheap preemptible concurrency. Then pay the bill: one loop uses one core, so parallelism means sharding connections across loops or processes; blocking libraries have to move to a thread pool and return through a future, which pushes async style along the whole call chain; and because nothing preempts a handler, saturation shows up as loop lag rather than as a busy CPU. Operate it on that loop — tune loop count and offload-pool size, watch loop lag and per-handler time, expect a stalled loop before a full queue, and gate release on a per-loop connection ceiling that fits the file-descriptor limit.

How it works

Variations

Single-threaded reactor
One loop runs both the demultiplexing and every handler. Simplest, no locking anywhere, but a slow handler stalls all other connections.
Worker-pool reactor
The loop only demultiplexes and dispatches; the actual handler work runs on a bounded thread or task pool, so one slow handler no longer blocks ingestion of new events.
Multi-reactor (thread-per-core)
Run N independent loops, each pinned to a core and owning its own slice of connections, sharing nothing — the shape behind nginx workers and modern thread-per-core servers.
Reactor vs. Proactor
Reactor notifies "this descriptor is ready, go read it yourself"; Proactor notifies "your read already completed, here's the data" — the OS or an async layer performs the I/O, as in Windows IOCP.

Trade-offs

Pros

  • No thread-per-connection overhead — one loop scales to tens of thousands of idle sockets.
  • No locking inside the loop: handlers on the same thread never race each other.
  • Low, predictable memory footprint per connection compared to a parked thread and stack.
  • Dispatch order within the loop is explicit and easy to reason about.

Cons

  • A single blocking or CPU-heavy handler stalls every other event on that loop.
  • One loop uses one core — real parallelism needs multiple reactor instances.
  • Callback-driven control flow is harder to step through than straight-line, blocking code.
  • Every handler must be written non-blocking, which pushes async style through the whole call chain.

When to use it

Reach for it when

  • You're serving many concurrent, mostly-idle I/O connections — sockets, pipes, timers.
  • Thread-per-connection overhead (memory, context switches) is the actual bottleneck.
  • Work is I/O-bound and can be expressed as short, non-blocking handlers.

Avoid when

  • The workload is CPU-bound — a reactor's single loop just serializes the crunching.
  • Your runtime already gives you cheap, preemptible concurrency (lightweight threads, coroutines) — reintroducing an explicit loop adds complexity for no gain.
  • You depend on libraries that only offer blocking calls and can't be made async or offloaded to a pool.

Code sketch

TypeScript — a minimal single-threaded reactor 
type Handler = (fd: number) => void;

class Reactor {
  private handlers = new Map<number, Handler>();

  register(fd: number, handler: Handler): void {
    this.handlers.set(fd, handler);
  }

  unregister(fd: number): void {
    this.handlers.delete(fd);
  }

  // The loop: block until the OS says something is ready,
  // then dispatch each ready fd to its handler. A handler
  // must never block — that stalls every other connection.
  run(): void {
    while (true) {
      const ready = demultiplex([...this.handlers.keys()]); // epoll/kqueue
      for (const fd of ready) {
        this.handlers.get(fd)?.(fd);
      }
    }
  }
}

In the wild

nginxEach worker process runs its own epoll (Linux) or kqueue (BSD) event loop over thousands of connections, which is why it serves idle keep-alives so cheaply. worker_processes (often auto) sets one loop per core and worker_connections caps sockets per worker.
Node.js / libuvA single-threaded event loop over libuv demultiplexes socket, timer, and completion events and dispatches each to its JavaScript callback. Blocking or CPU-heavy work must go to worker_threads or the libuv thread pool (UV_THREADPOOL_SIZE, default 4).
RedisA single-threaded loop processes every command in turn, which is why commands are atomic and why one slow command (such as KEYS on a large keyspace) stalls the server. Redis 6 added io-threads that parallelize socket read/write while command execution stays single-threaded.

In production

Tuning knobs

  • Loop / worker count — Event loops per process, usually one per core (nginx worker_processes auto). A single loop uses only one core no matter how many connections it holds.
  • Max connections per loop — nginx worker_connections and the OS file-descriptor limit cap how many sockets one loop can multiplex.
  • Offload thread-pool size — Blocking or CPU-heavy work must move off the loop to a pool, such as libuv UV_THREADPOOL_SIZE (default 4); the pool size caps concurrent offloaded work.
  • Demultiplexer wait timeout — The epoll or kqueue wait timeout bounds how long the loop sleeps before it wakes to service timers.

Signals to watch

  • Event-loop lag — How late scheduled callbacks fire, measurable with Node perf_hooks monitorEventLoopDelay. Rising lag means the loop is saturated or blocked.
  • Connections per worker — Active sockets each loop is multiplexing.
  • Handler execution time — Time spent inside a single callback. Any long one delays every other event on that loop.

Failure modes under load

  • Blocked event loop — One synchronous, blocking, or CPU-heavy callback freezes every connection on that loop until it returns.
  • Single-core ceiling — A lone loop cannot use more than one core, so throughput caps there unless work is sharded across loops or processes.
  • Event backlog — If handlers cannot keep pace with arrivals, the ready-event queue and socket buffers grow, adding latency to everything.

Readiness checklist

  • Never block the loop; offload blocking I/O and CPU-heavy work to a thread pool or separate process.
  • Run one loop per core to use all cores.
  • Bound accepted connections per loop within the file-descriptor limit.
  • Monitor event-loop lag as the primary saturation signal.
