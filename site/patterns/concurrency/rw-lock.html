Read-Write Lock

Lets any number of threads read shared data at once, but the instant one needs to write, every reader and every other writer is forced to wait — reads scale for free, writes stay exclusive and safe.

Concurrency Lens

What it is

A read-write lock (also called a shared-exclusive lock, or RWLock) is a synchronization primitive with two acquisition modes instead of one. Any number of threads can hold it in read mode at the same time, but the moment a thread requests write mode it must wait for every current reader to release, and while it holds the write lock no other reader or writer can proceed. Readers share with readers; writers exclude everyone.

It resolves a shape of contention that a plain mutex handles badly. A mutex treats every critical-section entry identically, so on data that's read far more often than it's written, it serializes threads that never actually conflict — two readers blocking each other even though neither mutates anything. That's parallelism thrown away on hardware built to run many things at once.

The read-write lock buys that parallelism back by tracking readers and writers separately — typically a reader count plus a writer flag — so the acquisition logic can tell "shared, safe to join" from "exclusive, everyone else waits." The cost is a genuinely harder primitive than a mutex: starvation policy, fairness between the two roles, and upgrade semantics all become explicit design decisions instead of being handled for you.

Explained at three levels

Basic

When lots of code only looks at some shared data and hardly anything changes it, making every reader take turns is wasted time — looking never breaks anything. So let any number of lookers in together, but the moment someone wants to change the data, wait for the lookers to finish and let the changer work alone. Like a whiteboard many people may read but only one may rewrite.

Advanced

The primitive has two acquisition modes over one reader count and a writer flag: readers share with readers, writers exclude everyone including each other. That converts a mutex's blanket serialization into parallelism proportional to core count on read-dominated structures — caches, config, routing tables. The extra bookkeeping is not free, and three policy questions become explicit design decisions: fairness between the two modes, whether an upgrade from read to write is permitted, and whether acquisition is reentrant.

Expert

Choose it only when reads vastly outnumber writes and read sections are long enough that serializing them costs measured throughput; on short sections or balanced traffic the per-acquisition bookkeeping costs more than the contention it removes, and a copy-on-write snapshot takes the lock off the read path altogether. The failure modes are policy, and each has a move: reader preference starves writers while writer preference starves readers, which a fair ticket queue bounds at the price of peak read throughput; a recursive caller deadlocks on a non-reentrant lock, which reentrancy fixes at twice the accounting; and two readers that each try to upgrade deadlock on each other, so you release and re-acquire, or downgrade from write to read instead. Then operate on the ratio — tune the preference policy, watch writer wait time against the write fraction, expect starvation long before you expect corruption, and gate release on a measurement showing the plain mutex really was the bottleneck.

How it works

Variations

Reader-preference vs. writer-preference
Decide who wins when both roles are waiting. Naive reader-preference lets a steady stream of readers starve a writer indefinitely; writer-preference flips the risk onto readers instead.
Fair / ticket-queued
Queue read and write requests in arrival order so neither role starves the other, at the cost of extra bookkeeping and slightly lower peak read throughput.
Upgradeable read lock
Lets a thread already holding a read lock promote to a write lock without releasing it first, closing the gap where another writer could sneak in between release and re-acquire.
Recursive (reentrant) read-write lock
Allows the same thread to re-acquire a mode it already holds — needed when locked code calls other locked code — but doubles the accounting and can deadlock if reentry rules aren't precise.

Trade-offs

Pros

  • Concurrent readers scale with core count instead of serializing behind one another.
  • Writes stay fully exclusive, so invariants hold exactly as they would under a plain mutex.
  • A natural drop-in for data that's read far more often than it's written — caches, config, routing tables.
  • Separates read and write contention, making which one is the bottleneck visible and tunable.

Cons

  • More overhead per acquisition than a plain mutex — tracking a reader count and a wait queue costs cycles a simple lock doesn't pay.
  • Naive implementations starve writers under constant read traffic, or starve readers under writer-preference.
  • Not reentrant by default; recursive acquisition needs deliberate support and can deadlock if mishandled.
  • On workloads where reads and writes are roughly balanced, the bookkeeping outweighs any parallelism gained.

When to use it

Reach for it when

  • Reads vastly outnumber writes on the same shared structure.
  • Read operations hold the lock long enough that serializing them under a plain mutex would bottleneck throughput.
  • Correctness only requires writers see a consistent snapshot, not a specific interleaving with reads.

Avoid when

  • Reads and writes arrive at roughly similar rates — the extra bookkeeping isn't repaid, use a plain mutex.
  • Critical sections are so short that lock overhead itself dominates, not contention.
  • Writes are frequent enough that readers rarely overlap anyway, so there's little concurrency left to win back.

Code sketch

TypeScript — a minimal async read-write lock 
class RwLock {
  private readers = 0;
  private writerActive = false;
  private queue: Array<() => void> = [];

  async readLock(): Promise<void> {
    while (this.writerActive) await this.park();
    this.readers++;
  }
  readUnlock(): void {
    if (--this.readers === 0) this.wakeAll();
  }

  async writeLock(): Promise<void> {
    while (this.writerActive || this.readers > 0) await this.park();
    this.writerActive = true;
  }
  writeUnlock(): void {
    this.writerActive = false;
    this.wakeAll();
  }

  private park(): Promise<void> {
    return new Promise((resolve) => this.queue.push(resolve));
  }
  private wakeAll(): void {
    this.queue.splice(0).forEach((wake) => wake());
  }
}

// usage
await lock.readLock();
try { /* read shared state */ } finally { lock.readUnlock(); }

In the wild

Go sync.RWMutexMany concurrent RLock holders or one Lock holder, implemented over runtime semaphores. A blocked writer stops new readers from acquiring, which bounds writer starvation but means a goroutine must never recursively RLock while a writer waits, or it deadlocks.
java.util.concurrent.locks.ReentrantReadWriteLockAdds reentrancy and an optional fairness flag in the constructor, and supports downgrading from the write lock to the read lock. Upgrading read to write is not supported and deadlocks; readLock() and writeLock() expose the two halves.
POSIX pthread_rwlockThe pthreads reader-writer primitive: pthread_rwlock_rdlock, wrlock, and unlock. glibc prefers readers by default; PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP via pthread_rwlockattr_setkind_np favors writers. ISO C has no equivalent; C11 threads.h ships only mutexes and condition variables.

In production

Tuning knobs

  • Fairness / preference policy — Reader-preference, writer-preference, or fair FIFO ordering. ReentrantReadWriteLock takes a fair boolean; glibc pthread_rwlock defaults to reader preference and switches via pthread_rwlockattr_setkind_np.
  • Acquire timeout — A tryLock with a timeout bounds how long a thread waits for the lock instead of blocking indefinitely.
  • Reentrancy — Whether a thread may re-acquire a lock it already holds. ReentrantReadWriteLock allows it and supports downgrade (hold write, take read, release write) but not upgrade.

Signals to watch

  • Read/write ratio — The fraction of acquisitions that are writes. A read-write lock only pays off when reads dominate and critical sections are non-trivial.
  • Writer wait time — How long writers block behind active readers. Growing values mean readers are starving writers.
  • Lock hold time — How long critical sections hold the lock and how long threads sit queued behind it.

Failure modes under load

  • Writer starvation — Under reader preference, a steady stream of overlapping readers can keep a writer waiting indefinitely.
  • Upgrade deadlock — Two readers that each try to upgrade to the write lock deadlock, since each waits for the other to release its read lock.
  • Worse than a mutex — When writes are frequent or critical sections are tiny, the extra bookkeeping of a read-write lock costs more than a plain mutex.

Readiness checklist

  • Measure the read/write ratio first; a plain mutex often wins unless reads clearly dominate.
  • Choose the fairness or preference policy deliberately to bound writer (or reader) starvation.
  • Never upgrade a read lock to a write lock; release and re-acquire, or use a lock that supports it.
  • Keep critical sections short; the write lock serializes every thread.
