Value Object

Defined only by its attributes, with no identity of its own — two instances holding the same data are simply the same value, immutable, freely comparable, and safe to share without a second thought.

DDD Lens

What it is

A value object models a concept whose full meaning is its attributes — a sum of money, a date range, a coordinate, an email address. Left as a bare number or string, that concept has nowhere to keep its rules: one caller reads the amount as pounds and the next as pence, any line can set it to minus five, and the same check gets pasted at every call site. Give it a type of its own and the rules travel with the data. It carries no identifier and no lifecycle: two with equal attributes are equal wherever each was built, and neither ever changes afterwards — an operation that looks like a mutation returns a new instance.

Behind that sits the question Domain-Driven Design asks of every concept: does this thing have a continuous existence you must track through change, or is it fully described by what it currently holds? A customer is tracked — the same customer after a name change is still that customer. Five dollars is not — any five dollars will do. Answering "tracked" by reflex, and giving every concept an id and a setter, is identity bloat: you end up maintaining a lifecycle nobody asked for, and equality that answers a question the domain never posed.

A value has no independent existence. It lives inside the entity or aggregate that owns it, and it is replaced wholesale rather than edited — changing a customer's address does not edit the Address, it hands the customer a different one. Asking which Address object this is has no answer in the domain, which is exactly why nothing needs to protect it.

Explained at three levels

Basic

Hand someone your shopping list and let them scribble on it, and your copy changes too. Money, dates and postcodes are not like that: any five pounds is as good as any other, so there is no "my" five pounds to protect. Build such a thing once, complete, and never let it be edited afterwards — to change it, make a new one. Two of them count as the same whenever their contents match.

Advanced

Equality and hash code read every component, so two separately built instances are interchangeable as set members and map keys, and nesting one inside another makes equality compose recursively down the tree. Because nothing refers to this particular instance, a runtime or library is free to cache and reuse equal values — which is why comparing two of them with reference equality is a bug rather than a shortcut. What you pay is replacement: changing a field deep inside a nested value rebuilds every value along the path to it.

Expert

The usual failure is under-use — a one-field wrapper feels like ceremony, so the raw string stays and its validation is copy-pasted across a dozen call sites; the counter-move is a wrapper per validated primitive, declared with the language's record or data-class support so it costs a line rather than a file. Then the bill. Hand-written equality that misses a field silently reintroduces the identity bugs you adopted the pattern to remove, so derive equality from the components instead of writing it out. Allocation churn bites on hot paths where a value is rebuilt inside a loop — reuse the common instances or hoist the rebuild out. And row-oriented storage has nowhere to put a thing with no key, so embed its columns in the owning entity's row or serialize it into one.

How it works

Variations

Immutability
Fields are set once at construction and never reassigned; every "change" produces a new instance instead. This is less an optional variant than the core discipline that makes the rest of the pattern safe.
Self-validating value
The constructor enforces its own invariants — a Money that rejects negative cents, an Email that checks its format — so an invalid instance simply cannot exist.
Value object with behavior
Operations like add(), overlaps(), or format() live on the value itself and return new instances, keeping domain logic beside the data it acts on.
Structural (composite) value
Built from other value objects — an Address composed of Street, City, and PostalCode — with equality defined recursively across every part.

Trade-offs

Pros

  • Equality by value eliminates whole classes of aliasing bugs — equal data means interchangeable.
  • Immutability makes instances safe to share, cache, and pass across threads without defensive copies.
  • Validates its own invariants at construction, so an invalid instance can never exist.
  • Keeps domain logic — formatting, arithmetic, comparison — next to the data instead of scattered in services.

Cons

  • Every "change" allocates a new instance — real churn and GC pressure at scale if overused.
  • Equality and hashing must compare every field; forgetting one silently reintroduces identity bugs.
  • Persistence layers built around row identity often force embedding or serialization workarounds.
  • Easy to under-use — a thin primitive wrapper feels like ceremony, so primitive obsession creeps back in.
  • Value or entity is a call each model makes for itself, not a property of the concept: an address is a value to the shipping context and an identified thing to the utility that bills the premises, so a classification carried across a service boundary is wrong as often as it is right.

When to use it

Reach for it when

  • A concept is fully described by its attributes, and no two with the same attributes should be told apart — money, a date range, a coordinate.
  • You want equality, comparison, and hashing based on content rather than reference.
  • You're validating the same primitive — an email, a percentage, a currency amount — in more than one place.

Avoid when

  • The concept has a continuous lifecycle that must be tracked even as its attributes change — that's an Entity.
  • Persistence or a client needs to reference this exact instance independent of its current data.

Code sketch

TypeScript — an immutable Money value 
class Money {
  private constructor(
    readonly amountCents: number,
    readonly currency: string,
  ) {
    if (!Number.isInteger(amountCents)) {
      throw new Error("amount must be whole cents");
    }
  }

  static of(amountCents: number, currency: string): Money {
    return new Money(amountCents, currency);
  }

  add(other: Money): Money {
    if (other.currency !== this.currency) throw new Error("currency mismatch");
    return new Money(this.amountCents + other.amountCents, this.currency); // new instance
  }

  equals(other: Money): boolean {
    return this.amountCents === other.amountCents && this.currency === other.currency;
  }
}

const a = Money.of(500, "USD");
const b = Money.of(500, "USD");
a.equals(b); // true  — same value, no shared identity
a === b;     // false — different objects, and that's fine

In the wild

java.timeLocalDate, Duration and Instant are documented value-based classes: immutable, self-validating, and compared by their components rather than by reference. Their Javadoc warns against identity-sensitive operations such as == comparison or synchronizing on an instance, since implementations may cache or intern values.
Java recordsA language-level value aggregate, final since Java 16: the compiler makes the components final and derives equals, hashCode and toString from them, giving component-wise value equality without hand-written boilerplate.
