Lens · Domain-Driven Design

Aggregate

A cluster of entities and value objects bound behind one root and saved as a unit, so a rule that spans them is never left half-enforced.

DDD Lens

What it is

An aggregate is a cluster of domain objects — entities and value objects — that the model treats as one unit whenever its data changes. One entity in it is the aggregate root: the only member outside code may reference, and the door every command comes through.

It exists for an invariant that spans more than one object: an order's total must equal the sum of its lines. If any code can edit a line directly, nobody owns that rule — one path adds a line and forgets the total, another writes a total from a stale read, and a customer finds the mismatch. Hiding the internals behind the root leaves one place that can break the rule and one that checks it, at the price of reaching line items only through the order's own methods.

Persistence follows the boundary. A repository loads the whole cluster and writes it back as one atomic save, and a version on the root turns two concurrent writers into one success and one rejected save rather than a half-applied change. An event-sourced root swaps that stored snapshot for a fold over its past events, with periodic snapshots to bound the cost of the fold.

The design fails in either direction. Draw the boundary too small and invariants leak back out into services that reach across several roots by hand; draw it too large and unrelated data gets dragged into every transaction, turning each write into a lock that competes with everything else touching that root.

Explained at three levels

Basic

Picture a paper order form: the total at the bottom must match the lines above it. Let three clerks scribble on separate lines and the total drifts until a customer complains. So one person holds the form — every change is asked of them, and they re-add the total before handing it back. One object owns the data and refuses any edit that leaves the numbers disagreeing.

Advanced

The rule that makes this work is one cluster per transaction. A command arrives at the root, which validates and commits alone; anything it needs to change in another cluster is deferred rather than joined in. So clusters hold each other by identity, never by object reference, and agreement across a boundary is eventual by construction — a domain event carries the change and a second transaction applies it.

Expert

Choose the boundary from the invariants that must hold inside a single transaction and let everything else be eventual, because that one choice sets your lock granularity. A boundary drawn around a contended field serializes commands that never conflicted; pay for it by splitting that field into its own root, or by budgeting conflict retries. Eventual agreement between roots buys the throughput and costs machinery: an outbox to publish reliably, a process manager to close the gap, and consumers that tolerate a window where the two sides disagree. Reference neighbours by identity from the first line, so redrawing a boundary later is a change to one root's methods rather than to every consumer's object graph.

How it works

Variations

Reference by identity
An aggregate holds other aggregates by ID, never by object reference, so each cluster stays small and independently transactional.
Domain events on commit
The root records events internally as it mutates; they're published only after the transaction that saved it has actually succeeded.
Event-sourced aggregate
State is derived by folding a stored stream of past events rather than loaded as a snapshot; a command only ever produces new events, never a direct field write.
Aggregate factory
Multi-step construction — assembling an Order from a cart, say — is delegated to a dedicated factory, so the root's constructor stays a simple, valid-by-construction call.

Trade-offs

Pros

  • Invariants spanning multiple objects are enforced in one place, not scattered across services.
  • A clear transaction boundary — one aggregate is one atomic load and save, no partial updates.
  • Encapsulation: internal entities are hidden, so their rules can't be bypassed from outside.
  • Concurrency control stays tractable — version or lock the root, not a web of related tables.

Cons

  • An aggregate that grows too large drags unrelated data into every transaction and lock.
  • Cross-aggregate consistency becomes eventual, which needs real machinery — events, sagas — to close.
  • Choosing the right boundary is genuinely hard, and a wrong one is expensive to redraw later.
  • Loading a large aggregate can pull in far more data than a single command actually needs.

When to use it

Reach for it when

  • Several objects share an invariant that must never be violated, like a total matching its parts.
  • You need a clear transaction boundary for saving and loading a related cluster of data.
  • The domain has a natural grouping that only makes sense together, like an order and its line items.

Avoid when

  • The objects share no real invariant — plain Entities or Value Objects suffice.
  • You're tempted to widen the boundary "just in case" — that's exactly how aggregates balloon and lock contention appears.
  • The true consistency requirement is eventual, not immediate — reference the other side by ID and let a Domain Event synchronize it later.

Prevents the smell of an Anemic Domain Model, where the rules that belong on the root leak into service code.

Code sketch

TypeScript — an Order aggregate root 
class Order { // aggregate root
  private readonly items: LineItem[] = [];

  addItem(sku: string, quantity: number, unitPrice: Money): void {
    if (quantity <= 0) throw new Error("quantity must be positive");
    this.items.push(new LineItem(sku, quantity, unitPrice));
  }

  get total(): Money {
    return this.items.reduce((sum, i) => sum.add(i.subtotal), Money.zero());
  }
}

// LineItem is reachable only through Order.
class LineItem {
  constructor(readonly sku: string, readonly quantity: number, readonly unitPrice: Money) {}
  get subtotal(): Money { return this.unitPrice.times(this.quantity); }
}

In production

Tuning knobs

  • Aggregate boundary size — How much sits inside one root. Wider locks more on every command; narrower pushes invariants out into service code.
  • Optimistic concurrency version — A version field or timestamp on the root that each write checks against the loaded value, rejecting the save on mismatch. The alternative, pessimistic locks held across the transaction, trades throughput for fewer conflicts.
  • Conflict retry policy — How many times a command is replayed when an optimistic version check fails before the failure surfaces to the caller.
  • Snapshot frequency — For an event-sourced root, how many events accumulate before a state snapshot is written, so a load does not re-fold the entire history every time.

Signals to watch

  • Version-conflict rate — How often a save is rejected because another writer changed the same root first. A climbing rate flags a hot root.
  • Aggregate hydration cost — Rows or bytes pulled to reconstruct one aggregate, and the time to do it. Growth signals a boundary that has ballooned.
  • Command retry count — Retries per command driven by conflict, a proxy for contention on the hottest roots.

Failure modes under load

  • Hot aggregate contention — Commands crowd onto one root — a shared counter, say — and retries pile up until throughput collapses there.
  • Oversized aggregate — A boundary drawn too wide loads and locks unrelated data on every command, so each write competes with everything else touching the root and transactions slow.
  • Unbounded event replay — An event-sourced aggregate with a long history and no snapshotting re-folds thousands of events on each load, and hydration time creeps upward.

Readiness checklist

  • Reference other aggregates by identity, never by object reference.
  • Guard the root with an optimistic version and settle the conflict-retry policy before load appears.
  • Publish domain events only after the aggregate transaction has committed, never inside it.
  • Confirm each invariant genuinely spans the cluster; if it does not, the boundary is too wide.
