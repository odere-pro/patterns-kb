Message Router

Inspects each incoming message against a set of rules and forwards it, unchanged, to exactly one of several output channels — so senders never have to know who's listening or how many consumers exist.

Messaging Lens

What it is

A message router is a filter that sits on a single input channel and, based on a set of conditions, forwards each message to exactly one of several possible output channels. It doesn't split, transform, or enrich the message — it only decides where it goes next, using whatever it needs to make that call: a header, a message type, the sender's identity, or an external rule table. The body passes through untouched.

The force it resolves is routing knowledge that doesn't belong to the sender. Without a router, every producer would need to know the full set of possible consumers and pick among them directly — hardcoding destination logic into business code that has nothing to do with routing. The router centralizes that decision: producers publish to one channel, the router owns the mapping from condition to destination, and either side can change without touching the other.

It's the base of a small family. A plain router evaluates fixed rules against message metadata; a Content-Based Router inspects the payload itself to decide; a dynamic router loads its rules from a registry so they can change without a redeploy; and a recipient list abandons the "exactly one" constraint entirely, fanning the same message out to every channel that matches.

Explained at three levels

Basic

The order service holds the address of the refunds handler, the support desk and the fulfilment team, and picks between them itself. Add a fourth handler and you edit the order service, which has no business knowing who reads its messages. Put one step in between instead: senders write to a single address, and that step reads the label on the outside of the message — what kind it is, who sent it — and hands it to the one handler it belongs to. The message is passed on exactly as it arrived, and anything the labels do not cover goes to a default handler rather than disappearing.

Advanced

That step is a stateless filter with one input channel and several output channels, and it decides from metadata alone — a header, the message type, the sender's identity, or a lookup in a rule table. Because it never parses the body, the decision costs the same whatever the payload is and survives a payload schema change untouched. Rules are ordered and first match wins, so a broad rule placed above a narrow one shadows it permanently, and the fall-through case needs a real default channel or unmatched messages dead-end. Three variants differ in where the rules live: a static router compiles them in and needs a redeploy to add a route, a dynamic router re-reads them from a registry or control channel at runtime, and a recipient list keeps the same evaluation but drops the exactly-one constraint and delivers to every rule that matched.

Expert

Reach for it when the destination follows from metadata and the mapping changes on a different schedule from the code on either side; skip it when the broker can do the same job with bindings, because a topic exchange matching routing keys costs you no component to operate. Three costs, each with a counter-move. Every message crosses one component, so it is both a coupling point and a throughput ceiling — keep evaluation to a header lookup and run a stateless replica pool off the same input channel, since nothing in the decision is stateful. A misroute is silent, because the body arrives intact and the wrong consumer processes it happily — watch per-channel distribution for a channel that drops to zero, and carry a correlation identifier so one message's path is reconstructable. Rule sets sprawl into decision trees nobody dares edit, and rules that read mutable external state cannot be reasoned about statically — version the rule set, review changes like code, and test each rule against representative messages. Then run the loop: tune evaluation order and the reload interval, watch the unroutable rate, expect no-match-with-no-default to lose messages first, and gate release on a fallback channel that exists and is alerted.

How it works

Variations

Content-Based Router
Routes by inspecting the message body itself, rather than a header or an external rule table.
Static / rule-table router
A fixed, config-file or hardcoded mapping from condition to channel — simplest form, but adding a route means a redeploy.
Dynamic router
Rules are loaded from a registry or control channel and can be changed or reloaded at runtime without touching the router's code.
Recipient list
Sends the message to every channel that matches, not just one — a fan-out cousin rather than an exclusive routing decision.

Trade-offs

Pros

  • Centralizes routing logic, so producers stay decoupled from the number and identity of consumers.
  • New destinations are added by changing the router's rules, not the sender's code.
  • Leaves the message body untouched — routing stays a separate, easily reasoned-about concern.
  • Rules live in one place, so they're testable and auditable instead of scattered across senders.

Cons

  • The router becomes a single point of coupling — and potentially a throughput bottleneck.
  • Rule sprawl turns a simple router into an unmaintainable decision tree over time.
  • Debugging a misrouted message means auditing the router's rules, not just the message.
  • Rules that depend on external or mutable state make routing behavior harder to predict statically.

When to use it

Reach for it when

  • Multiple downstream consumers exist and the right one depends on something other than the message body.
  • Senders should stay ignorant of how many consumers exist or where they run.
  • Routing logic changes often enough that it shouldn't be baked into producer code.

Avoid when

  • There's only one possible destination — a direct channel needs no router at all.
  • The decision genuinely depends on the message's content — reach for Content-Based Router instead.
  • Every consumer needs the same message — that's a fan-out, not an exclusive routing decision.

Code sketch

TypeScript — a rule-based router 
type Channel = "orders" | "refunds" | "support";

interface Message {
  headers: Record<string, string>;
  body: unknown;
}

type Rule = { matches: (m: Message) => boolean; channel: Channel };

class MessageRouter {
  constructor(
    private readonly rules: Rule[],
    private readonly fallback: Channel,
  ) {}

  route(message: Message): Channel {
    for (const rule of this.rules) {
      if (rule.matches(message)) return rule.channel;
    }
    return this.fallback; // nothing matched
  }
}

const router = new MessageRouter(
  [
    { matches: (m) => m.headers["type"] === "refund", channel: "refunds" },
    { matches: (m) => m.headers["priority"] === "vip", channel: "support" },
  ],
  "orders",
);

publish(router.route(incoming), incoming); // decide once, forward unchanged

In the wild

Apache CamelIts routing DSL implements the EIP catalog directly: choice().when().otherwise() for a content-based router, routingSlip() for a route read from a header, dynamicRouter() for rules evaluated per message, and recipientList() for fan-out.
Spring IntegrationShips router endpoints — HeaderValueRouter, PayloadTypeRouter, or a SpEL expression — that resolve one input channel to an output channel, with a default-output-channel for unmatched messages.
RabbitMQ exchangesA direct exchange matches the routing key to a binding exactly, a topic exchange matches routing-key patterns with the * and # wildcards, and a headers exchange routes on header attributes instead — publishers address the exchange and bindings decide the queue.

In production

Tuning knobs

  • Default / fallback channel — Where a message matching no rule goes; without one, unmatched messages are dropped or dead-ended.
  • Rule evaluation order — First-match vs. evaluate-all ordering of the rule list decides which of several matching rules wins.
  • Rule reload interval — For a dynamic router, how often rules are re-read from the registry or control channel without a redeploy.

Signals to watch

  • Unroutable / fallback rate — Fraction of messages hitting the default channel or matching no rule; a spike means the rules have drifted from the traffic.
  • Per-channel distribution — Message counts per output channel; a channel that suddenly drops to zero flags a broken or shadowed rule.
  • Routing latency per message — Time to evaluate the rule set, which matters when a rule consults external or mutable state.

Failure modes under load

  • Silent misroute — A wrong rule forwards a message to the wrong channel; because the body is untouched, nothing downstream signals the error.
  • No match, no fallback — A message that satisfies no rule and has no default channel is dropped or dead-ended.
  • Stale external rule table — Rules that depend on mutable state route to a decommissioned or renamed channel after the topology changes underneath them.
  • Router bottleneck — All traffic funnels through one router; heavy per-message rule evaluation makes it the throughput ceiling for everything downstream.

Readiness checklist

  • A default or fallback channel exists for messages that match no rule
  • Rules are tested in isolation against representative messages
  • Unroutable-message rate is monitored and alerted
  • Rule changes are versioned and reviewable, not edited live without a record
