Correlation Identifier

Stamps every request with a unique token that each downstream reply, retry, or log line copies verbatim — so a flood of concurrent, asynchronous messages on a shared channel can still be traced back to the one conversation that produced them.

Messaging Lens

What it is

You send three requests onto the same channel and go on with other work. Three answers come back later, in whatever order the network produced them, mixed in with answers meant for somebody else entirely. Nothing on any of them says which question it answers. Guess by arrival order and you will be right until the day one reply is slow, and then you hand a customer somebody else's result — a wrong match that only shows up under load is far worse than one that fails loudly. A correlation identifier is the fix everyone reinvents: write a unique ticket number on the way out, and have whoever replies write the same number back.

A token — a UUID, a monotonic sequence number, or a business key already known to be unique — stamped into a message header when a request goes out, and copied verbatim by every participant that emits anything tied to that request. Its shape means nothing to the messaging infrastructure. It exists so a listener can ask which conversation this belongs to and get one unambiguous answer, whatever order things arrive in.

The pattern generalizes past a single request/reply pair. Thread the same identifier through every hop of a longer chain — a message that fans out to several services, a saga's sequence of compensating steps, a request that crosses five microservices before it produces a response — and every log line, span, and metric emitted along the way can be filtered down to the one logical operation, even though the systems that emitted them share nothing else in common.

It's deliberately distinct from a message ID. A message ID names this one message and dies with it; a correlation ID names the conversation or operation the message is part of, and many messages across many systems can legitimately share it.

Explained at three levels

Basic

You ask three questions at once and the answers come back much later, in any order, mixed in with answers meant for other people. Nothing on an answer says which question it belongs to. Matching them up by whichever arrives first works right up until one answer is slow — and then somebody gets a result that was never theirs, which is the kind of bug that only appears when the system is busy. So write a unique ticket number on each question as it goes out, and have whoever answers write the same number back. Now the order does not matter: read the number, find the question. It is the numbered slip at a coffee shop — drinks come up in whatever order they finish, and every one still finds the right person. Keep a note of the numbers you are still waiting on, and give up on the ones that never come back.

Advanced

A token — a UUID, a sequence number, or a business key already known to be unique — stamped into a message header on the way out and copied verbatim by every participant that emits anything downstream. It names the conversation rather than the message, which is exactly what separates it from a message id: a message id dies with its message, while one correlation id can legitimately appear on hundreds of messages across systems that share nothing else. The variants differ in what the id spans. Classic request/reply puts a GUID in a dedicated header (JMSCorrelationID, AMQP correlation_id) and the responder echoes it onto the reply queue. A fan-out uses it as the aggregation key, so a collector knows which replies belong to which request. A distributed trace id (W3C traceparent) is the same idea propagated across every hop, which is what joins spans from unrelated services into one trace. And a long-running workflow threads one id through its steps, so completion, compensation and timeout handlers all know which instance they belong to.

Expert

Adopt it the moment more than one conversation shares an asynchronous channel: it costs one header field and buys order-independent matching plus a free join key across logs, spans and metrics — at small scale that is a tracing stack you did not have to install. The bill is discipline rather than machinery, on three lines. Every hop must re-emit the id unchanged, and one component that regenerates it breaks the chain silently, under load, far from where anyone notices — so assert the id on ingress and treat a missing one as an error rather than minting a fresh one. The requestor pays separately: pending ids need both a timeout and a hard ceiling, or a downstream that stops replying turns into unbounded memory in the caller. Uniqueness has to be earned, not assumed — a business key reused across concurrent conversations attributes a reply to the wrong requestor, which is a data-integrity bug wearing a matching bug's clothes. And be clear what it does not do: it marks relatedness only, so completeness needs an aggregator that knows how many replies to expect, and ordering needs a sequence number of its own. Then run the loop — tune the pending timeout and the id scheme, watch the pending-map size and the unmatched-reply rate, expect leaked pending entries to bite first, and gate the release on ingress assertion and a bounded map.

How it works

Variations

Message-header correlation ID
The classic form — a GUID placed in a header field (JMSCorrelationID, AMQP's correlation_id) that the responder copies straight from the request into the reply.
Business key as correlation ID
Reuse a domain identifier that's already unique — an order id, a session id — instead of minting a synthetic token. Cheaper, but only safe when that key genuinely can't repeat across concurrent conversations.
Scatter-Gather aggregation key
One correlation id ties every parallel reply back to a single fan-out request, so the aggregator knows when it has collected them all.
Distributed trace ID
The same idea propagated across every hop of a call chain (W3C traceparent, X-Request-Id) so logs and spans from otherwise unrelated services join into one trace.
Saga correlation
One id threads every step of a long-running saga, so its completion, compensation, and timeout handlers all know which instance they belong to.

Trade-offs

Pros

  • Lets one channel or queue carry many concurrent conversations without cross-talk between them.
  • Replies can arrive in any order, or interleaved with unrelated traffic, and still land on the right pending request.
  • Costs almost nothing to add — one extra header field, copied verbatim at every hop.
  • Extends directly into distributed tracing: the same mechanism stitches a whole multi-service call into one story.

Cons

  • Every hop must copy the id correctly — one component that drops or regenerates it silently breaks the chain. Assert the id on the way in and reject a message without one, rather than minting a fresh id and losing the thread.
  • The requestor must track pending correlation ids itself, with timeouts, or a reply that never arrives leaks memory forever — give the pending map a hard ceiling as well as an expiry, so a silent downstream degrades instead of exhausting the caller.
  • A collision or an accidentally reused id attributes a reply to the wrong requestor — use a random UUID unless a business key is provably unique across concurrent conversations.
  • It only marks messages as related — it provides no ordering and no guarantee that every expected reply actually arrived.
  • Completeness needs a second mechanism on top: something has to know how many replies to expect and what to do when one never comes, which is the job of a scatter-gather aggregator, not of the id.
  • An id that reaches a log or an audit trail carries whatever it was derived from — a business key used as a correlation id puts an order number, or worse, into every span and log line a third party might hold.

When to use it

Reach for it when

  • Multiple requests are in flight at once over the same asynchronous channel or queue.
  • Replies can arrive out of order, or interleaved with unrelated messages, and still must land on the right caller.
  • One logical operation spans several services or processes and needs to be traced as a single unit.

Avoid when

  • The exchange is a synchronous request/reply call — the open connection already correlates request and response for free.
  • Only one request is ever outstanding at a time, so there's nothing to disambiguate.
  • You need the workflow around the correlated messages managed, not just the matching — reach for Scatter-Gather or Saga.

Code sketch

TypeScript — matching vendor callbacks back to their flow 
interface Callback { flowId: string; payload: unknown; }

class CorrelatingVendorClient {
  private pending = new Map<string, (cb: Callback) => void>();

  // flowId is minted once when the flow is created, not per call: the same id
  // rides every transition, task row, vendor request and the final webhook.
  async request(flowId: string, payload: unknown): Promise<Callback> {
    return new Promise<Callback>((resolve) => {
      this.pending.set(flowId, resolve);
      idVendor.send({ flowId, payload });
    });
  }

  // Called whenever the vendor calls back into the API.
  onCallback(cb: Callback) {
    const resolve = this.pending.get(cb.flowId);
    if (!resolve) return; // unknown, late, or already-handled callback
    this.pending.delete(cb.flowId);
    resolve(cb);
  }
}

In the wild

W3C Trace ContextStandardizes the traceparent header — version, 16-byte trace-id, 8-byte span-id, and flags — plus a tracestate header for vendor data, so every service in a call chain propagates one trace id that joins otherwise unrelated spans into a single trace.
JMS JMSCorrelationIDA standard JMS header the responder copies from the request into the reply so the requestor can match it against its pending calls; typically paired with JMSReplyTo, which names the queue the reply should return on.
AMQP correlation_idA dedicated message property carried alongside reply_to; the RabbitMQ RPC tutorial documents using the two together to implement request/reply over queues, the responder echoing the correlation_id back on the reply-to queue.

In production

Tuning knobs

  • Pending-request timeout — How long the requestor keeps a correlation entry waiting for its reply before expiring it and reclaiming the slot.
  • Pending-map ceiling — The maximum number of outstanding correlations the requestor will hold at once, and what it does on reaching it — reject, shed, or block.
  • ID generation scheme — Random UUID versus a reused business key; it sets how much collision resistance you have when many conversations share one channel.
  • Propagation header — Which header carries the id (traceparent, X-Request-Id, JMSCorrelationID), and therefore what every hop has to read and re-emit.

Signals to watch

  • Outstanding pending correlations — Size of the requestor pending map, next to its ceiling — the number that tells you whether replies are coming back at all.
  • Unmatched reply rate — Replies whose correlation id has no pending entry — late, unknown, or an id that was dropped or regenerated somewhere upstream.
  • Missing-id rate on ingress — Messages arriving with no correlation header at all, counted per upstream — this names the component that is breaking the chain.
  • Request-to-reply latency — Time from stamping the id on a request to matching its reply, measured per correlation.

Failure modes under load

  • Leaked pending entries — A reply that never arrives, with no timeout on the pending map, grows the requestor state without bound until the process dies.
  • Dropped or regenerated id — One hop that fails to copy the id verbatim breaks the chain, and every reply behind it becomes unmatchable.
  • Collision or reuse — A repeated or accidentally reused id attributes a reply to the wrong requestor — a silent, load-dependent mismatch.
  • Late reply after expiry — A reply arriving after its pending entry timed out has nowhere to land; without a defined path it is dropped silently, and the work it reports on looks like it never finished.

Readiness checklist

  • Every pending correlation expires, and the expiry path is exercised in tests rather than first in an incident
  • The pending map has a hard ceiling as well as a timeout, so a silent downstream degrades instead of exhausting memory
  • Ids are collision-resistant, or the business key used instead was shown to be unique across concurrent conversations
  • Ingress asserts the id is present and rejects rather than minting a replacement, so a broken chain is loud
  • A reply that arrives after its entry expired has a defined destination and is counted, not dropped
  • The id carries no data you would not want in a log line or a third-party trace
