Claim Check

Stores a bulky payload in durable storage and lets only a lightweight reference — the claim check — travel through the message channel, so the channel stays fast and the data moves only when a consumer actually redeems it.

Messaging Lens

What it is

A customer uploads a 30 MB scan of their passport, and you put it on the queue. The broker rejects it outright, or it accepts it and now every message behind it moves slower, because the channel was built for thousands of small notes and you just posted a suitcase through it. Four of the five services listening only wanted to know that a document arrived — none of them ever opens the file. A claim check separates the two: store the file once somewhere built for files, and put only its address on the queue. Whoever actually needs the bytes goes and gets them.

The producer writes the payload to durable shared storage, waits for that write to confirm, then publishes a message carrying only a key or a presigned URL. The consumer that genuinely needs the bytes redeems the reference against the store; the rest route on the metadata and never touch it. That keeps traffic inside the broker's practical limits — Kafka defaults to a 1 MB message cap, SQS to 256 KB — and it lets storage and messaging scale on their own terms, the bulk data sitting wherever it is cheapest to hold.

The name comes from the same idea as a coat check or an airport baggage tag: you hand over the bulky item once, get back a small ticket, and only redeem the ticket for the item when you actually need it back.

Explained at three levels

Basic

A message channel is built for one thing: moving enormous numbers of small notes quickly. The moment you hand it something big, it stops being good at that — it either refuses the item outright or it accepts it and everything queued behind it slows down. The interesting part is that the big thing is usually not what the readers wanted anyway. Most of them only need to know that a document arrived; one of them, eventually, opens it. So split those two jobs. Put the file somewhere built for files, take back the little ticket that names it, and send only the ticket. Whoever needs the contents swaps the ticket for them. Two rules come with it and neither is optional. The file has to be safely stored before the ticket goes out, or somebody redeems a ticket for nothing. And someone has to throw the old files away on a schedule, because handing back a ticket deletes nothing.

Advanced

The broker limits are what force the split — 256 KB by default on SQS, 1 MB by default on Kafka — and under them sits a second cost: every consumer that only routes on metadata was paying to move bytes it never opened. The variants differ in what the reference is and who can use it. An opaque key needs a shared client and credentials on the consumer side; a time-boxed presigned URL is fetchable by anything that holds it, at the cost of an expiry you now have to size. A content-addressed reference — the hash of the payload — makes identical bodies collapse to one stored object and lets a consumer verify that what it fetched is what was sent. And whichever you pick, the stored objects need a lifecycle rule, because a redeemed claim check does not delete anything by itself.

Expert

Adopt it when payloads routinely strain the channel, or when most consumers only filter on metadata: you are trading a broker problem for a two-system invariant, and the invariant is where the work is. The store write and the publish are not atomic, so a crash between them leaves either an orphaned object or a reference to data that does not exist — order the write first and make the publish ride an outbox when the pair has to hold. Retention has to outlive your slowest consumer and your whole replay window, because a redelivery six days later redeems nothing if the lifecycle rule swept the object on day five. The store also joins the critical path: its outage no longer loses messages, it stalls every consumer that needs a body, which is a different incident with a different runbook. There is an upside worth naming — sensitive payloads never enter the broker at all, so the store's own access controls guard them and queue tooling only ever sees a reference. Costs you keep paying: a round trip on every redemption, and harder debugging, because the message tells you where to look rather than what happened. Then run the loop — tune the offload threshold and retention, watch fetch errors and orphaned-object growth, expect a phantom reference to be your first real incident, and gate the release on a confirmed-write ordering and a consumer that handles a missing object on purpose.

How it works

Variations

Store-first hand-off
The producer writes the payload to the store and waits for confirmation before publishing the claim check, so the message never references data that isn't there yet.
Reference as pre-signed URL
The claim check is a time-boxed, directly fetchable URL rather than an opaque key, so any consumer can retrieve the payload without a shared client library or extra credentials.
Content-addressed claim check
The reference is a hash of the payload itself, so identical bodies collapse to one stored object and a consumer can verify what it fetched matches what was sent.
Claim check with TTL / cleanup
Stored objects expire or get swept after a retention window, so an unredeemed or already-consumed claim check doesn't leave storage growing forever.

Trade-offs

Pros

  • Keeps the message channel fast by capping what actually crosses it to a small reference.
  • Consumers that don't care about the payload never pay to move, deserialize, or buffer it.
  • Storage and messaging scale independently — cheap object storage for bulk data, a lean broker.
  • The payload can be inspected, versioned, or reprocessed in the store without replaying the message.
  • Sensitive payloads never enter the broker — the store's own access controls guard them, and queue-monitoring tooling only ever sees the reference.

Cons

  • Adds a network round trip and a second system — the store — that must be up for the message to be useful.
  • Two writes, store then queue, aren't atomic — a crash between them leaves an orphaned object or a phantom reference. Write to the store first, and put the publish behind an outbox when the pair genuinely has to hold.
  • Someone has to garbage-collect stored payloads once every claim check is redeemed or expires — a lifecycle rule on the bucket, not a promise to remember.
  • Debugging is harder: the message body only tells you where to look, not what happened.
  • Retention becomes a correctness setting rather than a cost setting: sweep the object before the slowest consumer or a replay gets to it, and the reference redeems nothing.
  • The store is now on the critical path. Its outage no longer loses messages — it stalls every consumer that needs a body, which is a different incident and needs its own runbook.

When to use it

Reach for it when

  • A payload routinely exceeds the broker's practical or hard message-size limit.
  • Most consumers only need to route or filter on metadata, not the full body.
  • Storage and message-channel throughput need to scale independently.

Avoid when

  • Payloads are consistently small enough to fit the channel without strain — the extra store round trip only adds latency.
  • The store write and the message publish must be atomic — pair with an outbox instead of send-and-hope.
  • Only one consumer ever exists and it always needs the full payload immediately — just send it inline.

Code sketch

TypeScript — store the bytes, send the address 
// Producer: the file goes to storage first, and only its key goes on the queue.
async function submit(photo: Buffer) {
  const photoKey = await store.put(photo);   // wait for the write to confirm
  await queue.send({ type: "verify", photoKey });
}

// Consumer: redeem the key for the bytes, but only if you actually need them.
async function verify(msg: { photoKey: string }) {
  const photo = await store.get(msg.photoKey);
  await idVendor.verify(photo);
}
TypeScript — flow steps that pass a photo key, never the photo 
interface ClaimCheckStore {
  put(payload: Buffer): Promise<string>;   // returns a storage key — the claim check
  get(key: string): Promise<Buffer>;
}

interface Task {
  flowId: string;
  personaId: string;
  type: "verify" | "screen";
  photoKey: string;                        // the check, not the image
}

async function submitIdPhoto(
  flowId: string,
  personaId: string,
  photo: Buffer,
  store: ClaimCheckStore,
  queue: { send(task: Task): Promise<void> },
): Promise<void> {
  const photoKey = await store.put(photo);              // bytes land in the store first
  await queue.send({ flowId, personaId, type: "verify", photoKey });
}

async function runVerify(
  task: Task,
  store: ClaimCheckStore,
  idVendor: IdVendor,
  queue: { send(task: Task): Promise<void> },
): Promise<void> {
  const photo = await store.get(task.photoKey);         // redeem the check for the bytes
  await idVendor.verify(task.flowId, photo);
  await queue.send({ ...task, type: "screen" });        // hand on the key, never the image
}

In the wild

Amazon SQS Extended Client LibraryTransparently stores oversized payloads in an S3 bucket and sends only the object pointer on the queue — built around the classic 256 KB SQS message size, today the default rather than the cap (raised to 1 MiB in 2025). payloadSizeThreshold sets the offload cutoff and alwaysThroughS3 forces every payload through S3; the receiving client fetches the object and can delete it after processing.
Apache Camel claimCheck()The Claim Check EIP offers Set/Get/Push/Pop operations against a keyed repository: it moves the message body into the store under a claim-check key and replaces the exchange body with that key, then a later Get or Pop step restores the body on demand within the route.

In production

Tuning knobs

  • Offload size threshold — The payload size above which the body goes to the store and only a reference is sent, versus sending it inline (SQS Extended Client payloadSizeThreshold, or an always-offload flag).
  • Store retention / TTL — How long a stored payload lives before a lifecycle rule reclaims it (object-store lifecycle expiration).
  • Reference expiry — When the claim check is a time-boxed presigned URL, the validity window of that URL before it stops resolving.
  • Store durability / class — Which storage tier holds the payload — the durability and read-latency trade for the bytes taken off the channel.

Signals to watch

  • Store fetch latency — The added round trip a consumer spends redeeming the reference — pure overhead on every message whose body is actually needed.
  • Fetch error rate — References that resolve to a missing or unavailable object — phantom references and premature cleanup both surface here first.
  • Orphaned object growth — Stored payloads no message points at — a rising floor of storage nothing will ever redeem or delete.
  • Offload ratio — Fraction of messages sent by reference versus inline; it confirms the threshold is diverting the payloads you meant it to.

Failure modes under load

  • Phantom reference — Publishing the message before the store write commits, or crashing between the two, leaves consumers holding a reference to data the store does not have.
  • Orphaned payload — The store write succeeds but the publish fails, so the object sits in storage with no claim check that will ever redeem or delete it.
  • Store outage blocks consumers — The reference is valid but the store is down, so a message that crossed the channel fine is useless until the store recovers — consumers stall rather than fail.
  • Premature expiry — A retention window shorter than a slow consumer or a replay needs sweeps the payload before it is redeemed, and the redelivery finds nothing.
  • Redemption stampede — A fan-out means every subscriber redeems the same reference at once, so one published message becomes N concurrent reads of one object.

Readiness checklist

  • The store write is confirmed before the reference is published, and the crash-between-the-two case has a decided outcome rather than an assumed one
  • Retention was compared against the slowest consumer's observed lag and the full replay window, not set to a round number
  • A lifecycle rule or sweep reclaims objects no claim check will redeem, and its effect is measured rather than assumed
  • Consumers handle a missing object explicitly instead of treating the fetch as infallible
  • Where the store write and the publish must be atomic, the publish goes through an outbox
  • Access control on the store is at least as strict as on the channel, since the payload no longer travels with the message
