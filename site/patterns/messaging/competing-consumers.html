Lens · Messaging

Competing Consumers

A pool of interchangeable consumers pulls from one shared channel, so a single message goes to one worker at a time and the pool's combined throughput — not any one consumer's — sets the pace.

Messaging Lens

What it is

Jobs pile into a queue faster than the one program reading it can finish them. Each one takes two seconds, four arrive every second, and the line only ever gets longer — by evening a receipt that should have gone out at once is hours old, and nothing in the code is wrong. You cannot make the one worker twice as fast, and you cannot ask the senders to slow down. Competing consumers is the other move: start several identical copies of the worker on the same queue, and let the queue hand each job to whichever copy is free. When the line grows you start one more; when it shrinks you stop one.

Several identical, stateless consumer instances read one channel — a queue, a topic partition, a work stream — and the broker hands each message to whichever member is free. The consumers never coordinate and do not know how many siblings they have; they pull, process, and ack. Delivery is exclusive at a moment, not forever: the broker leases a message to one member at a time, and a lease that expires unacked puts the message back for a sibling, which makes delivery at-least-once.

What that buys is a change of unit. "Add capacity" becomes "add a consumer instance" — a deployment decision rather than a code change, because the consumers are interchangeable and hold no state between messages. Scaling back down is just as cheap.

It is a lens rather than one fixed mechanism: the same idea shows up as JMS queue listeners, Kafka consumer groups, RabbitMQ consumers on a shared queue, and SQS workers polling one queue. What they share is one channel, many pullers, and one-consumer-at-a-time delivery to the group.

Explained at three levels

Basic

There are two ways to make work go faster: do each item quicker, or do more items at the same time. The first one runs out — a program that takes two seconds per job is not going to take one, however hard you try, and meanwhile jobs keep arriving at four a second. The second one barely has a limit, provided the jobs do not depend on each other. So instead of one worker reading the queue, run several identical copies of it against that same queue and let the queue hand each job to whichever copy is free. Nobody assigns work and no copy knows how many others exist: each takes the next job, finishes it, comes back. It is one airport queue feeding whichever desk opens up, so busy morning means open another desk. The catch is that a copy can die halfway through a job, and the queue will then give that job to somebody else — so the same job is sometimes done twice, and your work has to be safe to repeat.

Advanced

Several identical stateless consumers read one channel, and the broker leases each message to exactly one of them at a time; an unacked lease expires and the message reappears for a sibling, so delivery is at-least-once and every handler owes idempotency. Capacity becomes replica count rather than code. The variants differ in how the group is formed. A flat pool takes whatever is next and gives up ordering entirely. Keyed or partitioned consumption hashes each message to a partition owned by one consumer at a time, which preserves per-key order and caps parallelism at the partition count. Layer a pool under a topic and each subscriber group still receives every message once while members inside a group compete for it — fan-out across groups, load-sharing within one. A broker is not even required: worker replicas can claim rows from a task table with a skip-locked read, where the row lock is the lease.

Expert

Choose it when work items are independent and arrivals outrun one process: throughput becomes a deployment dial, and any consumer can die mid-message with no special handling. The bill is ordering and exactly-once, both surrendered, and each line has a counter-move. Relatedness has to be re-expressed as a partition key, and that key caps parallelism at the partition count — pick the count for the throughput you expect to need, because raising it later re-scatters existing keys across partitions. Redelivery after a lease expiry means duplicate work, so buy safety with idempotent handlers keyed on a message id instead of trying to buy exactly-once from a broker that cannot sell it. A message that fails every attempt burns pool capacity indefinitely, so cap attempts and divert it to a dead-letter channel with an alert on depth. And a pool only fixes the consumer side: when the producer's bursts are the real problem, put a load-leveling queue in front rather than running a pool sized for the peak all day. Then run the loop — tune consumer count, prefetch and lease, watch queue depth against drain rate and the spread of work across instances, expect a lease shorter than p99 processing to double work first, and gate the release on idempotent handlers and a dead-letter path.

How it works

Variations

Static pool
A fixed number of consumer instances, sized for expected peak load. Simple to operate, wasteful when load is bursty.
Partitioned / keyed consumption
Messages are hashed to a partition or shard by key, and each partition is owned by exactly one consumer at a time — preserves per-key order while still spreading unrelated keys across the pool (Kafka partitions, Kinesis shards).
Publish-Subscribe
Layer competing consumers under pub/sub: each subscriber group receives every message once, but the consumers inside a group compete for it — fan-out across groups, load-sharing within one.
Exclusive delivery via lease / visibility timeout
The broker hides a delivered message from other consumers for a lease window; a consumer that crashes before acking lets it reappear for someone else to pick up.

Trade-offs

Pros

  • Scales throughput horizontally by adding consumer instances, with no producer changes.
  • Consumers are stateless and interchangeable — any one can crash and restart without special handling.
  • The channel itself absorbs load spikes as a buffer while the pool catches up.
  • Failed processing just means the message goes back for another consumer to try.

Cons

  • No ordering guarantee across the pool — two related messages can be processed out of sequence by different consumers.
  • Most brokers give at-least-once delivery, so a redelivered message must be handled safely, not processed twice — that is what idempotency is for.
  • A poison message that always fails can bounce between consumers, burning capacity, until an attempt cap sends it to a dead-letter channel.
  • Uneven message cost means one consumer can be starved while another sits idle.
  • Restoring order costs parallelism: a partition key keeps related messages in sequence, and the partition count then becomes the ceiling on how many consumers can work at once.
  • A pool only widens the consumer side. If the producer's bursts are what hurts, a leveling queue in front is cheaper than a pool sized for the peak all day.

When to use it

Reach for it when

  • A single consumer can't keep up with the rate messages arrive on a channel.
  • The work is naturally parallel — messages don't depend on each other's outcome.
  • You want to scale processing capacity by deployment, without touching the producer.

Avoid when

  • Messages must be processed in strict global order — a single consumer, or per-key partitioning, fits better.
  • Every consumer needs to see every message — that's fan-out, not sharing; reach for Publish-Subscribe instead.
  • Processing isn't safely repeatable — redelivery under at-least-once delivery will corrupt state.

Code sketch

TypeScript — the whole idea: identical workers, one queue 
async function worker(queue: Queue) {
  while (true) {
    const job = await queue.receive();   // the queue picks one free worker
    if (!job) continue;                  // nothing waiting, ask again
    try {
      await handle(job);
      await queue.ack(job);              // done — it leaves the queue
    } catch {
      await queue.nack(job);             // put it back for a sibling to retry
    }
  }
}

// Capacity is the number of copies you start. Nothing here knows about the others.
for (let i = 0; i < workerCount; i++) worker(jobQueue);

interface TaskQueue {
  claim(leaseMs: number): Promise<Task | null>;
  complete(id: string): Promise<void>;
  release(id: string): Promise<void>; // returns the task for another consumer
}

const claimSql = `
  UPDATE task SET status = 'processing', locked_at = now(), attempts = attempts + 1
  WHERE id = (
    SELECT id FROM task
    WHERE status = 'pending' AND run_after <= now()
    ORDER BY run_after
    FOR UPDATE SKIP LOCKED       -- the whole pattern: a locked row is invisible
    LIMIT 1)
  RETURNING id, flow_id, type`;

async function runConsumer(queue: TaskQueue, handle: (t: Task) => Promise<void>) {
  while (true) {
    const task = await queue.claim(30_000); // leased to this replica for 30s
    if (!task) continue;                    // nothing waiting, poll again
    try {
      await handle(task);
      await queue.complete(task.id);        // done — leaves the queue
    } catch {
      await queue.release(task.id);         // let a sibling retry it
    }
  }
}

In the wild

Kafka consumer groupsPartitions are divided among the consumers in a group so exactly one member reads each partition; a rebalance reassigns partitions when a member joins or leaves. The partition count is the hard ceiling on parallelism — consumers beyond it sit idle with nothing assigned.
CeleryPython workers compete for tasks on a shared RabbitMQ or Redis broker, scaling by adding worker processes or raising --concurrency. worker_prefetch_multiplier controls how many tasks each worker reserves ahead of time, the knob that trades throughput against even distribution.
SidekiqRuby workers compete for jobs on shared Redis queues, each process running a pool of threads (concurrency) that pull with BRPOP. Because plain BRPOP removes the job before it is done, an in-flight job is lost if the process is killed; reliable fetch that re-queues interrupted jobs is a Pro/Enterprise feature.
Amazon SQSMany workers poll one queue and each message is handled once: a visibility timeout hides an in-flight message from sibling workers while it is processed, a Lambda event source mapping polls the queue and invokes functions in batches, and a redrive policy moves a message to a dead-letter queue after maxReceiveCount failed attempts.

In production

Tuning knobs

  • Consumer count / concurrency — The number of consumer instances or threads pulling from the channel — the primary throughput dial, changed by deployment rather than by code.
  • Prefetch / batch size — How many unacked messages one consumer holds at a time (RabbitMQ basic.qos prefetch_count, Kafka max.poll.records), trading per-consumer throughput against how evenly work spreads.
  • Visibility timeout / lease — How long a delivered message is hidden from the rest of the pool before it reappears (SQS VisibilityTimeout). Kafka's dial is different in kind: max.poll.interval.ms is a poll deadline whose breach costs the consumer its whole partition assignment, not one message.
  • Max delivery attempts — The redelivery count after which a message is diverted to a dead-letter path (SQS maxReceiveCount).
  • Partition / shard count — In a keyed model, the number of partitions — it fixes the ceiling on how many consumers in a group can work in parallel (Kafka partitions, Kinesis shards).

Signals to watch

  • Queue depth / consumer lag — Backlog waiting versus drain rate (Kafka consumer-group lag, SQS ApproximateNumberOfMessages) — the headline signal of whether the pool is keeping up.
  • Per-consumer throughput spread — Distribution of completed work across instances; a wide spread means the sharing is not working, whatever the total says.
  • In-flight / unacked count — Messages leased but not yet acked — a number that is high and stuck points at slow handlers or leaked leases.
  • Redelivery rate — How often messages come back after a nack or a lease expiry — a proxy for handler failures and for duplicate work.
  • Dead-letter depth and arrival rate — Messages that exhausted their attempts; every one is work that silently did not happen.

Failure modes under load

  • Lease shorter than processing — A visibility timeout below real processing time redelivers the message while the first consumer is still working on it, so two consumers do the same work and both may write.
  • Prefetch starvation — A prefetch set too high lets one consumer pull the whole backlog into its buffer while its siblings sit idle, so adding instances stops adding throughput.
  • Idle consumers past partition count — In a keyed model, consumers beyond the partition count get no partition assigned and sit idle no matter how deep the backlog is.
  • Poison message churn — A message that always fails bounces through the pool, consuming a slot on every pass, until an attempt cap dead-letters it.
  • Rebalance stalls — A member joining, leaving or missing its poll deadline triggers a reassignment, and consumption on the affected partitions pauses until it settles — frequent restarts turn this into steady-state lost throughput.

Readiness checklist

  • Handlers are idempotent, and that was tested by replaying the same message rather than assumed
  • The lease was set from an observed p99 processing time under load, not from a default
  • Work distribution across the pool was watched with a full backlog, not only with an empty one
  • A dead-letter path exists with an attempt cap, and its depth is alerted on
  • In a keyed model, the partition count is at least the consumer count you plan to run
  • Consumers shut down by finishing or releasing the message in hand, so a deploy does not manufacture redeliveries
