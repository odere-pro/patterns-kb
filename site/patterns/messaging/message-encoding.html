Messaging

Message Encoding

Fixes the wire contract between a producer and consumers it never meets: the format the payload is written in, the schema that says what the fields mean, and the compatibility rules that decide which changes are safe to deploy. Get the rules right and either side can be released alone; get them wrong and every schema change is a coordinated outage.

Messaging

What it is

Message encoding is the agreement about how a message is written down. A producer serialises a structure into bytes and a consumer turns those bytes back into a structure, and the two are never deployed together — so the encoding, the schema describing it, and the rules for changing that schema are the contract between them. It is separate from the transport: a queue moves bytes and does not care what they mean.

Three decisions sit inside it. The format trades human readability against size and decode speed — a text format anyone can inspect with a terminal, or a binary one that halves the payload and parses several times faster. The schema is where the field names, types and optionality live; keeping it in a registry rather than inside each service gives both sides one definition to compile against instead of two that drift. And the compatibility rule decides which changes may ship: backward compatibility lets a new consumer read old messages, forward compatibility lets an old consumer read new ones, and full compatibility is both — which is what you actually need when producers and consumers deploy independently and a queue holds messages written days ago.

The rules follow from the encoding, and they are stricter than they look. Adding a field is safe only if it has a default, because an old message simply will not carry it. Removing a field is safe only if it was optional, because an old consumer still expects it. Renaming is never safe — it is a remove and an add wearing one commit. In a positional binary encoding the field's tag number is its identity, so a number may never be reused after retirement even though the name is free again. Enforce all of that in the pipeline rather than in review: a registry that rejects an incompatible schema at build time is the difference between a failed build and a poison message that stops a partition at three in the morning. Then carry the schema identity in the message — a version or a registry id in the envelope — so a consumer knows how to read a payload before it tries.

Explained at three levels

Basic

One service writes a message and another reads it, and they are updated by different people at different times. Rename a field on the writing side and the reading side stops finding it — but nothing warns you, because the queue happily carries whatever bytes it is given. So write down the shape both sides agree on, keep that description in one place both of them use, and only make changes an old reader can survive: add fields, do not rename or remove them.

Advanced

Choose the format for what the traffic actually costs: a text format is inspectable and needs no tooling, a binary one is substantially smaller and faster to decode, which starts to matter at volume. Keep the schema in a shared registry so both sides compile against one definition rather than two that drift apart. Then pick the compatibility mode the deployment reality demands — with independent releases and a queue holding older messages, that is full compatibility: an old consumer must survive a new message, and a new consumer must survive an old one. Stamp the schema version into the envelope so a consumer knows which definition to read a payload with, and never make it guess.

Expert

Treat the schema as an API, because it is one, and enforce its rules mechanically. Register the schema in the build, fail the build on an incompatible change, and the class of incident where one deploy poisons a topic disappears — a code review will not catch a reused tag number, and a running consumer will not survive one. Then price the format honestly rather than by preference: binary encoding buys throughput and cheaper egress on a hot topic, and costs you the ability to read a message with an ordinary terminal, which is worth real money during an incident. A common resolution is to split by traffic class — text for low-volume control and integration events where debuggability wins, binary for the high-volume streams where bytes and CPU dominate — accepting two toolchains as the price. Keep the envelope separate from the payload: identity, correlation, timestamps and schema version live in headers a router or a dead-letter handler can read without deserialising a body it may not understand. And when a payload is genuinely large, encode a reference rather than the bytes, so the broker keeps carrying small messages.

How it works

Variations

Self-describing text encoding
Each message carries its own field names, so anything can read it without a schema in hand and a human can inspect it with a terminal. That makes it the right default for low-volume integration events, where debuggability beats bytes. You pay for it on every message — the names are repeated in every copy, parsing is slower, and with no schema anywhere the contract lives only in whatever documentation people remember to update.
Schema-first binary encoding
Fields are identified by number rather than by name, so payloads are markedly smaller and decode substantially faster, and both sides generate code from one definition. It is what high-volume streams want. The definition must reach every consumer, a message is opaque without it, and tag numbers become permanent identity — retire a field and its number is retired with it.
Registry-resolved schema
The message carries a small schema id and the consumer resolves the full definition from a registry, caching it. Payloads stay compact while every message remains exactly readable, and the registry can refuse an incompatible change before it is ever published. The registry is now on the critical path for a cold consumer, so it needs its own availability story and a local cache that survives it being down.
Envelope and payload separated
Identity, correlation id, timestamp, content type and schema version live in headers, distinct from the encoded body. A router, a filter or a dead-letter handler can then act on a message without deserialising a body it may not be able to read. It is two things to keep consistent, and metadata put in the envelope that belongs in the payload tends to end up duplicated in both.
Reference instead of payload
When the content is genuinely large, the message encodes a pointer to it and the bytes go to object storage — the claim check. The broker keeps carrying small messages, so throughput and retention stay predictable no matter how big the content gets. The reference has a lifetime, and a consumer that reads it after the object expires fails in a way no schema check will catch.

Trade-offs

Pros

  • Producers and consumers can be released independently, because the compatibility rule says in advance which changes are safe.
  • The contract stops living in documentation and becomes a definition both sides compile against.
  • A registry catches an incompatible change at build time, turning a production poison message into a failed pipeline.
  • A binary format cuts payload size and decode cost, which shows up directly in broker storage, egress and consumer CPU.
  • Metadata in the envelope lets routing, filtering and dead-lettering work without deserialising the body.

Cons

  • A binary payload cannot be read without its schema, so inspecting a message during an incident needs tooling you must have already built.
  • The schema becomes a shared artifact with its own repository, release process and ownership question.
  • Renaming a field is never a safe change, so early naming mistakes are effectively permanent.
  • A registry on the critical path is another dependency a cold consumer needs before it can read anything.
  • Retired tag numbers stay retired forever, and reusing one produces a decode failure that looks like data corruption.
  • Compatibility rules bound what the schema can express, so the model drifts toward what is safe to change rather than what is accurate.

When to use it

Reach for it when

  • Producer and consumer are deployed separately, by different people, on different schedules.
  • A queue or log holds messages long enough that a consumer will read something written before its own release.
  • Volume is high enough that payload size and decode cost are visible in the bill or the latency.
  • Consumers are written in several languages and need generated types rather than hand-written parsers.

Avoid when

  • Both sides ship in one deployment, where a shared type already is the contract.
  • The volume is tiny and the shape is stable, where a registry costs more to run than the drift it prevents.
  • The schema is still changing shape daily, where freezing compatibility rules over a draft blocks the exploration.

Code sketch

Schema evolution — which changes are safe, and why the tag number is the identity 
// v1 — the shape both sides were built against.
message OrderPlaced {
  string order_id = 1;
  string sku      = 2;
  int32  quantity = 3;
}

// v2 — SAFE. A new field at a new number: an old consumer never looks at tag 4
// and ignores it; a new consumer reading a v1 message gets the default.
message OrderPlaced {
  string order_id = 1;
  string sku      = 2;
  int32  quantity = 3;
  string currency = 4;          // added, optional, defaults cleanly
  reserved 9;                   // retired earlier — the NUMBER can never return
  reserved "discount_code";     // and neither can the name
}

// v3 — UNSAFE, and it compiles. `sku` was renamed and its number handed to a new
// field of a different type. An old consumer still reads tag 2 as a string and
// gets bytes that are not one, so the decode fails — and it fails for every
// message on the partition, not just this one.
message OrderPlaced {
  string order_id     = 1;
  int64  product_ref  = 2;      // WRONG: tag 2 already means "sku", as a string
  int32  quantity     = 3;
}
TypeScript — publish with the schema id in the envelope, and refuse to guess on read 
// Register on the way out. An incompatible schema is rejected HERE, at build or
// first publish — which is the whole point. Catching it in review does not scale.
const schemaId = await registry.register("order-placed-value", ORDER_PLACED_SCHEMA, {
  compatibility: "FULL",   // old consumer reads new message AND new reads old
});

await producer.send({
  topic: "orders",
  // The envelope is readable without decoding the body, so a router or a
  // dead-letter handler can act on a message it cannot itself parse.
  headers: { "schema-id": String(schemaId), "content-type": "application/x-protobuf",
             "correlation-id": correlationId },
  value: encode(ORDER_PLACED_SCHEMA, event),
});

// On the way in, resolve the schema the message was WRITTEN with — never assume
// it matches the one this service was compiled against.
async function handle(msg: Message) {
  const id = msg.headers["schema-id"];
  if (!id) throw new PoisonMessage("no schema id");   // dead-letter, do not guess

  const writerSchema = await registry.get(Number(id));   // cached; survives a registry outage
  const event = decode(writerSchema, READER_SCHEMA, msg.value);
  await process(event);
}

In the wild

Protocol BuffersFields are identified by tag number, not by name, so payloads are compact and the number is the identity — the language provides reserved precisely so a retired tag or name can never be reused by accident.
Apache AvroA message is decoded with both the schema it was written with and the schema the reader expects, and the resolution rules between them are part of the specification. That is why it is the common choice for long-lived event logs where old messages must stay readable.
Schema registriesConfluent Schema Registry and comparable services store schemas by subject, hand out an id the message carries, and enforce a configured compatibility mode — so an incompatible schema is rejected at registration rather than discovered by a stalled consumer.
CloudEventsA CNCF specification for the envelope rather than the payload: it standardises the metadata around an event — id, source, type, time, datacontenttype — so routing and dead-lettering work without decoding the body.

In production

Tuning knobs

  • Compatibility mode — Backward, forward, or full. Independent deploys plus a queue that retains messages means full — anything weaker is a rule that will be broken by a deployment order nobody controls.
  • Format choice per topic — Text or binary, decided per traffic class rather than once for the estate. High-volume streams pay for readability on every message; low-volume integration events pay for tooling on every incident.
  • Schema cache lifetime in the consumer — How long a resolved schema is kept locally. It is what decides whether a registry outage stops new consumers only, or everything.
  • Envelope contents — Which fields live in headers rather than the body — schema id, content type, correlation id, timestamp. Anything a router or a dead-letter handler needs must be readable without decoding the payload.
  • Maximum message size — The point past which a payload becomes a reference instead. Set it below the broker limit, so the switch is a design decision rather than a rejected publish.

Signals to watch

  • Deserialisation failure rate — Messages that could not be decoded. It is normally exactly zero, so any non-zero value is a schema incident rather than noise.
  • Dead-letter arrivals by schema id — Which schema version the undecodable messages were written with. It names the offending deploy immediately.
  • Average payload size by topic — Bytes per message over time. A step change usually means a field carrying something that should have been a reference.
  • Registry lookup latency and error rate — How the schema resolution path is behaving. A cold consumer cannot start without it, so it belongs on the same dashboard as the broker.
  • Count of live schema versions per subject — How many definitions are actually in flight. It bounds what a consumer must be able to read.

Failure modes under load

  • Poison message stops a partition — One undecodable message at the head of an ordered partition blocks every message behind it. Throughput on that partition goes to zero while the rest of the topic looks healthy.
  • Incompatible schema deployed — A rename or a reused tag number ships, and every consumer on the old definition fails at once. Rolling the producer back does not help the messages already written.
  • Registry unavailable to a cold consumer — A consumer restarts with an empty cache and cannot resolve any schema, so it cannot read anything at all until the registry returns.
  • Payload growth crosses the broker limit — A field that grew quietly pushes messages past the maximum size, and publishes start failing for records that used to be fine.
  • Retired tag number reused — A number freed by a removed field is assigned to a new field of a different type, and old consumers read the new bytes as the old type — a decode failure that reads like corruption.

Readiness checklist

  • The schema lives in one place both sides build against, not in two hand-written copies
  • Every message carries its schema identity in the envelope
  • An incompatible schema change fails the build, not a consumer
  • Compatibility mode matches the deployment reality — full where releases are independent
  • Undecodable messages go to a dead-letter destination instead of blocking the partition
  • Consumers cache resolved schemas so a registry outage does not stop running work
  • Retired field names and numbers are reserved so they can never be reused
  • There is a documented way to inspect a binary payload during an incident
