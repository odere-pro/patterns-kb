Network · Resilience

Token Bucket

Meters work against a bucket of tokens that refills at a steady rate — letting callers burst up to the bucket's size, then pacing everything to the refill rate.

Distributed Resilience

What it is

A token bucket is a rate-limiting algorithm. Picture a bucket that holds up to C tokens and is topped up at a steady rate of r tokens per second, never past its capacity. Every request must take one token before it may proceed; if the bucket is empty, the request is refused (or made to wait). Because the bucket can be full, a caller who has been quiet may spend a whole bucketful at once — but once it drains, they are paced to the refill rate.

The force it resolves is bursty traffic against a finite budget. You want to protect a service from being swamped, and to share it fairly among callers, without punishing the normal, spiky shape of real traffic. A naïve fixed-window counter is unfair at the edges — it can let 2× the intended rate through across a window boundary — while a strict constant-rate limiter rejects legitimate bursts. The token bucket separates two concerns cleanly: capacity governs how big a burst you tolerate, and refill rate governs the long-run average.

Its cousin, the leaky bucket, drains queued work at a constant rate and so smooths output completely; the token bucket instead permits bursts up to its size. The same two-dial idea — a burst allowance plus a steady rate — is why it is the algorithm most API rate limiters actually run.

Explained at three levels

Basic

Demand comes in bumps. A cap that resets on the clock either turns away honest surges or lets twice as much through at the reset. Instead, let someone who has been quiet build up credit to a ceiling and spend it as they like. Holiday days work that way: they build up steadily, they stop at the ceiling, and a saved fortnight goes at once — then back to the trickle.

Advanced

Two dials: capacity C, the largest burst tolerated, and refill rate r, the long-run average. The whole state is two fields per bucket: a token count and a last-refill timestamp. On each arrival the count is topped up lazily by elapsed time times r, clamped to C, and the request spends a token or, on an empty bucket, is refused or made to wait. O(1), no timer thread. It is the mechanism inside most API rate limiters, and it stacks: a per-caller bucket under a global one, every request paying at each level.

Expert

Choose it when burst and average must be governed independently: a fixed-window counter is unfair at its seam, a leaky bucket used as a queue paces the output and refuses legitimate spikes outright. The payoff is a burst allowance you can widen without raising the sustained rate. The bill sits in the same two numbers: a generous capacity admits a burst that flattens a fragile downstream while the average stays inside budget. Enforcing one bucket across a fleet turns every check into an atomic check-and-decrement on a single key — the busiest key you own. And the refill is computed from a timestamp, so a coarse or non-monotonic clock hands out too many tokens or too few whatever the dials say.

How it works

Variations

Token bucket vs. leaky bucket
Both bound a rate, and which leaky bucket you mean decides the rest. Used as a queue, the leaky bucket holds arrivals and drains them at a strictly constant rate, so nothing bursty ever leaves it. Used as a meter it queues nothing and only marks each arrival as conforming or not — given the same parameters it admits exactly the traffic a token bucket would, because the smoothing comes from queueing the work, not from the accounting. Reach for the queue form when you need perfectly smooth output; for the token bucket when a burst is acceptable and desirable.
Lazy (on-demand) refill
Instead of a background timer dripping tokens in, store a lastRefill timestamp and, on each request, add elapsed × rate tokens (capped at capacity). No thread, no scheduler — the standard implementation.
Distributed / shared bucket
Keep the token count in a shared store so a whole cluster enforces one global rate rather than one rate per replica. Correctness then rests on an atomic check-and-decrement (for example a Redis Lua script).
Weighted / cost-based tokens
Let an expensive request cost more than one token — by payload size, query complexity, or price tier — so the limit tracks real work rather than raw request count.
Hierarchical buckets
Layer buckets: a per-user bucket plus a global bucket, and a request must draw a token from every level it passes through. This bounds any single caller and the aggregate at once.

Trade-offs

Pros

  • Allows bursts up to capacity while bounding the long-run average rate — two independent dials.
  • Cheap and O(1): each bucket is just a token count plus a last-refill timestamp.
  • Lazy refill needs no background timer or scheduler thread.
  • Fairer than a fixed-window counter, which lets a double burst slip across the window boundary.

Cons

  • Per-instance buckets don't share state; N replicas allow up to N× the intended global rate.
  • A global limit needs an atomic shared store, adding a dependency and per-call latency.
  • A large capacity still lets a big burst through that can overwhelm a fragile downstream.
  • Choosing capacity and rate is real tuning; wrong values throttle honest traffic or leak too much.

When to use it

Reach for it when

  • You must cap the average request rate but want to tolerate short, natural bursts.
  • You're building an API limiter keyed per user, per API key, per tenant, or per IP.
  • You want to shape offered load to a downstream's real capacity.
  • A fixed-window counter is too coarse or unfair at its window edges.

Avoid when

  • You need a strictly constant output rate with no bursts — a queue or leaky bucket fits better.
  • A single-node process with no contention needs no rate governance at all.
  • The limit must be exact and global but you cannot afford an atomic shared store — rethink the requirement.
  • You actually want to buffer excess work rather than shed it.

Guards against the overload that turns one traffic spike into a system-wide brownout, where a struggling service degrades every caller behind it.

Code sketch

TypeScript — a token bucket with lazy refill 
class TokenBucket {
  private tokens: number;
  private lastRefill = Date.now();

  constructor(
    private readonly capacity: number,     // burst size — the most you may spend at once
    private readonly refillPerSec: number, // steady-state rate
  ) {
    this.tokens = capacity;                 // start full
  }

  /** True if the request is allowed, false if it should be rate-limited. */
  tryConsume(cost = 1): boolean {
    this.refill();
    if (this.tokens < cost) return false;  // bucket empty → shed the request
    this.tokens -= cost;
    return true;
  }

  private refill(): void {
    const now = Date.now();
    const elapsedSec = (now - this.lastRefill) / 1000;
    if (elapsedSec <= 0) return;
    // lazy refill: no timer — derive accrued tokens from elapsed time
    this.tokens = Math.min(this.capacity, this.tokens + elapsedSec * this.refillPerSec);
    this.lastRefill = now;
  }
}

// 10 requests/second sustained, bursts up to 20
const bucket = new TokenBucket(20, 10);
if (!bucket.tryConsume()) throw new Error("429 Too Many Requests");

In the wild

EnvoyIts local rate-limit filter is configured with a literal token_bucket block — max_tokens (capacity), tokens_per_fill, and fill_interval — spending a token per matching request.
Go golang.org/x/time/rateThe standard rate.Limiter is a token bucket: NewLimiter(r, b) sets the refill rate r and burst size b, exposed through Allow, Wait, and Reserve.
Guava RateLimiterHands out permits at a fixed rate and lets unused permits accumulate up to a small burst (SmoothBursty) — token-bucket behaviour under the hood.
AWS API GatewayRequest throttling uses the token bucket algorithm, with a steady-state rateLimit (refill) and a burstLimit (bucket capacity) per stage or route.

In production

Tuning knobs

  • Bucket capacity (burst size) — The maximum number of tokens, and so the largest instantaneous burst you permit (max_tokens, burstLimit, the burst b).
  • Refill rate — Tokens added per unit time; this is the enforced steady-state average rate (tokens_per_fill / fill_interval, rateLimit, the rate r).
  • Token cost per request — Whether every request costs one token or expensive ones cost more, weighting the limit by real work rather than raw count.
  • Bucket key granularity — Whether buckets are keyed per IP, per API key, per tenant, or global — this sets how many buckets exist and what each one caps.
  • On-empty behaviour — Reject immediately (shed load, e.g. HTTP 429) or block and wait for a token (throttle) when the bucket is empty.

Signals to watch

  • Throttle / rejection rate — The fraction of requests denied for lack of a token (e.g. the 429 count) — a limit that is biting hard.
  • Available tokens / fill level — How full buckets are; buckets that sit persistently empty mean the configured rate is below offered load.
  • Offered rate vs. configured rate — Incoming request rate measured against the refill rate, to see how close callers run to the cap.
  • Token-store latency and errors — For a shared bucket, the added latency per check and the error rate of the atomic store.

Failure modes under load

  • Per-instance divergence — Replicas each holding a local bucket collectively admit up to N× the intended global rate.
  • Shared-store hot key — A single key backing a global bucket becomes a contention and latency hotspot at high request volume.
  • Oversized burst — A capacity set too high lets a burst through that overwhelms a fragile downstream even though the average is within budget.
  • Clock skew on lazy refill — A coarse or non-monotonic clock distorts the elapsed-time calculation, leaking too many or too few tokens.

Readiness checklist

  • Decide global vs. per-instance; if global, hold bucket state in an atomic shared store (e.g. a Redis check-and-decrement script).
  • Set capacity and refill rate from the downstream's measured capacity, not from a guess.
  • Return 429 with a Retry-After (or equivalent) so clients back off instead of retrying instantly.
  • Emit throttle-rate and rejection metrics with alerts on sustained shedding.
  • Choose the bucket key deliberately and bound the number of buckets so memory stays finite.
