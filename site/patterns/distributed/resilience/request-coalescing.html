Request Coalescing

When several callers ask for the same thing at the same time, only the first is allowed to do the work — the rest wait on the answer it is already fetching, so N simultaneous requests cost the backend exactly one.

Distributed

What it is

A popular cache entry expires. In the next forty milliseconds eight hundred requests arrive wanting it, every one of them misses, and every one asks the database for the same row. Seven hundred and ninety-nine of those queries are waste — they compute an answer another query is already computing. Request coalescing puts one gate in front of the work: the first caller to arrive starts the fetch and registers it under the key it is fetching, and everyone who arrives while that fetch is running waits on its result instead of starting their own. One backend call is made, and all eight hundred callers are served from it.

The mechanism is a map from key to in-flight promise, guarded so that check-and-insert is one atomic step. On arrival a caller looks the key up: a hit means subscribe to the existing call, a miss means store your own promise first and then do the work. The entry is removed when the call settles — on failure as well as on success, or the next caller inherits a rejection that has nothing to do with its own attempt.

The force it resolves is that caching and concurrency are usually designed as though they were independent, and they are not. A cache turns repeated reads into one read over time; it does nothing about repeated reads at the same instant, because none of them has finished writing the entry yet. That gap is where a cache stampede lives, and adding cache capacity never closes it. Coalescing closes it by making duplicate concurrent work impossible rather than merely unlikely.

Explained at three levels

Basic

A hundred people walk up to a counter within a second, all asking the same question. You can send a hundred runners to fetch a hundred copies of one answer, or send one runner and have everybody wait for them to come back. Sending one runner is the whole idea: the first person to ask starts the errand, and everyone who asks while it is running gets handed the same answer when it arrives.

Advanced

The runner is a shared in-flight promise in a concurrent map keyed by the request, and the correctness of the pattern rests entirely on making check-and-insert atomic — two callers that both look, both miss, and both start work have reproduced the problem the pattern exists to solve. A per-key lock or an atomic compute-if-absent gives you that guarantee. Scope matters as much as the mechanism: an in-process map deduplicates within one instance, so a fleet of fifty still sends up to fifty calls, and cutting that further means moving the gate to a shared store or moving the fill behind a read-through cache that owns the miss path for everyone.

Expert

Reach for it when duplicate concurrent work is expensive and the answer is genuinely shareable; skip it when requests only look identical, because coalescing on a key that omits the tenant or the caller's permissions serves one user another user's data. The bill has three lines and each has a counter-move. Shared fate — one slow or failed fetch is now every waiter's — is paid with a timeout on the shared call and a bound on how many may wait, so a hung leader fails fast for everyone rather than hanging everyone. Head-of-line latency, where a caller arriving at the last millisecond waits out the whole fetch, is paid by serving stale on arrival and coalescing the refresh behind it. And deduplication is only as wide as the map, so on a large fleet measure the residual concurrency you actually get before assuming the origin sees one call rather than one per instance.

How it works

The subgraph is what carries the guarantee. If looking the key up and inserting your own promise are two separate steps, two callers can both pass the lookup before either inserts, the origin sees two calls, and the pattern degrades to no pattern at all under exactly the load it was added for.

Variations

In-process single-flight
One map per instance and no coordination. It costs nothing to operate and removes duplicate work inside a process, but a fleet of N instances still sends up to N concurrent calls to the origin. This is the default, and it is usually enough.
Cross-process coalescing
The gate moves to a shared store: whoever wins a short-lived lock does the fetch and publishes the result, and the losers poll or subscribe for it. Origin concurrency falls to one across the whole fleet, at the price of a network round-trip on the happy path and a lock whose holder can die mid-fetch.
Serve-stale-and-refresh
Waiters are handed the expired value immediately while exactly one refresh runs behind them. Nobody blocks, so head-of-line latency disappears, and the cost is that callers knowingly read data that is a little out of date.
Windowed batching of adjacent keys
A short window collects different keys and issues one multi-get instead of collapsing identical ones. That is batching rather than coalescing — it trades a small fixed latency for far fewer round-trips — and the two compose: collapse the duplicates, then batch what remains.

Trade-offs

Pros

  • Bounds origin concurrency per key at one, so a burst of identical misses costs a single backend call rather than hundreds.
  • Needs no coordination in its common form — a map and a lock inside one process, with nothing extra to deploy or operate.
  • Protects the origin without asking callers to behave, so it still holds when a new client ships without the retry discipline everyone assumed.

Cons

  • Waiters share the leader's fate: one slow or failed fetch becomes slow or failed for everyone attached to it.
  • A caller arriving late waits out the whole in-flight fetch, so its latency is worse than an uncoalesced call would have been.
  • The key is a correctness boundary. Omit the tenant, the locale or the permission scope and one caller is served another's data.
  • Deduplication is only as wide as the map, so on a large fleet the origin still sees roughly one call per instance unless the gate is shared.

When to use it

Reach for it when

  • Many callers want the same expensive thing at the same moment — a hot key expiring, a cold start, a cache flush.
  • The origin is the scarce resource and duplicate work is what exhausts it, rather than genuine distinct demand.
  • The answer is shareable between those callers without a further authorization check.

Avoid when

  • The requests are not truly identical — anything varying by caller, tenant or permission must not share one result.
  • The work has side effects. Collapsing two writes into one silently drops the second, which is a correctness bug rather than an optimization.
  • Every caller needs its own freshest read, as in a compare-and-set loop that must observe the newest value.

Code sketch

TypeScript — a single-flight gate over any async loader 
/* One entry per key while a fetch is running. In a single-threaded runtime the
 * get-then-set below cannot interleave, which is what makes it atomic here; the
 * same two lines in a threaded language need a per-key lock or computeIfAbsent. */
export function coalesce<T>(load: (key: string) => Promise<T>) {
  const inFlight = new Map<string, Promise<T>>();

  return function get(key: string): Promise<T> {
    const existing = inFlight.get(key);
    if (existing) return existing;           // someone is already fetching this

    const call = load(key).finally(() => {
      // Release on rejection too, or the next caller waits on a dead promise.
      inFlight.delete(key);
    });

    inFlight.set(key, call);
    return call;
  };
}

// 800 concurrent misses on one key produce exactly one loadUser call.
const getUser = coalesce(loadUser);
await Promise.all(Array.from({ length: 800 }, () => getUser("u-42")));
