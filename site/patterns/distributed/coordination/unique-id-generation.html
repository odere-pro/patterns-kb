Unique ID Generation

Builds an identifier out of a clock reading, a per-generator identity and a counter, so any node can mint a key that nothing else will ever produce — and, because the clock sits in the high bits, keys still arrive at the index in roughly the order they were created.

Distributed

What it is

Every scheme for minting identifiers across many machines mixes the same three ingredients in different proportions: a clock reading, a generator identity, and a counter or some random bits. The identity keeps two machines apart, the counter keeps one machine's own output apart within a single tick, and the clock puts the whole thing in order.

The force it resolves is a direct conflict between uniqueness and ordering. Uniqueness without coordination is easy if you use enough randomness — and randomness destroys ordering, which turns out to cost real money at the storage layer. Put the clock in the most significant bits and the two stop fighting: ids from any node compare by time first, so they sort roughly by creation and land at the tail of an index instead of scattering through it.

That is the whole reason to care. A random key sends every insert to a different leaf page, which forces page splits, inflates write-ahead log volume, evicts useful pages from the buffer cache and gives compaction more to do — reported as multiples slower than sequential inserts once write volume is high. A time-ordered key keeps inserts in one hot page that stays cached and fills densely. The same property that makes the key cheap to index also makes it a rough timestamp, which is sometimes convenient and sometimes a leak.

Two bit layouts dominate. The compact form is 64 bits: one sign bit fixed at zero, 41 bits of milliseconds since a chosen epoch, 10 bits of node id, and 12 bits of sequence — which is 1,024 generators, 4,096 ids per generator per millisecond, and about 69 years before the timestamp field runs out. The 128-bit standard form is specified in RFC 9562 as version 7: 48 bits of Unix milliseconds, a version marker, 12 bits of sub-millisecond sequence, a variant marker, then 62 random bits — no node-id assignment to administer, at twice the storage and index width.

Explained at three levels

Basic

The database used to hand out the next number, so ids were small, in order, and never repeated. Then there were several databases and several services minting rows, and asking one counter for every id made it the slowest thing on the write path. Switching to a big random number fixes the collisions and quietly makes inserts slower, because rows now arrive at the index in no order at all. Build the id instead: the time, who made it, and a counter — unique because of who made it, in order because the time comes first.

Advanced

The ordering is a property of bit position, not of the values: put the timestamp in the most significant bits and lexical comparison becomes time comparison, so every insert lands in the index tail page rather than a random leaf. That single fact separates a fully random 128-bit identifier from a time-ordered one, and it shows up as page splits, write-ahead log volume and buffer-cache churn rather than as anything visible in application code. The compact 64-bit form buys smaller keys by making you assign each generator a node id; the standard 128-bit form buys administration-free uniqueness by spending those bits on randomness instead.

Expert

Reach for this only where a single writer's sequence is genuinely insufficient — a native sequence is denser, smaller and simpler, and outgrowing one is a measurement rather than an assumption. Where you do, three costs each have a counter-move. Time-based ids depend on a monotonic clock, and a backwards step can duplicate or misorder: pay that by refusing to mint until the clock catches up, and alerting on the stall rather than hiding it. The tail-page concentration that makes indexing cheap becomes a write hot spot at extreme rates: pay that by prefixing a shard or tenant discriminator above the timestamp, trading global ordering for per-shard ordering. And the embedded timestamp and node id leak creation time and fleet shape to anyone holding a key: pay that by keeping the sortable id internal and exposing an opaque random one at the API boundary.

How it works

Variations

Fully random 128-bit identifier
No clock, no node id, no coordination — and no ordering. The right answer when the identifier is public and should reveal nothing, and the wrong one when it is also the primary key of a large indexed table.
Time-ordered 128-bit identifier
A millisecond timestamp prefix, then randomness. Standardized as version 7 in RFC 9562, so most languages have it built in and nothing needs administering. The default choice for a new system.
Compact 64-bit time, node and sequence
Half the width of the standard form, which shows up in every index and foreign key on a large table. The price is assigning each generator a distinct node id and keeping that assignment correct as the fleet changes.
Sortable text encoding
The same time-ordered bits rendered in a case-insensitive base32 alphabet, so the string sorts the same way the bytes do. Useful when the id travels through systems that only handle text, such as object keys or log lines.
Range allocation from a coordinator
A coordinator hands each node a block of numbers, and the node mints locally until the block is exhausted. Keeps ids small and dense at the cost of a dependency and one round trip per block — the middle ground between a shared sequence and pure local minting.
Shard-prefixed identifier
Put a shard or tenant discriminator above the timestamp. Global ordering is given up on purpose, in exchange for spreading inserts across as many hot pages as there are shards.

Trade-offs

Pros

  • Any node mints a key with no round trip, so the write path has no central allocator to queue behind or lose.
  • A time-ordered key keeps inserts at the index tail, so pages fill densely and the hot pages stay cached.
  • Writers can be partitioned, offline or in different regions and still produce keys that never collide.
  • The key doubles as a rough creation timestamp, which makes range scans and retention windows cheap.

Cons

  • The identifier leaks what it encodes: creation time to anyone holding one, and fleet size to anyone collecting a few.
  • Correctness depends on the clock, so a backwards step can mint a duplicate or an out-of-order key.
  • 128-bit keys double index and foreign-key width against a 64-bit integer, on every table that references them.
  • Node-id assignment is the original coordination problem, moved from once per id to once per process — not removed.
  • Each field is a ceiling: the epoch choice sets an exhaustion date, and sequence exhaustion inside one tick blocks the generator until the next.
  • Ordering is only as good as clock agreement between nodes, so two ids a few milliseconds apart say nothing reliable about which event happened first.

When to use it

Reach for it when

  • More than one process mints rows for the same logical table, so no single sequence owns the numbering.
  • The identifier is the primary key of a large, heavily-written indexed table, where insert locality shows up in the bill.
  • Writers must keep working while partitioned from each other, or offline, and reconcile later.

Avoid when

  • One database writer already owns the sequence and has the throughput — a native sequence is smaller, denser and has no clock dependency.
  • The identifier is public and must reveal nothing: use randomness, and keep any sortable key internal.
  • You need a total order you can reason about across nodes — this gives approximate order, not consensus.

Code sketch

TypeScript — the 64-bit layout, including the clock-went-backwards branch 
const EPOCH = 1_700_000_000_000n; // chosen once; changing it invalidates every existing id
const NODE_BITS = 10n, SEQ_BITS = 12n;
const MAX_SEQ = (1n << SEQ_BITS) - 1n;

class IdGenerator {
  private lastMs = -1n;
  private seq = 0n;

  constructor(private nodeId: bigint) {
    if (nodeId >> NODE_BITS) throw new Error("node id does not fit in 10 bits");
  }

  next(): bigint {
    let ms = BigInt(Date.now()) - EPOCH;

    if (ms === this.lastMs) {
      this.seq = (this.seq + 1n) & MAX_SEQ;
      // 4096 ids used inside one millisecond: the only correct move is to wait.
      if (this.seq === 0n) ms = this.spinUntilAfter(this.lastMs);
    } else if (ms < this.lastMs) {
      // The clock moved backwards. Minting now risks reissuing an id we already
      // handed out, so refuse rather than produce a duplicate silently.
      throw new Error(`clock went backwards by ${this.lastMs - ms}ms`);
    } else {
      this.seq = 0n;
    }

    this.lastMs = ms;
    // Field order IS the sort order: time highest, so ids compare by time first.
    return (ms << (NODE_BITS + SEQ_BITS)) | (this.nodeId << SEQ_BITS) | this.seq;
  }

  private spinUntilAfter(ms: bigint): bigint {
    let now = BigInt(Date.now()) - EPOCH;
    while (now <= ms) now = BigInt(Date.now()) - EPOCH;
    return now;
  }
}

In the wild

RFC 9562The current UUID specification, published May 2024 to supersede RFC 4122. It standardizes the time-ordered layout as version 7: a 48-bit Unix millisecond timestamp, then a version marker, sub-millisecond sequence bits, a variant marker and random bits.
SnowflakeThe 64-bit generator Twitter announced in 2010, and the name the timestamp-node-sequence layout is now known by generally: 41 bits of milliseconds, 10 bits of machine id, 12 bits of per-millisecond sequence.
ULIDThe same time-ordered idea specified as a 26-character Crockford base32 string, so the text form sorts the same way the underlying bits do.
PostgreSQL B-tree indexesWhere the cost of random keys is most often measured: scattered inserts force page splits, which shows up as inflated write-ahead log volume and buffer-cache churn rather than as slow queries.

In production

Tuning knobs

  • Field widths and epoch — How many bits go to timestamp, node id and sequence, and which epoch the timestamp counts from. Each choice is a ceiling: generator count, ids per tick, and the date the timestamp field overflows.
  • Node-id assignment source — Where a generator learns its own id — static config, a coordination service lease, or derived from the instance address. Determines what happens when the fleet is replaced.
  • Clock-regression policy — Whether a backwards clock step blocks minting, throws, or is absorbed by a monotonic counter that ignores the wall clock until it catches up.
  • Key width at rest — 64-bit integer versus 128-bit value, which propagates into every index and foreign key that references the row.

Signals to watch

  • Index page splits and write amplification — Splits per second and bytes written to the log per row inserted. The direct measure of whether keys are arriving in order.
  • Sequence exhaustion events — How often a generator uses its whole per-tick sequence and has to wait. Tells you the current headroom against burst write rate.
  • Clock offset against a reference — How far each generator drifts from a trusted time source. Correctness rests on this, and nothing else reports it.
  • Duplicate-key rejection rate — Unique-constraint violations on the primary key. Should be exactly zero; anything else means two generators share a node id.

Failure modes under load

  • Two generators share a node id — A misconfigured or reused node id makes two machines produce identical ids in the same millisecond, and the collision surfaces as a unique-constraint violation on insert — or as silent overwrites where there is no constraint.
  • Insert throughput decays as the table grows — The signature of random keys: fine on an empty table, progressively worse as the index outgrows the buffer cache and every insert touches a cold page.
  • Clock step stalls the write path — A time correction moves the clock backwards and the generator refuses to mint until it catches up, so writes block for the length of the correction.
  • Tail page becomes the write hot spot — Perfect time ordering concentrates every insert on one leaf page, so the locality win turns into lock contention at the top of the index.

Readiness checklist

  • Node ids are unique by construction — leased or derived, not hand-assigned in config where a copy-paste reuses one.
  • A backwards clock step blocks minting and raises an alert, rather than being allowed to reissue an id.
  • The key width and the epoch are recorded as decisions, since neither can be changed later without rewriting every stored id.
  • Sequence exhaustion is measured, so the per-tick ceiling is known against real burst rates rather than assumed.
  • Any identifier exposed publicly is opaque, so the internal sortable key does not leak creation time or fleet size.
