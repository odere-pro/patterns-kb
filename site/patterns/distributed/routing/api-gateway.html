Network · Routing & Scale

API Gateway

A single front door for a constellation of backend services — every request lands here first, gets authenticated, rate-limited, and routed to the right service, so clients never learn the internal topology behind it.

Distributed Routing & Scale

What it is

Your mobile app knows the address of nine backend services, and proves who the user is to every one of them. Split one of those services in two and the app breaks in the field, where you cannot fix it. Get the auth check subtly wrong in one of the nine and only that one is wrong, quietly. An API gateway gives clients a single address to talk to: it checks the caller once, works out from the request who should handle it, and passes it on.

The gateway dispatches on what a request means — which path, host, header, API version or tenant — and so chooses among services that deploy independently of each other and of it. On the way through it applies the policy each of those services would otherwise reimplement: authentication, rate limiting, request logging, response caching, and translation between the protocol the client speaks and the one the backend speaks. That decision layer, not the forwarding underneath it, is the pattern.

What that buys is one seam instead of a fan-out. Clients bind to a surface that stays still while services behind it are split, merged and rehomed, and the rules that must hold for every caller — who you are, how much you may ask for, what gets logged — live in one deployable rather than in a dozen copies that drift apart.

It is not just a reverse proxy with a different name. A reverse proxy forwards bytes; a gateway makes routing decisions grounded in the request's meaning — which API version, which tenant, which feature flag — and layers policy on top of that. That extra intelligence is also its hazard: pushed too far, the gateway accretes business logic that belongs in the services it's meant to be routing to, not in the routing layer itself.

Explained at three levels

Basic

Put one address in front of everything, and let it work out who should handle each request. Like a single border post: one check, one set of rules, then on you go. Three things get easier at once. The caller proves who it is here and nowhere else, so the check cannot be right in one place and quietly wrong in another. The same door counts how much each caller is asking for and writes down what came through, so nobody has to build that twice. And when a team moves or splits the service behind the door, callers never find out — the address they know did not change.

Advanced

Give external clients one entry point that dispatches on what a request means — path, host, header, API version, tenant — and so selects among services that deploy on their own schedules. On the way through it applies what those services would otherwise each reimplement: authentication, rate limiting, logging, response caching, and translation between the client protocol and the internal one. The variants divide by how much the edge does beyond dispatch. Pure routing keeps the edge thin and the reading rule — path prefix, hostname, or header — is itself a decision about who owns configuration. Aggregation composes several backend calls into one response, which cuts round trips for a distant client and puts fan-out latency and partial-failure handling in the edge. Offloading moves TLS termination, compression and caching off every service. And a backend for frontend gives each client class its own gateway rather than one config that has to satisfy web, mobile and partners at once.

Expert

Choose it when many services face outside clients and one set of authentication, quota and versioning rules has to hold identically across all of them; the payoff is that clients bind to a stable surface while the topology behind it churns. Most of the bill is organisational, and each part has a counter-move. It is one shared deployable on one release cadence that every routing team now depends on, so split by client class into backends for frontend before you start negotiating a single config between teams that want different things. It attracts business logic that belongs in services, so make the test explicit — anything a second client would have to duplicate belongs behind the edge, not in it — and apply it at every release, because that drift is one-way. It is on the path of every external request, so per-upstream timeouts and circuit breaking are not optional: without them one slow backend consumes the shared connection pool and takes the unrelated routes with it. And what it enforces is edge-deep only: service-to-service traffic and batch jobs never pass through, which is the gap a service mesh fills. Then run the loop — tune limits and upstream timeouts per route, watch gateway-added p99 against backend service time, find whether the tier or one upstream saturates first, and gate the release on a config rollout that is progressive and reversible.

How it works

Variations

Gateway Routing
Pure request dispatch with no aggregation or reshaping — the thinnest form of the pattern. What the gateway reads to choose a service is a decision of its own, with its own trade-offs: a path prefix gives consumers one address and every team a shared configuration, a hostname gives each team its own name and each consumer another one to remember, and a header carries versions and variants on top of either. See API Routing.
Gateway Aggregation
Fans a single client request out to several backend calls and composes the results into one response, cutting round trips for slow or mobile clients.
Gateway Offloading
Moves shared infrastructure concerns — TLS termination, compression, caching, auth — out of every service and into the gateway itself.
Backend-for-Frontend
One gateway per client type — web, mobile, partner — instead of a single universal gateway trying to satisfy all of their conflicting needs at once.
Streaming Gateway
Carries a long-lived streaming response — server-sent events, chunked transfer, or a WebSocket upgrade — rather than buffering one payload and returning it. It shifts the gateway's job from request/response to holding an open flow, which forces different read timeouts, disables response buffering, and often needs connection affinity (see Sticky Session) so the stream isn't cut mid-flight by a rebalance.
Agent-Facing Gateway
Exposes backing capabilities as discoverable, self-describing tools an autonomous AI agent can enumerate and invoke at runtime, instead of fixed endpoints a human wired up ahead of time. The agent is just another client class — a Backend-for-Frontend for software that decides its own calls. Anthropic's Model Context Protocol (MCP) is the current real-world example of this tool-server shape.

Trade-offs

Pros

  • One place to enforce auth, rate limiting, and logging instead of duplicating it in every service.
  • Clients depend on a stable surface, not the internal service topology, which is free to change behind it.
  • Central point for protocol translation and API versioning as backends evolve independently.
  • Aggregation can cut chatty round trips for clients on slow or high-latency networks.

Cons

  • A single point of failure and a potential bottleneck — run it as a horizontally scaled tier across zones, or it relocates the outage it was meant to prevent.
  • Prone to becoming a dumping ground for business logic that belongs in the services behind it — anything a second client would have to duplicate is a service's job, not the edge's.
  • Adds a network hop and a layer of latency to every single request.
  • Yet another highly-available deployable to build and operate, and a shared release cadence every team routing through it now depends on — give each client class its own backend for frontend rather than negotiating one config between teams that want different things.
  • Edge policy is only edge-deep. Service-to-service calls, batch jobs and internal tools never cross the gateway, so anything it enforces has to be enforced inside the perimeter too — that is the work a service mesh exists to do.

When to use it

Reach for it when

  • Clients — web, mobile, partners — need one stable entry point across many backend services.
  • You need auth, rate limiting, or logging enforced consistently without repeating it per service.
  • Backend services are being split, merged, or migrated and clients shouldn't feel any of that churn.

Avoid when

  • There's a single backend service — there's no fan-out to front, just call it directly.
  • Client types have sharply different aggregation needs — one shared gateway becomes a tangle of conflicting requirements; split it with a Backend-for-Frontend per client instead.
  • The team can't yet run one more highly-available, horizontally-scaled service — an under-resourced gateway just becomes the new single point of failure.

Code sketch

TypeScript — a minimal routing gateway 
type Route = { prefix: string; target: string };

const routes: Route[] = [
  { prefix: "/orders", target: "http://orders-svc:3000" },
  { prefix: "/users", target: "http://users-svc:3000" },
  { prefix: "/inventory", target: "http://inventory-svc:3000" },
];

app.use(authenticate);              // once, at the edge
app.use(rateLimit({ windowMs: 60_000, max: 100 }));

app.use(async (req, res, next) => {
  const route = routes.find((r) => req.path.startsWith(r.prefix));
  if (!route) return res.status(404).json({ error: "no route" });

  try {
    const upstream = await fetch(route.target + req.path, {
      method: req.method,
      headers: req.headers as HeadersInit,
      body: req.method === "GET" ? undefined : req.body,
    });
    res.status(upstream.status).send(await upstream.text());
  } catch {
    next(new Error("upstream unavailable")); // let error middleware handle it
  }
});

In production

Tuning knobs

  • Rate-limit thresholds — Requests per window per client, key or route, and the burst allowed before the edge starts refusing.
  • Upstream timeout and retry — How long the gateway waits on a backend and whether it retries — the dial that decides if one slow service can hold the caller.
  • Upstream connection pool — Concurrent connections held to each backend, which bounds in-flight requests per upstream and keeps one of them from taking the whole tier.
  • Response cache TTL — How long a cacheable response is served from the edge before the backend is asked again.
  • Body size limits — Caps on request and response payloads, so one large upload cannot exhaust gateway memory.
  • Config rollout unit — How route and plugin configuration is delivered — all at once, per route, or progressively — which sets how much traffic a bad change can reach.

Signals to watch

  • Gateway-added latency — The p99 of the edge hop measured against backend service time — what the seam costs every request.
  • Rejection rate per route — Requests refused at the edge by limit or policy, per route and client, which separates one abusive caller from a limit set too low.
  • Upstream error and timeout rate — 5xx and timeouts per upstream, so a single failing backend is still identifiable behind the single surface.
  • Tier resource and connection count — CPU, memory and open connections on the gateway fleet — the capacity that every route shares.
  • Traffic never reaching a service — The share answered entirely at the edge by cache, rejection or failed auth — the load the gateway is genuinely removing.

Failure modes under load

  • Whole surface down — An undersized or unhealthy gateway tier makes every route behind it unreachable at once, however healthy the services are.
  • Head-of-line blocking — One slow upstream ties up shared connections or worker threads and starves unrelated routes, unless each upstream has its own bound.
  • Auth dependency outage — With identity checked per request against an external provider, that provider being unreachable fails every request at the edge.
  • Bad config rollout — A broken route or plugin reaches live traffic in one step and stays broken until someone rolls it back.
  • Retry amplification at the edge — The gateway retrying on behalf of a client that also retries multiplies load on a backend that is already failing.

Readiness checklist

  • Losing one gateway instance under load was tried, and traffic kept flowing — the tier is proven horizontal, not drawn that way
  • One backend held slow shows unrelated routes still serving, so head-of-line blocking is ruled out by test rather than by intent
  • What the edge does when the identity provider is unreachable was chosen deliberately and someone outside the team agreed to it
  • Route and plugin config is validated before it ships, rolled out progressively, and reversible without a full redeploy
  • Every route records its owning team, so an error at the edge is attributable without reading the config
  • Nothing on the gateway holds logic a second client would have to duplicate, reviewed each release because that drift only goes one way
