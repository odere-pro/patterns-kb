Valet Key

A short-lived, narrowly scoped key lets a client reach a resource directly — one file, one queue, one row — without ever holding your master credentials or making your servers proxy the traffic.

Distributed Routing & Scale

What it is

Every file a user uploads arrives at your server, which reads it into memory and writes it straight out to the storage bucket. You pay for that bandwidth twice and hold a connection for the length of a phone upload, and your server adds nothing to the bytes it copies. Letting the browser talk to the bucket itself would fix that, except the browser would then need the credentials to the whole bucket. A valet key is the third option: a token that opens one file, for one action, for the next few minutes.

A trusted service authenticates the caller and mints a signed credential naming one resource, one action and one expiry — canonically a presigned storage URL or a shared-access-signature token. The resource validates that signature on each use and never calls back to the issuer, so the issuing server leaves the data path entirely and keeps only the decision: who may have a key, over what, for how long.

The split is between deciding and carrying. Your server keeps the decision, which is the part that needs your business rules; the resource takes the bytes, which is the part it is already built to do at scale. It's named for the valet who's handed a key that starts the car and pops the trunk, but can't touch the glovebox or drive it off the lot.

Once minted, a key is a bearer credential: whoever holds it can use it until it expires or its uses run out. That trade — convenience and scale against a window of exposure — is what every variation below tunes.

Explained at three levels

Basic

A user uploads a video and it goes through your server on its way to storage. Your server reads every byte and writes every byte, adds nothing to any of them, and cannot answer anyone else while it does. The obvious fix — let the browser talk to the storage directly — means giving the browser the password to all of your storage, which is far more than this one upload needs. So hand out a spare key instead: it opens one file, allows one action, and stops working in a few minutes. Like a hotel card that only opens your room and dies at checkout.

Advanced

A trusted service authenticates the caller, decides what they may do, and mints a signed credential naming exactly one resource, one action and one expiry. The resource verifies that signature itself on every use and never calls back, so the issuer is out of the data path and the bytes go client-to-store. The variants differ in what the credential covers and how long it survives. A presigned URL covers one object; a signed cookie covers a path prefix, which is what private CDN content needs; a capability URL is the whole credential, so the link and the permission are one thing; and a single-use key is invalidated on redemption, closing the replay window at the cost of a round trip. Where the resource supports extra conditions — an IP range, HTTPS only, a start time — they narrow the same credential further.

Expert

Choose it when the payload is large and the entire authorization decision can be made at issuing time; you buy back bandwidth, connections and server memory, and you give up every per-request hook you had while the bytes went through you. What you hand out is a bearer credential, so the expiry is the blast radius. A bare signed URL usually cannot be pulled back — bind it to a server-side policy or to a signing key you can rotate if a recall has to be possible, and know that this form is fixed at minting, not during the incident. Three further costs carry counter-moves. Scope built from client-supplied input will happily name someone else's object, so derive it from the authenticated identity. Keys leak through logs, referrer headers and shared links, so keep them out of anything that records URLs and keep the window short. And your audit trail now ends at issuance while the resource holds the rest, so make the two joinable before an auditor asks. Then run the loop: tune the TTL and the scope to the operation, watch the invalid-key rejection rate for skew and replay, find whether the resource or the minting path saturates first, and gate the release on a rehearsed signing-key rotation.

How it works

Variations

Pre-signed URLs
A cloud storage vendor signs a URL with an embedded expiry and permission set — S3 pre-signed URLs and Azure SAS tokens are the canonical form.
Signed cookies
The key rides in a cookie instead of the URL, so it covers a whole path prefix (a CDN's private content tree) rather than one object.
Single-use vs. multi-use keys
A single-use key is invalidated after one redemption, closing the replay window entirely; a multi-use key trades that safety for fewer round trips.
Capability URLs
The URL itself is the only credential — no separate login step — so possessing the link is equivalent to holding the permission.

Trade-offs

Pros

  • Removes the app server from the data path, freeing it for control-plane work only.
  • Scales bandwidth- or storage-heavy operations without provisioning servers to carry them.
  • Scoped and time-limited, so a leaked key exposes only one resource, and only briefly.
  • The client never holds standing credentials to the resource itself.

Cons

  • A valid key generally can't be revoked before it expires — bind it to a server-side policy or a signing key you can rotate if you need a recall, and decide that at minting time rather than during the incident.
  • Getting scope or expiry wrong quietly grants broader or longer access than intended — derive the scope from the authenticated identity, never from a path the client supplied.
  • Requires the resource layer to support token-based validation — not every store does.
  • Clock skew or an overlong expiry undermines the whole "temporary" guarantee — keep both sides on synchronized time and treat the expiry as the blast radius, since it is.
  • Your audit trail stops at issuance: what the holder actually did is only in the resource's own access log. Make the two joinable on a request or object id, or the record has a hole exactly where the data path used to be.
  • Caps neither the bytes transferred nor the number of times the key is used, so a client looping on an upload runs up an egress bill against a key that is behaving exactly as issued. Where the store allows it, grant create rather than write — create refuses to overwrite, which makes each key good for one object.
  • Puts a live credential in a URL, which means it lands in every access log along the path. Restrict who can read those logs, and hold log shipping back until the keys inside have expired.

When to use it

Reach for it when

  • Clients need direct, high-volume access to a resource — file upload or download — and proxying it through your servers is wasted work.
  • You want to offload bandwidth to a CDN or blob store without ever issuing standing credentials.
  • The access need is transient and well-defined — one object, one action, one short window.

Avoid when

  • The operation needs per-request business logic or auditing that only your server can enforce.
  • You can't safely bound the scope or lifetime within the resource's own access model.
  • Revocation before expiry is a hard requirement and the resource has no way to honor it.

Code sketch

TypeScript — minting and verifying a fifteen-minute upload key 
interface ValetKey {
  resource: string;
  action: "read" | "write";
  expiresAt: number;
  signature: string;
}

function mintKey(resource: string, action: ValetKey["action"], ttlMs: number, secret: string): ValetKey {
  const expiresAt = Date.now() + ttlMs;
  const payload = `${resource}:${action}:${expiresAt}`;
  return { resource, action, expiresAt, signature: hmacSha256(payload, secret) };
}

// Run by the object store itself, never by the API that minted the key
function verifyKey(key: ValetKey, requestedResource: string, secret: string): boolean {
  if (Date.now() > key.expiresAt) return false;              // past the window
  if (key.resource !== requestedResource) return false;       // one key, one object
  const payload = `${key.resource}:${key.action}:${key.expiresAt}`;
  return hmacSha256(payload, secret) === key.signature;        // tamper check
}

// The onboarding API mints a fifteen-minute write key for exactly one ID photo and
// hands it to the onboardee. The bytes go browser → store; this server never sees them.
const resource = `id-photos/${personaId}/${flowId}.jpg`;
const key = mintKey(resource, "write", 15 * 60_000, SECRET);
const uploadUrl = `https://blobs.example.com/${resource}?exp=${key.expiresAt}&sig=${key.signature}`;

In the wild

Amazon S3 pre-signed URLsThe app signs a URL with the caller credentials, scoped to one object and one HTTP method, with a bounded expiry (up to 7 days for signature v4); the browser then uploads or downloads straight to S3 with no account key exposed.
Azure Shared Access SignaturesGrants a named permission set (read, write, list) on a blob, container, or queue for a start-to-expiry window, optionally restricted by IP range and HTTPS-only; a user-delegation SAS is signed with Microsoft Entra credentials so the account key never leaves the server.
CloudFront signed URLs and cookiesThe distribution nominates a trusted key group whose public key validates each signature, granting time-limited access to private edge content; a signed URL covers one file while signed cookies cover a path pattern, and a custom policy can additionally restrict by IP range and date window.

In production

Tuning knobs

  • Expiry (TTL) — How long the key stays valid. Make it as short as the operation allows, because it is the window a leaked key stays useful for.
  • Scope — The resource and actions the key names — one object, one method. It is the ceiling on what a leaked key can reach.
  • Single-use or multi-use — Whether redemption invalidates the key, closing the replay window, or it stays usable until expiry for fewer round trips.
  • Clock-skew tolerance — The leeway allowed on expiry checks, absorbing small differences between the minting server and the validating resource.
  • Redemption conditions — Extra restrictions the resource can enforce where it supports them — an IP range, HTTPS only, a start time — narrowing the same credential further.
  • Signing key rotation period — How often the signing material changes. Rotation is the only recall some key forms have, so its period is also a security dial.

Signals to watch

  • Invalid-key rejections — Keys refused at the resource as expired, wrong-scope or badly signed. A spike is clock drift, replay attempts or a broken minting path.
  • Issuance rate — Keys minted per unit time, per caller. A client minting far more keys than it uploads is worth a look.
  • Direct-to-resource share — Bytes moving client-to-store against bytes still passing through the app server — the traffic the pattern has actually offloaded.
  • Time from minting to redemption — How long keys sit before use. Keys redeemed near expiry mean the TTL is protecting less than its number suggests.

Failure modes under load

  • Over-broad or over-long grant — A scope or expiry wider than the moment needed hands out access nobody reviewed, and a leaked key keeps all of it.
  • Scope built from client input — A key whose object path comes from the request can name another user's object, and the resource will honour whatever the signature covers.
  • Revocation decided too late — A bare signed URL cannot be withdrawn before it expires; a policy-bound or rotatable-key form can. Which one you issued was settled at minting.
  • Clock skew — Minter and resource disagreeing on the time reject live keys or honour dead ones, and neither failure is obvious from the error.
  • Key leakage — A credential in a URL travels into logs, referrer headers, screenshots and shared links, and whoever holds it can use it.

Readiness checklist

  • Minting is authenticated and authorized by the same rules that used to guard the proxying endpoint — the decision moved, it did not disappear
  • The scope of every key is derived from the authenticated identity, never from a path or object id the client sent
  • The signing secret lives in a secret store and its rotation has been rehearsed, since rotation is the only recall some key forms have
  • Keys are kept out of access logs, referrer headers and analytics, checked against what a request actually records rather than what it should
  • Clocks on the minting and validating sides are synchronized, and the skew the resource tolerates is known rather than assumed
  • Someone decided in advance what happens when a key leaks — short TTL, policy-bound issuance, or resource-side revocation where it exists
  • Issuance logs and the resource access log can be joined on a request or object id, so the audit trail survives leaving the data path
