Backend-for-Frontend

Gives each class of client — mobile app, web app, third-party partner — its own backend, shaped around exactly the calls and payloads its screens need, instead of forcing every client through one general-purpose API.

Distributed Routing & Scale

What it is

A Backend-for-Frontend (BFF) is a thin backend service built and owned by the same team as one specific client — the iOS app, the web app, a partner integration — sitting between that client and the shared downstream services. It calls whatever it needs, aggregates the results, and returns exactly the shape that client's screens expect.

The force it resolves is a one-size-fits-none API. Mobile wants a small, denormalized payload to save battery and bandwidth; the web app wants a richer, more graph-shaped response for a dense dashboard; a partner needs a stable, versioned contract that can't shift under it. A single general-purpose API serving all three accretes optional fields, client-detection branches, and version flags until every change risks breaking someone else's consumer.

The BFF splits that API along client lines instead. Each frontend gets a backend that speaks only its own language, evolves on its own release schedule, and is owned by the people who actually feel the pain when it's wrong — the frontend team, not a shared platform team fielding requests from three directions at once.

It doesn't replace the shared services underneath; it sits in front of them as a translation and aggregation layer, so the services stay generic while the client-specific shaping lives at the edge, one BFF per client.

Explained at three levels

Basic

One shop counter serving every kind of customer ends up serving none of them well — the list of goods grows, and each visitor picks through things they never wanted. Give each regular their own personal shopper instead. Same shelves, same stock, but the shopper walks the aisles and returns with exactly that person's basket, and answers only to them.

Advanced

Backend-for-Frontend gives each client type — iOS, web, a partner integration — its own thin service, built and released by the team that owns that client. It fans out to the shared downstream services in parallel, aggregates their responses, and returns one denormalized payload matching that client's screens, so the generic services keep no client-specific branching. It sits in front of those services rather than replacing them, splitting the single-gateway idea along client lines, with edge-deployed variants running it close to the client.

Expert

Choose it when client types diverge sharply enough that one generic contract cannot serve them — different payload shapes, aggregation and release cadences — and the frontend team will run a service. The value is that client-specific shaping moves to a layer the client's own team owns, so the shared services stay generic and nobody's change breaks a stranger's consumer. The bill is one more deployable per client, each with its own pipeline, dashboards and on-call, plus cross-cutting concerns — auth, error mapping, caching — that duplicate across them until someone extracts a shared library. Left unwatched, the same downstream entity drifts into a different shape behind every client, and the divergence has no owner.

How it works

Variations

Per-platform BFF
One BFF per platform — iOS, Android, web — each tuned to that platform's payload size, latency budget, and release cadence.
One BFF per experience
Count the BFFs by the experiences you deliver, not by the app stores you publish to: if iOS and Android present the same experience, one mobile BFF serves both and there is one shaping layer to keep in step instead of two. Ownership decides the rest — a BFF that two teams change is a shared backend again. The risk runs the other way as its client list grows, when the accumulated per-client shaping starts to conflict and the split you avoided becomes the fix.
GraphQL BFF
The BFF exposes one GraphQL schema instead of several REST endpoints, so each screen queries exactly the fields it needs in a single round trip.
Team-owned BFF
The BFF lives in the same repo and on-call rotation as the frontend it serves, so the frontend team ships both without waiting on a shared backend team.
Edge-deployed BFF
Runs as an edge function (Lambda@Edge, Cloudflare Workers) close to the client, so aggregation happens near the request instead of after a long backbone hop.
Agent BFF
An autonomous AI agent is its own class of client: it discovers operations at runtime and needs self-describing, coarse-grained tools rather than the fine-grained calls a screen makes. A BFF shaped for it — exposing tools over something like the Model Context Protocol (MCP) — beats making the agent share a human-facing API.

Trade-offs

Pros

  • Each client gets a payload shaped exactly for its screens — no unused fields, no client-side reshaping.
  • Frontend teams own their BFF and ship on their own schedule, without queuing behind a shared backend roadmap.
  • Aggregates several downstream calls into one round trip, cutting chattiness for bandwidth-constrained clients.
  • Keeps client-specific branching out of the shared services, which stay generic and simpler to reason about.

Cons

  • Multiplies backend services — one per client type — each with its own deploy, monitoring, and on-call.
  • Cross-cutting logic (auth, error mapping, caching) tends to duplicate across BFFs unless it's factored into a shared library.
  • The same downstream data can drift into slightly different shapes across BFFs if no one's watching for it.
  • Adds one more hop and one more moving part between the client and the services it ultimately needs.

When to use it

Reach for it when

  • You serve genuinely different client types whose data shape, aggregation, or performance needs diverge sharply.
  • A shared general-purpose API has accreted so many client-specific branches that no one client is well served.
  • A frontend team wants to own its own backend contract and ship on its own schedule.

Avoid when

  • There's only one client type — a single well-designed API is simpler, with nothing to specialize for.
  • Clients' needs are similar enough that optional fields or partial responses on one API cover them without duplication.
  • You lack the operational capacity to run, deploy, and monitor another service per client.

Code sketch

TypeScript — a mobile BFF aggregating two services 
// Mobile BFF: one call, shaped for the app's home screen
app.get("/mobile/home/:userId", async (req, res) => {
  const { userId } = req.params;

  // Fan out to the shared backend services in parallel
  const [profile, orders] = await Promise.all([
    userService.getProfile(userId),
    orderService.getRecentOrders(userId, { limit: 3 }),
  ]);

  // Reshape into exactly what the mobile UI renders — nothing more
  res.json({
    name: profile.displayName,
    avatarUrl: profile.avatarSmallUrl,  // small asset, not the desktop one
    recentOrders: orders.map(o => ({
      id: o.id,
      total: o.totalFormatted,
      status: o.status,
    })),
  });
});

In the wild

In production

Tuning knobs

  • Per-downstream call timeout — How long the BFF waits on each backend before giving up, so the slowest dependency bounds the aggregated response.
  • Fan-out concurrency — Whether downstream calls run in parallel and any cap on simultaneous in-flight calls per request.
  • Response cache TTL — How long a client-shaped response or a downstream result is cached before it is refetched.
  • Downstream connection pool size — Bounds the concurrent connections the BFF holds to each shared service.

Signals to watch

  • Aggregated endpoint p99 latency — Tracks the slowest downstream in the fan-out, which dominates the response.
  • Per-dependency error and timeout rate — Failure rate the BFF sees toward each shared service it aggregates.
  • Response payload size — Bytes returned to the client — the thing a mobile BFF exists to keep small.
  • Fan-out call count per request — Downstream calls made per request, to catch accidental N+1 fan-out.

Failure modes under load

  • Slowest-call stall — One lagging downstream in a fan-out holds up the whole response unless per-call timeouts and a partial or degraded response are in place.
  • Duplicated cross-cutting logic — Auth, error mapping, and caching drift apart across per-client BFFs when they are not factored into a shared library.
  • Shape drift — The same downstream data ends up subtly different across BFFs, so clients disagree about the same entity.
  • BFF as a logic sink — Business rules accrete in the BFF that belong in the shared services behind it.

Readiness checklist

  • Per-downstream timeouts with a partial or degraded response path when a dependency is slow or down.
  • Downstream calls fanned out in parallel, not chained sequentially.
  • Owned by the frontend team with its own deploy pipeline and on-call.
  • Shared cross-cutting concerns factored into a common library, not copy-pasted per BFF.
