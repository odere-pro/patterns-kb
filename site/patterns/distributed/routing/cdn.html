Network · Routing & Scale

CDN

Pushes static content out to a distributed fleet of edge servers positioned near users, so a request is answered from a nearby cache instead of crossing continents to a single origin.

Distributed Routing & Scale

What it is

A content delivery network is a fleet of cache servers — points of presence (PoPs) — distributed across regions, sitting between clients and an origin server. DNS or anycast routing sends each request to the nearest PoP rather than the origin. If that PoP already holds a fresh copy of the asset, it answers directly: no round trip to the origin, no origin load at all.

The force it resolves is distance. Round-trip latency is bounded by the speed of light long before any origin-side optimization runs out of headroom — a request crossing half the globe pays that tax no matter how fast the origin responds. A CDN doesn't make the origin faster; it makes the trip shorter by answering from somewhere close to the request.

It resolves a second force too: concentrated load. A single origin serving every client on every request is one target for every spike, every hotlink, every crawler. By absorbing the repeat, cacheable traffic at the edge, the origin only ever sees the cold path — first requests and cache misses — and a global surge in demand never has to reach it directly.

Explained at three levels

Basic

When the same things are asked for over and over from far away, keep copies close to the people who want them. Big shops do this with regional depots: popular goods sit a few miles from your town rather than at one distant factory, so an order arrives next day. The catch is that a depot restocks on its own schedule.

Advanced

A fleet of cache servers — points of presence — stands in front of the origin, and DNS or anycast routing steers each request to the nearest one. A PoP holding a fresh copy answers on the spot; on a miss it pulls from the origin, stores the result for the length of its TTL, and serves everyone after that locally. A purge is how you take a copy back early. It fronts object storage naturally, and edge compute lets a PoP decide as well as serve.

Expert

Choose it when the same bytes are read far more often than they change and the audience is not one region: the payoff is that distance stops being a tax on the common case and the origin only ever sees cold paths. Invalidation is the standing bill — a TTL is a promise to serve stale for that long, and a purge is only eventually consistent across a global fleet, so freshness ends up handled in your release process. Personalized responses cache nothing and pay the extra hop anyway. And a second vendor in the request path is another thing to misconfigure, whose failures you debug from the outside, PoP by PoP, on someone else's logs.

How it works

Variations

Cache-Aside pull model
The default: an edge node checks its own cache, and on a miss fetches from origin and stores the result — origin traffic tracks only cold, actually-requested paths.
Push CDN
The origin proactively uploads or replicates content to edges ahead of demand, instead of waiting for a first request. Common for large media libraries with a known release schedule.
Consistent Hashing for edge selection
Within a PoP or across a shard, requests for the same key route to the same cache node by hash, so duplicate copies of one object don't scatter across the fleet.
Multi-CDN
Route across two or more CDN vendors, by region or health, to avoid a single provider's outage or peering problem taking down delivery entirely.
Edge compute
Run request-time logic — auth checks, redirects, A/B routing, image transforms — at the PoP itself, so even dynamic decisions skip the trip to origin.

Trade-offs

Pros

  • Cuts latency by answering from a PoP physically close to the user, not the origin.
  • Absorbs traffic spikes and bandwidth cost at the edge, shielding the origin.
  • Improves availability — cached content can keep serving through an origin outage.
  • Scales to a global audience without provisioning the origin for worldwide peak load.

Cons

  • Cache invalidation is the hard part — stale content lingers until TTL expiry or a purge propagates everywhere.
  • Personalized, highly dynamic, or per-user content doesn't cache well and gains little.
  • Another layer of infrastructure, config, and vendor to operate and debug.
  • Doesn't remove the origin dependency — cold paths and misses still hit it directly.

When to use it

Reach for it when

  • You serve static assets — images, scripts, video, downloads — to a geographically spread audience.
  • Traffic is spiky or global, and the origin shouldn't have to absorb it directly.
  • Latency to a distant origin region is the bottleneck users actually feel.

Avoid when

  • Content is deeply personalized per request with no cacheable overlap between users.
  • Your whole audience is co-located with the origin — there's no distance to remove.
  • Reads must be strictly consistent and a stale cached response is unacceptable.

Code sketch

TypeScript — a minimal pull-mode edge cache 
interface Origin {
  fetch(path: string): Promise<{ body: string; ttlSeconds: number }>;
}

interface CacheEntry {
  body: string;
  expiresAt: number;
}

class EdgeNode {
  private cache = new Map<string, CacheEntry>();

  constructor(private readonly origin: Origin) {}

  async serve(path: string): Promise<string> {
    const hit = this.cache.get(path);
    if (hit && hit.expiresAt > Date.now()) {
      return hit.body; // cache hit — no origin request
    }
    const { body, ttlSeconds } = await this.origin.fetch(path); // cache miss
    this.cache.set(path, { body, expiresAt: Date.now() + ttlSeconds * 1000 });
    return body;
  }

  purge(path: string): void {
    this.cache.delete(path); // explicit invalidation ahead of TTL
  }
}

In the wild

AkamaiOne of the first CDNs, grown out of MIT research on consistent hashing for web caching; its distributed edge fleet serves cached objects from PoPs close to users and pulls from origin only on cold paths.
CloudflareUses anycast to route each request to the nearest of its many PoPs; edges serve cached assets and can run request-time logic in the Workers runtime, and tiered caching funnels misses through upper-tier data centers to cut origin load.
FastlyBuilt on Varnish; its instant-purge system can invalidate cached objects across the whole network in seconds, and VCL and its Compute platform let request logic run at the edge.

In production

Tuning knobs

  • Cache TTL / max-age — How long an edge serves an object before revalidating with origin, set via Cache-Control or an edge override per asset class.
  • Cache key composition — Which parts of the request — path, selected query params, headers, cookies — vary the cached object; over-broad keys destroy the hit ratio.
  • Origin timeout and failover — How long the edge waits on origin and whether it fails over to a backup origin or serves stale content.
  • Tiered caching / origin shield — Whether misses funnel through a mid-tier before hitting origin, so origin sees far fewer requests.
  • Purge and invalidation strategy — TTL expiry versus explicit purge for pushing new content out ahead of TTL.

Signals to watch

  • Cache hit ratio — The fraction of requests served from the edge — the primary health metric for offload.
  • Origin request rate and egress — What actually reaches origin after edge offload, and the bandwidth it costs.
  • Edge latency and error rate — p99 and error rate split by edge-served versus origin-served responses.
  • Bandwidth served from edge — Bytes delivered at the edge versus fetched from origin.

Failure modes under load

  • Hit-ratio collapse — The cache key varies on a cookie or volatile query param, so nearly everything misses and origin is flooded.
  • Stale content after deploy — TTL too long or a purge that did not propagate leaves old assets served from some PoPs.
  • Cache stampede — Many edges miss the same key at once when it expires and hit origin simultaneously; needs request coalescing or a shield.
  • Origin outage past TTL — Once cached copies expire the edge has nothing to serve, and errors surface to users.

Readiness checklist

  • Cache key normalized — irrelevant query params and cookies stripped to maximize hits.
  • Cache-Control and TTLs set per asset class; static assets fingerprinted in the URL for safe cache-busting.
  • Purge and invalidation path tested and fast enough for the content's change rate.
  • Origin protected by request coalescing or a shield tier so a miss storm cannot overwhelm it.
  • Hit ratio and origin offload monitored with alerts.
