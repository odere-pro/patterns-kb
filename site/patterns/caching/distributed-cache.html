Distributed Cache

A caching service that runs as its own tier — Redis, Memcached — separate from the application and the database, so every application instance reads and writes the same entries over the network instead of each keeping its own private copy.

Caching

What it is

A distributed cache is a dedicated caching service — Redis or Memcached being the usual choices — that lives in its own tier, separate from both the application and the database. The application reaches it over the network: on a read it asks the cache first, and only a miss falls through to the source of truth, whose value is then written back into the cache for next time.

The force it resolves is sharing. A scaled system runs many application instances, and if each kept its own cache, they'd waste memory holding duplicate copies and, worse, disagree about the value of the same key. A distributed cache gives every instance one shared view: once any instance populates a key, all the others get the hit for free. It's the default cache in most system designs precisely because it decouples cache capacity and lifetime from any single app process — the cache survives deploys and restarts, and scales on its own.

Explained at three levels

Basic

Twenty servers answer requests, and each one asks the database the same question and keeps its own copy of the answer. That is twenty copies of one piece of data, twenty times the database work, and nineteen servers still handing out the old value after the twentieth learns it changed. Put the answers in one memory store that all twenty servers reach instead. Whichever server looks something up first puts the answer there, and every other server reads it back without going near the database. Like a shared fridge in an office kitchen rather than a mini-fridge under each desk.

Advanced

That store is a dedicated service — Redis and Memcached are the usual choices — running in its own tier, so its memory ceiling, its eviction policy and its lifetime are set independently of any application process, and entries survive deploys, restarts and autoscaling. Past one node's capacity or throughput it shards: clients map each key to an owning node, and consistent hashing (or a fixed slot map, as in Redis Cluster's 16,384 hash slots) keeps a node change from reshuffling the whole keyspace. Each shard usually carries replicas, so losing a node does not cold-start its slice. The tier is only the store — how reads and writes flow through it is a separate choice, cache-aside by default, read-through or write-through when that logic moves into the cache layer — and a small in-process cache in front of it answers the hottest keys without the hop.

Expert

Choose it when instances must agree on one view and the cache has to outlive any single process; keep the data local instead when one instance serves the traffic or the working set is tiny, because a local read has no hop to pay. Three costs come with the tier, each with a counter-move. Every hit pays a network round trip plus serialization on both ends, so put a small near cache in front of the handful of keys that dominate reads and accept the cross-instance staleness that buys. One very popular key lands on a single node however wide the cluster, saturating it while the rest look idle — replicate that key under several suffixed names, or coalesce concurrent misses so one request reaches the origin instead of thousands. A node that dies or restarts hands its whole slice to the origin at once, so replicate every shard with automatic failover and jitter TTLs so keys do not expire in lockstep. Then run the loop: tune max memory and the eviction policy, watch hit rate and per-node request skew, expect a hot key to break first, and gate on the ceiling, the routing and the failover being set before the tier carries traffic.

How it works

Variations

Single node vs. clustered
One cache node is simplest; past its capacity or throughput, the cache is sharded across a cluster and clients pick the owning node — commonly by consistent hashing so a node change reshuffles the fewest keys.
Replicated for availability
Each shard keeps replicas so a node failure doesn't cold-start that slice of the cache; the same replication also lets reads of a hot key spread across copies.
Near cache (L1 + L2)
A small in-process cache sits in front of the distributed cache: the local copy answers the hottest reads, and the shared tier backs everything else — trading a little cross-instance staleness for fewer network hops.
Strategy on top
The distributed cache is just the store; how reads and writes flow through it is a separate choice — cache-aside (app-managed) is the default, read-through / write-through move that logic into the cache layer.

Trade-offs

Pros

  • One shared view: every application instance sees the same entries, so they don't diverge or duplicate memory.
  • Outlives the app: the cache survives instance restarts and deploys, so a rollout doesn't cold-start it.
  • Scales independently: cache capacity and throughput grow by scaling the cache tier, not the app.
  • Holds far more than one process's heap, and can be sized and tuned as its own component.

Cons

  • Every hit pays a network round trip — slower than an in-process cache that has no hop at all.
  • It's another component to run, monitor, secure, and keep available.
  • A single very popular key still lands on one node, so it can hot-spot even though the cluster looks healthy.
  • Values must be serialized and deserialized across the wire, adding CPU and latency per operation.
  • The tier is a remote dependency on the read path, so every caller needs a route that still answers from the source of truth when the cache is slow or unreachable.

When to use it

Reach for it when

  • Multiple application instances need to share one consistent cache instead of each keeping its own.
  • The cache must outlive individual processes — surviving restarts, deploys, and autoscaling.
  • The working set is larger than any single process can comfortably hold in memory.
  • You want to scale cache capacity or throughput independently of the application tier.

Avoid when

  • A single instance serves the traffic, or the data is tiny and read on every request — an in-process cache is faster and simpler.
  • You need sub-millisecond reads and can't afford the network hop.
  • The data is so cheap to recompute that running a whole cache tier isn't worth the operational cost.

Code sketch

TypeScript — cache-aside over a shared cache client, reachable by every instance 
// `cache` is a client to a shared tier (e.g. Redis) that every
// app instance connects to — so they all read and write one view.
async function getUser(id: string): Promise<User> {
  const key = `user:${id}`;

  const hit = await cache.get(key);            // network hop to the shared cache
  if (hit) return JSON.parse(hit);

  const user = await db.users.findById(id);    // miss → source of truth
  await cache.set(key, JSON.stringify(user), { ttlSeconds: 300 });
  return user;
}

In production

Tuning knobs

  • Per-key TTL & eviction policy — How long entries live and what is dropped at capacity — LRU/LFU/FIFO (e.g. a maxmemory-policy like allkeys-lru)
  • Max memory per node — The per-node memory ceiling at which eviction begins (e.g. Redis maxmemory)
  • Shard count & key routing — How many nodes and how keys map to them — consistent hashing or a fixed slot map (Redis Cluster uses 16,384 hash slots)
  • Replication mode — Async primary-to-replica, or a synchronous acknowledgement (Redis WAIT) for stronger durability at higher latency
  • Connection pool size — Client connections held per node, so a burst does not exhaust the server connection budget

Signals to watch

  • Hit rate — Fraction of reads served from cache — the number that justifies the cache existing at all
  • Per-node request skew — Requests per second per node; a spike concentrated on one node is a hot key forming
  • Memory used vs max & eviction rate — How close each node is to its ceiling and how fast it evicts — rising evictions mean the working set no longer fits
  • p99 read latency — Tail latency of a cache read; a cache slow at the tail is buying little

Failure modes under load

  • Node loss under async replication — A node dying before its writes replicate loses those entries, and the load lands on the origin
  • Hot key overloads one node — A single popular key sends all of its traffic to one node regardless of cluster size
  • Stampede on synchronized expiry — Many keys expiring at the same instant send a herd of misses to the origin at once
  • Cold cache after restart — A restarted or newly added node serves nothing until it warms, so the origin absorbs the miss storm

Readiness checklist

  • Set a max-memory ceiling and an eviction policy so a node degrades gracefully instead of running out of memory
  • Route keys with consistent hashing or a managed slot map so adding a node reshuffles few keys
  • Replicate each shard and enable automatic failover so losing a node does not drop a whole slice
  • Mitigate hot keys with a local in-process cache, key replication, or request coalescing
  • Add jitter to TTLs and coalesce concurrent misses to avoid a synchronized stampede on the origin
  • Size connection pools so a traffic burst cannot exhaust a node connections
