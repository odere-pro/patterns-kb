Lens · Caching

Refresh-Ahead

Before a hot key's TTL runs out, a background reload fetches its value from the source and swaps it in — so the entry never actually goes stale under load, and no reader ever pays for the refresh.

Caching Lens

What it is

A refresh-ahead cache watches the remaining time-to-live on an entry and, once it drops below a threshold, reloads the value from the source in the background — before the entry ever actually expires. The trigger can be a scheduled timer per key or a read that happens to land inside that threshold window; either way, the old value keeps serving requests until the fresh one comes back, then gets swapped in with a new TTL. No caller sees a miss for a key this is applied to.

The force it resolves is the cost concentrated at expiry. Under a plain TTL, the busiest keys expire at the worst possible moment — under load — and the very next reader pays a synchronous fetch from the source right as many other readers are arriving for that same now-expired key: a cache stampede, dozens or thousands of requests missing at once and hammering the backing store together. Refresh-ahead moves the reload earlier and off the request path entirely, so the hottest keys are the ones least likely to ever be seen expired.

That protection is deliberately narrow. Refreshing every key ahead of expiry regardless of traffic would waste load on entries nobody's asking for anymore, so refresh-ahead is usually gated by access frequency — only genuinely hot keys earn a proactive reload. It's less a standalone caching strategy than an enhancement bolted onto an existing read-through or cache-aside layer: the same load-and-populate path, just preempted by a background trigger instead of waiting for a miss.

Explained at three levels

Basic

A saved copy of an answer is thrown away after a few minutes. The moment it goes, the next person to ask has to wait for the slow original — and on a busy page that is not one person waiting, it is every reader who arrives in that same second, all asking the slow source at once. So fetch a new copy in the background shortly before the old one is due to go, and keep serving the old one until the new one lands. Like a shop restocking a popular item before the shelf is empty: nobody sees a gap, though the shop sometimes restocks something that has quietly stopped selling.

Advanced

The trigger is a remaining-lifetime threshold: once an entry's time-to-live drops below a set fraction of the original — commonly the last 10-20% — a read returns the current value and schedules the reload asynchronously, and the fresh value replaces the entry with a full TTL. Two trigger shapes differ mechanically. A read-driven threshold spends nothing on keys nobody reads, but cannot preempt a key whose traffic pauses across the window; a per-key or per-shard timer refreshes on a fixed cadence whatever the traffic, and pays for every key it tracks. Either shape needs an access-frequency gate to decide which keys qualify, and a single-flight latch so one hot key cannot launch several overlapping reloads. It layers on an existing read-through or cache-aside load path rather than replacing it, and a key that cools off just expires the ordinary way.

Expert

Reach for it when hotness is cheap to identify and expiry itself is what you are paying for — the synchronous refill plus the herd that arrives with it. Skip it when traffic per key is sparse, because every proactive reload then buys data nobody reads. Three costs come with it, each with a counter-move. Keys written in the same instant cross the threshold in the same instant, so their reloads burst the source — the stampede you were avoiding — and jitter on the refresh lead time is what pays that back. One hot key read repeatedly inside the window launches duplicate reloads; single-flight per key settles it. A reload that keeps erroring leaves an old value serving with every appearance of freshness, so alert on refresh failure rate and served-value age rather than hit rate, which sits at 100% while the data rots. Then run the loop: tune the threshold and the hot-key gate, watch refresh rate against read rate, expect wasted reloads on cooling keys to break first, and gate on the base TTL still expiring keys that stop being read.

How it works

Variations

Layered on Read-Through
The common form: reuse a read-through cache's existing load path, but trigger it from a background check instead of waiting for a miss to happen.
Threshold-triggered refresh
A read that lands once remaining TTL falls below a percentage of the original — say 10-20% — kicks off an async reload; the read itself is never blocked by it.
Scheduled background refresh
A per-key or per-shard timer reloads on a fixed cadence independent of traffic, so a key never goes stale even if it briefly stops being read.
Hot-key gating
Refresh only keys whose access frequency crosses a threshold; refreshing every entry blanket-style wastes load on data nobody's reading anymore.

Trade-offs

Pros

  • Busy keys effectively never expire under load — readers get a fresh value without ever paying for the reload.
  • Eliminates the cache stampede a hot key's expiry would otherwise cause at the worst possible moment.
  • Reload latency happens off the request path, so a slow source never shows up as user-facing latency.
  • Falls back to a plain TTL for free — a key that cools off just expires normally, no extra teardown needed.

Cons

  • Proactive reloads do real work, sometimes wasted — a key refreshed once then never read again cost a load for nothing.
  • Needs bookkeeping a plain cache doesn't have: which keys are hot, and how much TTL each has left.
  • A reload that keeps failing can leave the cache serving old data that looks perfectly fresh, unless failures are surfaced.
  • Threshold and hotness cutoffs are tuning knobs, not defaults that suit every workload.

When to use it

Reach for it when

  • A known set of keys is read constantly enough that an expiry-triggered miss would be visible latency or a stampede risk.
  • The source absorbs a steady trickle of proactive reloads more easily than a burst of simultaneous misses at expiry.
  • You can identify "hot" cheaply enough to gate refreshes to the keys that are actually worth it.

Avoid when

  • Traffic per key is sparse or unpredictable — most proactive reloads would refresh data no one is about to read; plain Read-Through is enough.
  • Data changes rarely and the existing TTL is already generous relative to load on the source.
  • A brief staleness window during the reload is unacceptable — the old value keeps serving until the new one lands.

Code sketch

TypeScript — a minimal refresh-ahead cache 
interface Entry<V> { value: V; ttlMs: number; expiresAt: number; }

class RefreshAheadCache<K, V> {
  private store = new Map<K, Entry<V>>();
  private inFlight = new Set<K>();

  constructor(
    private readonly load: (key: K) => Promise<V>,
    private readonly ttlMs = 60_000,
    private readonly refreshBelow = 0.2, // reload once 20% of TTL remains
  ) {}

  async get(key: K): Promise<V> {
    const entry = this.store.get(key);
    if (!entry) return this.populate(key);        // cold miss, must block

    if (entry.expiresAt - Date.now() < entry.ttlMs * this.refreshBelow) {
      this.refresh(key);                          // fire-and-forget
    }
    return entry.value;                           // always served from cache
  }

  private async populate(key: K): Promise<V> {
    const value = await this.load(key);
    this.store.set(key, { value, ttlMs: this.ttlMs, expiresAt: Date.now() + this.ttlMs });
    return value;
  }

  private refresh(key: K): void {
    if (this.inFlight.has(key)) return;            // single-flight, no dupes
    this.inFlight.add(key);
    this.populate(key).finally(() => this.inFlight.delete(key));
  }
}

In production

Tuning knobs

  • Refresh threshold — The remaining-TTL fraction (or absolute lead time) at which an accessed entry triggers a background reload; Caffeine's refreshAfterWrite and Coherence's refresh-ahead-factor set this.
  • Base TTL / expiry — The full lifetime that refresh-ahead only preempts; a key that stops being read still expires normally once its TTL runs out.
  • Hot-key gate — The access-frequency cutoff that decides which keys earn a proactive reload; refreshing every key blanket-style wastes load on data nobody is reading.
  • Refresh single-flight — Whether a key already refreshing suppresses a second trigger, so one hot key can't launch several overlapping reloads.

Signals to watch

  • Proactive refresh rate — Background reloads per second; if it dwarfs actual reads, the hot-key gate is too loose and load is being wasted.
  • Refresh failure rate — Background reloads that error; these are dangerous because a failed refresh can leave a stale value serving as if fresh.
  • Served-value age — How old the currently-served value is relative to its TTL; a rising age despite refreshes hints they are failing or lagging.
  • Residual miss rate on hot keys — Misses that still reach the blocking load path for keys meant to be hot; a nonzero rate means the threshold is too tight to preempt expiry.

Failure modes under load

  • Silent staleness on repeated refresh failure — A reload that keeps failing leaves the old value serving with the look of freshness; unless refresh errors are surfaced it goes unnoticed.
  • Wasted reloads on cooling keys — A key refreshed once then never read again cost a load for nothing; a loose hot-key gate multiplies this across the keyspace.
  • Refresh storm on the source — If many hot keys cross the threshold together — say all written at the same instant — their background reloads can burst the source, the very stampede refresh-ahead was meant to avoid.
  • Overlapping reloads for one key — Without single-flight, a hot key read repeatedly inside the threshold window can launch several concurrent reloads, multiplying source load.

Readiness checklist

  • Refreshes are gated to genuinely hot keys, not applied blanket across the keyspace
  • A refresh already in flight for a key suppresses duplicate reloads (single-flight)
  • Refresh failures are surfaced so a stale value can't serve indefinitely looking fresh
  • The base TTL still expires cooled-off keys so hot-key bookkeeping doesn't grow unbounded
  • Refresh triggers are jittered so many hot keys don't reload the source in the same instant
