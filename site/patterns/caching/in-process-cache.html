In-Process Cache

Keeps cached data inside the application process's own memory, so a hit needs no network hop at all — the fastest cache there is — at the cost of each instance holding its own, potentially divergent, copy.

Caching

What it is

An in-process cache keeps cached values in the application's own memory — a map, or a small library-managed cache, living inside the same process that serves requests. A hit is a plain memory lookup: no network call, no serialization, just a reference already sitting in the same address space. It's the fastest kind of cache by a wide margin, because it removes the one cost even a distributed cache can't avoid — the round trip to reach it.

The force it resolves is latency on the hottest, smallest data. Modern app servers run on machines with plenty of memory, and some data — configuration, feature flags, a small lookup table — is read on nearly every request and changes rarely. Paying a network hop to a shared cache for that on every request is pure overhead. The catch is the flip side of "in the process": each instance has its own copy, so caches on different instances can diverge, and the same data is duplicated across the fleet. That makes it a targeted optimization, not the default — and a natural front layer (an L1) in front of a shared cache for the very hottest keys.

Explained at three levels

Basic

Every request needs the same handful of settings, and the program fetches them from another machine each time. That fetch takes longer than the work the request came to do. Keep the settings in the program's own memory instead and reading them costs almost nothing — like keeping a pen on your desk rather than walking to the supply cupboard. The catch: every copy of the program keeps its own pen, so when someone changes a setting the copies disagree until each one goes back for a fresh look.

Advanced

The values sit on the application's own heap — a plain map, or a library such as Caffeine, Guava Cache or Ehcache — so a hit is a reference lookup with no hop and no serialization, and the bounds are ones the process enforces itself: a maximum entry count or weight, an eviction policy, and a time-to-live. That TTL is the only invalidation you get for free, and it sets the width of the disagreement window — a 30-second expiry means two instances can answer differently for up to 30 seconds. Narrowing it further is machinery you build: a write publishes an invalidation over a pub/sub channel and every instance applies it to its own copy. The usual deployment is not standalone but an L1 in front of a shared tier, absorbing the hottest keys locally and deferring the rest.

Expert

Choose it for small, hot, read-mostly data — configuration, feature flags, a lookup table — where even a shared cache's round trip dominates the request, or as an L1 that absorbs a hot key before it concentrates on one node of the shared tier. Three costs come with it, each with a counter-move. There is no single copy to update, so instances diverge until expiry: price the disagreement window, set the TTL to match it, and if the price is too high keep the data in the shared tier rather than operating a broadcast invalidation of your own. Every instance pays for the working set again, so memory cost scales with instance count rather than with the data — bound each cache by size or weight and keep local only what is genuinely hot. A rolling deploy empties every copy at once and the source sees a miss storm shaped exactly like the rollout, so stagger restarts and coalesce concurrent misses in the process. Then run the loop: tune the bound and the expiry, watch hit ratio against heap occupancy, expect an unbounded map to break first as collector thrash, and gate on every cache carrying a size bound and an expiry before it ships.

How it works

Variations

Bounded with eviction
A size cap plus an eviction policy (usually LRU) keeps the cache from growing without bound and consuming the process's heap — the common form for anything but a tiny fixed table.
TTL-based expiry
Each entry expires after a set time so the local copy can't drift too far from the source; the shorter the TTL, the narrower the cross-instance inconsistency window.
Near cache (L1 in front of L2)
The in-process cache fronts a shared distributed cache: it absorbs the hottest reads locally and defers everything else to the shared tier, cutting network hops for the keys that matter most.
Invalidation by broadcast
To fight divergence, a write publishes an invalidation (e.g. over a pub/sub channel) that every instance listens for and applies to its local copy — buying tighter consistency at the cost of more moving parts.
Server-assisted invalidation
Let the data store drive it instead of building the fan-out yourself. The server remembers which keys each connected client has read and sends an invalidation only to the clients holding a copy, so a write is not shouted at every instance in the fleet — Redis ships this as client-side caching with tracking. The server pays for it in memory, one set of remembered keys per client, which is why a broadcast mode exists alongside it for when that ledger costs more than the wasted messages did.

Trade-offs

Pros

  • The fastest cache possible: a hit is an in-memory lookup with no network hop and no serialization.
  • No extra infrastructure — it's a library or a plain map, with nothing new to deploy or operate.
  • No shared-cache dependency in the read path, so it keeps working even if the shared tier is down.
  • An effective L1 in front of a shared cache, soaking up the hottest keys before they leave the process.

Cons

  • Each instance has its own copy, so instances can serve different values for the same key.
  • The same data is duplicated across every instance, wasting memory at scale.
  • It starts cold on every restart or newly-scaled instance, so a deploy re-warms from scratch.
  • Invalidating a change across all instances is genuinely hard — there's no single copy to update.

When to use it

Reach for it when

  • Small, hot, read-mostly data — config, feature flags, a lookup table — is needed on nearly every request.
  • You need the lowest latency possible and can't spare even a shared-cache network hop.
  • You want an L1 in front of a distributed cache to shield the hottest keys from the network.

Avoid when

  • The data changes often and must read consistently across all instances — divergence will bite.
  • The working set is large; duplicating it in every instance wastes memory a shared cache would pool.
  • You run many instances and the memory duplication outweighs the latency you'd save.

Code sketch

TypeScript — a bounded-by-TTL cache living in the process's own memory 
// A plain Map in the app's own memory — no network hop on a hit.
// Each instance holds its own copy, so entries can diverge across the fleet.
type Entry<V> = { value: V; expiresAt: number };
const store = new Map<string, Entry<unknown>>();

function get<V>(key: string): V | undefined {
  const e = store.get(key);
  if (!e) return undefined;
  if (Date.now() > e.expiresAt) { store.delete(key); return undefined; }  // TTL expiry
  return e.value as V;
}

function set<V>(key: string, value: V, ttlMs: number): void {
  store.set(key, { value, expiresAt: Date.now() + ttlMs });
}

In production

Tuning knobs

  • Maximum size or weight — The entry count, or weighted capacity, at which eviction begins — maximumSize and maximumWeight in Caffeine and Guava Cache
  • Expiry policy — Time-to-live measured after write or after last access: expireAfterWrite bounds how stale a value can get, expireAfterAccess reclaims memory held by keys nobody reads any more
  • Eviction algorithm — What is dropped at capacity — least-recently-used, least-frequently-used, or the W-TinyLFU admission policy Caffeine uses
  • Background refresh window — Whether an ageing entry is reloaded asynchronously on access instead of being evicted and reloaded synchronously — refreshAfterWrite in Caffeine and Guava Cache
  • Share of the heap budgeted to the cache — How much process memory the cache may hold before it competes with request handling and pushes the collector

Signals to watch

  • Hit ratio — Share of lookups served without a load; below the level that justifies the memory it occupies, the cache is pure overhead
  • Eviction rate — How fast entries are dropped at capacity — a climbing rate means the working set no longer fits the bound you set
  • Load latency and concurrent loads — How long a miss takes and how many loads run at once, which is what a miss actually costs a request
  • Heap occupancy and collector pressure — Memory held by cached objects and the collection time attributable to it; an over-large cache shows up as garbage collection before it shows up as a cache problem

Failure modes under load

  • Instances answer the same question differently — With no shared copy, one instance picks up a change while the others keep serving their own entry until it expires
  • Fleet-wide cold start on deploy — A rolling restart empties every cache at once, so the source sees a miss storm shaped exactly like the rollout
  • Unbounded growth exhausts the heap — A cache with no size bound behaves as a memory leak and surfaces as collector thrash or an out-of-memory failure
  • The working set is paid for once per instance — Every instance holds the same entries, so memory cost scales with instance count rather than with the data
  • Concurrent misses each start their own load — Without coalescing, several threads missing on the same key at the same moment all load it independently

Readiness checklist

  • Bound every cache by size or weight — an unbounded map is a leak, not a cache
  • Set an expiry that matches how stale the value may safely be, since expiry is the only invalidation you get for free
  • Coalesce concurrent misses so one load serves every waiter in the process
  • Decide what a divergent read costs before caching anything that changes; if it matters, keep the data in the shared tier
  • Export hit ratio, eviction count and load latency — an unmeasured local cache hides both its value and its staleness
  • Stagger restarts so the whole fleet does not cold-start onto the source at the same moment
