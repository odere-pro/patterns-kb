Atomic Design

A design-system methodology that composes interfaces from the smallest reusable pieces — atoms into molecules into organisms into templates and pages — so the whole UI is built from one shared, consistent vocabulary.

Frontend

What it is

Left unmanaged, a UI drifts. Buttons and inputs get rebuilt slightly differently on every screen, designers and engineers name the same thing with different words, and nothing is a shared building block — so consistency is a matter of vigilance rather than structure.

Atomic Design imposes a compositional hierarchy on the design system, borrowing its metaphor from chemistry. The smallest indivisible pieces are atoms — a button, an input, a label. Atoms combine into molecules — a search bar is an input plus a button. Molecules assemble into organisms — a site header. Organisms lay out into templates, and templates filled with real content become pages.

The ladder is a way of seeing a UI at both scales at once — the parts and the whole — rather than a build order you walk in one direction. A tier draws on any tier below it, so an organism may hold molecules, loose atoms or other organisms, and a template places organisms and molecules side by side.

Because every screen is assembled from the same lower tiers, the whole interface speaks one vocabulary, and a change to an atom ripples consistently everywhere it appears.

Explained at three levels

Basic

Build every screen out of the same small parts. Start with the tiniest pieces — a button, a text box, a label — combine those into slightly bigger pieces like a search bar, and combine those into whole sections and then pages. Nothing on a screen is drawn from scratch, the way nothing in a Lego model is a custom-moulded brick. Change the smallest piece once and every screen that uses it changes with it, so the interface stays consistent because of how it is built rather than because someone remembered to check.

Advanced

The rule that makes the hierarchy hold is directional: a tier draws on tiers at or below its own, an organism nesting another organism included, but never on one above it. That keeps the dependency graph acyclic, so the blast radius of a change is exactly the tiers above the one you touched and a review can stop there. The template/page split earns its own keep — a template is the layout with placeholder content and a page is that template with real content, so layout breakage and content-length breakage surface as two separate tests. The component library and the shared vocabulary then become one artefact: design and engineering name a thing the same way because they point at the same file.

Expert

Choose it when more than one team ships into the same interface — that is where a shared vocabulary repays its cost, and a single-team product never amortizes the tiering. Pay the two bills rather than arguing them. Tier boundaries are genuinely ambiguous, so settle them by rule instead of by meeting: whatever owns state or fetches data is an organism, whatever is presentational and indivisible is an atom, and anything still contested is filed one tier down. Categorizing also crowds out shipping, so bound it — admit a component at whatever tier its first caller needs, and let a real second use, not a taxonomy debate, promote it.

How it works

Variations

Strict five-tier
The full atoms / molecules / organisms / templates / pages hierarchy, applied literally. Most explicit, but invites debate about which tier a given component belongs to.
Pragmatic component-library tiering
A looser grouping — primitives / components / patterns — that keeps the compositional spirit without arguing over five exact labels. Common in real design systems.
Design-token layer underneath the atoms
Adds a tier below atoms: named values for color, spacing, and type. Atoms consume tokens, so a single source of truth drives styling all the way up the hierarchy.

Trade-offs

Pros

  • Visual and behavioral consistency — every screen resolves down to the same building blocks.
  • Reuse of components rather than rebuilding the same widget on each page.
  • A shared language between design and engineering, and one that scales a design system across teams.

Cons

  • Taxonomy debates — is this a molecule or an organism? — that consume time without shipping anything.
  • Overhead that a small app with few screens will never recoup.
  • Categorizing can become a distraction from actually shipping the interface.

When to use it

Reach for it when

  • You are building or maintaining a design system across many screens or teams.
  • You need a shared component vocabulary that design and engineering both use.

Avoid when

  • It is a small app with few screens that will not amortize the structure.
  • The tier debate would cost more than the consistency it buys.

Code sketch

TypeScript / JSX — atoms compose into a molecule, then an organism 
// Atoms: the smallest indivisible building blocks.
const Button = ({ label }: { label: string }) => <button>{label}</button>;
const Input = ({ placeholder }: { placeholder: string }) =>
  <input placeholder={placeholder} />;

// Molecule: atoms combined into a small, reusable unit.
const SearchBar = () => (
  <div className="search-bar">
    <Input placeholder="Search…" />
    <Button label="Go" />
  </div>
);

// Organism: molecules and atoms assembled into a section of the page.
const Header = () => (
  <header>
    <h1>Acme</h1>
    <SearchBar />
  </header>
);
