Architecture

MVC

Splits an interactive application into a model that owns state and behavior, a view that renders it, and a controller that turns user input into changes to the model — so each piece changes without dragging the others with it.

Architecture

What it is

MVC divides an interactive application into three collaborating parts. The model owns application state and the rules for changing it, and knows nothing about how it's displayed. The view renders a representation of the model and forwards raw user input onward. The controller interprets that input, decides what it means, and updates the model accordingly. When the model changes, the view is told to refresh — directly, or by observing the model — so it never goes stale.

The force it resolves is tangled responsibilities. Three unrelated reasons to change — a rule changed, a layout changed, an input gesture changed — otherwise land on the same file, and its owner becomes whoever edited it last. Give each reason its own home and each one gets an owner who can act alone: a designer reworks the view without opening code that decides money, and a rule moves without a single template being touched.

Trygve Reenskaug devised the pattern at Xerox PARC in the late 1970s, on Smalltalk-79. The widely copied form is the later Smalltalk-80 one, where model and view were wired with a live observer link: the model notified its views the instant its state changed, and the UI updated in place. Web frameworks reshaped this into a request/response cycle — a controller handles one HTTP request, updates the model, and picks a view to render the response — trading the constant live push for a stateless round trip.

That reshaping is also where the pattern strains. A view that must know the model's shape in detail turns brittle — rename one field and every template that reads it breaks — and a controller with no live link to the model starts hoarding view state between requests to compensate. MVP and MVVM exist because those two seams, the controller's role and how the view learns of change, are exactly where implementations diverge.

Explained at three levels

Basic

Put the drawing, the rules and the click handling in one class and every change turns risky: restyling a button means opening the file that decides whether a discount applies, and you cannot check the discount without launching a window. Split the work three ways instead — one part holds the data and the rules for changing it, one part draws it, one part reads what the user did and asks the first part to change. It works like a scoreboard at a game: the score book holds the truth, the big board only shows it, and an operator works the buttons. Change the book and the board redraws.

Advanced

The dependency runs one way. The view and the controller both know the model; the model knows neither, and announces that it changed without naming who is listening — an Observer underneath. That is what lets one model feed several views at once, a page and an export and an API response, from rules written down once. Keep the controller a stateless translator: it turns a gesture into one call on the model and nothing else, so anything it would have remembered lives in the model instead, where a test can reach it without a screen.

Expert

Choose it when domain logic is worth testing without a UI, or when one body of state must drive several presentations; the practical draw is a vocabulary nearly every framework already ships. That ubiquity is the trap — each framework redraws the controller's edge, so naming the pattern settles nothing. Write down where input interpretation ends and view logic begins before the first controller exists, because unpinned it absorbs both and becomes the god object the split was meant to prevent; the counter-move is to push rules down into the model and formatting up into the view, not to cut the controller in half. Where the view must be fully passive and unit-tested through an interface, take MVP; where a binding engine already exists, take MVVM and let it own the change notification that classic MVC makes you wire by hand.

How it works

Variations

Classic (Smalltalk-80) MVC
Model and view are wired through a live observer link — the model pushes change notifications straight into every view watching it, in-process and in real time.
MVP
Swaps the controller for a presenter that owns all presentation logic; the view becomes passive, exposing only simple getters and setters the presenter drives.
MVVM
Introduces a view-model that exposes bindable, observable state; the view declares bindings instead of being pushed to or pulled from imperatively.
Request-response (web) MVC
Each HTTP request is one pass through the triad — controller updates the model, then renders a template — with no persistent live link between model and view.
Hierarchical MVC (HMVC)
Nests whole MVC triads inside one another so independent sub-UIs (a widget, a panel) each keep their own model, view, and controller.

Trade-offs

Pros

  • Domain logic in the model is testable without touching any UI.
  • The same model can back multiple views — a page, a widget, an export.
  • Designers and front-end code can change the view without risking business rules.
  • A well-understood vocabulary — most teams and frameworks already speak it.

Cons

  • The controller easily absorbs logic that belongs in the model or the view, and swells.
  • The boundary between view and controller is genuinely fuzzy and gets drawn differently by every team.
  • Live model-to-view notification needs its own wiring — usually another pattern (Observer) underneath.
  • Web frameworks bend the names to fit request/response, so "MVC" means something different in each one.

When to use it

Reach for it when

  • The application has real domain logic worth testing independently of the UI.
  • More than one presentation must show the same underlying state.
  • Input handling, business rules, and rendering are already tangled and need separating.

Avoid when

  • The UI is trivial — a static page or a single form doesn't need three layers.
  • Your framework's binding story fits MVVM far better than a hand-rolled controller.
  • You need the view fully passive and unit-testable in isolation — that's MVP's job.

Code sketch

TypeScript — a minimal triad 
interface State { count: number; }
type Action = "increment" | "reset";

class Model {
  private state: State = { count: 0 };
  private listeners = new Set<(s: State) => void>();

  get(): State { return this.state; }
  set(next: State) {
    this.state = next;
    for (const fn of this.listeners) fn(next);
  }
  onChange(fn: (s: State) => void) { this.listeners.add(fn); }
}

class Controller {
  constructor(private model: Model) {}
  handle(action: Action) {
    const s = this.model.get();
    if (action === "increment") this.model.set({ count: s.count + 1 });
    if (action === "reset") this.model.set({ count: 0 });
  }
}

// View renders on every model change; controller owns input handling.
const model = new Model();
const view = { render: (s: State) => console.log(`count: ${s.count}`) };
model.onChange((s) => view.render(s));

const controller = new Controller(model);
controller.handle("increment"); // view logs "count: 1"

In the wild

Ruby on RailsRails wires the triad by convention: ActiveRecord models map classes to tables, ActionController actions handle each request, and ActionView renders ERB templates; the router maps a URL to a controller action, so most of the wiring is supplied rather than written.
DjangoDjango calls its triad model-template-view: a URLconf dispatches each request to a view function (the controller role), which queries ORM models and renders a template.
Spring MVCA single front controller, the DispatcherServlet, routes each request to an @Controller handler that populates a Model and returns a logical view name, which a ViewResolver maps to a template such as Thymeleaf or JSP.
