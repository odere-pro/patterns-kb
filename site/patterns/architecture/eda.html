Architecture

Event-Driven Architecture

Components communicate by producing and reacting to events — facts about something that already happened — instead of calling each other directly, so publishers and subscribers can be built, deployed, and scaled independently.

Architecture

What it is

In an event-driven architecture, components emit events — immutable records that something happened, like OrderPlaced or PaymentCaptured — without knowing or caring who, if anyone, reacts. Interested components subscribe to the event types they care about and react asynchronously, whenever the event reaches them. No producer ever calls a consumer's method; it only asserts a fact into the world.

The force it resolves is coupling through synchronous calls. A service that invokes its collaborators directly must know their addresses, their interfaces, and be available to wait for their replies — one slow or failing dependent stalls the caller, and adding a new consumer means changing the producer's code. Events invert that: the producer publishes once, and zero, one, or a hundred consumers may react, today or after the producer has moved on.

Each decoupling is a concrete permission, and it is worth naming them separately. In time: producer and consumer never have to run at the same moment, so a nightly batch job can serve a producer that publishes all day. In space: the producer's configuration names a topic, not a hostname, so consumers move, multiply, or disappear with no redeploy on the other side. In behaviour: the published contract is the event's shape, so a consumer can change what it does with an OrderPlaced without asking the team that raised it.

The freedom has an owner-shaped cost. In a direct call the caller owns the outcome of the whole sequence; with events nobody does — each handler owns only its own reaction, so "was this order fully processed" stops being a return value and becomes a question you answer by inspecting several systems. Event-driven architecture trades dictating what happens next for reacting to what already happened, and you build the accounting for that trade yourself.

Explained at three levels

Basic

Checkout has to charge the card, email a receipt, tell the warehouse and update a dashboard. Written as four calls in a row, checkout waits for all four: the day the email service is slow the customer stares at a spinner, and the day someone wants a fifth reaction, someone edits checkout. Have checkout pin a note to a board instead — "order 42 was placed" — and go back to work. Each team watches the board and reacts on its own clock, so a listener that is asleep delays nobody, and a new listener starts watching without anyone touching checkout.

Advanced

The board is a broker, and its job is to be a durable buffer with independent read positions. The producer's write completes when the broker acknowledges the event, not when anyone processes it, and each subscriber group tracks its own position in the stream — so a consumer down for an hour resumes where it stopped, and a brand-new consumer can start from the beginning of whatever is still retained. Delivery is at-least-once and ordered only within one partition or key, which is not a detail you can paper over: every handler must be idempotent, and any handler that assumes it saw the previous event will eventually be wrong. What the broker does not solve is the producer's own dual write — committing the row and publishing the event are two operations, and either can succeed alone.

Expert

Justify it per boundary, not per system. Across independently owned services reacting to the same facts it is what lets teams ship without coordinating releases; inside one team's synchronous workflow it trades a readable stack trace for distributed debugging and buys nothing. Most of the bill has a named counter-move. The dual write is closed by a transactional outbox, so the event ships from the same commit as the row. Duplicates are closed by a dedup key the consumer commits with its own write, which is cheaper and more honest than any exactly-once claim. The lost call stack is closed by a correlation id carried on every event and traced on — decided before the first consumer ships, because backfilling it across a live fleet is not a sprint. What has no cheap counter-move is eventual consistency: a consumer's view is always behind, so a rule that needs an immediate consistent answer stays on a synchronous path. Then run the loop — size partitions and retention, watch lag, expect a poison message to stall a partition first, and gate the launch on idempotent consumers behind a dead-letter queue.

How it works

Variations

Choreography vs. orchestration
In choreography every service reacts to events on its own, with no central controller. In orchestration a coordinator — often a saga — tells each participant what to do next. Pure EDA favors choreography; orchestration returns when a business process needs an explicit, auditable sequence.
Event notification vs. event-carried state transfer
A thin event says only "this changed, go fetch details," forcing consumers to call back for the rest. A fat event carries the full new state so consumers never need to. Fatter events cut coupling further but risk staleness and duplicated data across services.
Domain Event vocabulary
The events themselves are named and shaped as business facts, not technical deltas — OrderPlaced, not RowUpdated. This is the vocabulary EDA is built out of.
Publish-Subscribe transport
The wiring mechanism underneath: producers publish to a topic, consumers subscribe to it, and a broker handles fan-out, buffering, and delivery — Kafka, SNS/SQS, RabbitMQ, EventBridge.
Event Sourcing persistence
Instead of just reacting to events in flight, the event stream itself becomes the system of record — current state is derived by replaying it. A natural, but optional, pairing with EDA.
Push subscription vs. durable log
A push broker tracks subscriptions and delivers each event to each subscriber, then forgets it — a consumer that was not subscribed when the event fired never sees it. A durable log instead appends events in order and keeps them; consumers hold their own read position and can rewind. Replay is the whole difference, and it decides what a consumer outage costs you: with a push broker, events missed during the outage are gone, while a log lets the consumer resume where it stopped, and lets a new consumer read history it was never present for. Replay is also how you reprocess after fixing a bug in a consumer.
How much the consumer has to remember
Consumers sit on a ladder of increasing state. The simplest reacts to one event and acts. The next correlates a few events by identifier and keeps what it learned from the earlier ones. Above that, a consumer looks for patterns across a series — a moving average over a time window crossing a threshold. At the top, a stream processor transforms the whole flow for a downstream subsystem. Each rung costs more state to hold and more care when an instance dies mid-window.
Who owns a multi-step flow
Choosing between the two above decides more than who picks the next step: it decides who holds the flow's state. Under choreography nobody does, so there is nothing to ask where an order stopped and nothing to restart — a broken sequence is found by reconciliation rather than by an alert, which is why this arrangement is the usual source of quiet inconsistency. A coordinator holds that state and can retry or compensate from it, and in exchange becomes a component whose own outage stops every flow passing through it.

Trade-offs

Pros

  • Producers and consumers are decoupled in time, space, and identity — add a reaction without touching the source.
  • Consumers scale, deploy, and fail independently of the producer and of each other.
  • Naturally resilient to partial outages: a down consumer doesn't block the producer, and queued events catch it up later.
  • Models the domain as a stream of things that happened, which often matches how the business actually thinks.

Cons

  • Hard to trace: one business flow scatters across independently-deployed handlers with no single call stack.
  • Eventual consistency is pervasive — consumers see stale state, and races between events are subtle.
  • Debugging and testing require standing up or simulating a broker; "where did this event come from" often means grepping logs across services.
  • Needs real operational discipline: schema versioning, idempotent consumers, dead-letter queues, and a plan for duplicate or out-of-order delivery.
  • Open subscription cuts both ways: whatever a producer publishes is readable by everything attached to the channel, including handlers it was never written for, so what goes into the payload is a disclosure decision and not only a schema one.
  • Event granularity has a cost in both directions and no default. Too fine, and the volume saturates the system and makes the overall flow impossible to follow — worst when a change has to be rolled back. Too coarse, and every consumer wakes up for events it does not care about. Calibrate by asking whether a consumer must open the payload to decide how to respond: if a compliance check publishes only Compliant and NonCompliant, subscribers filter by event type instead of by inspection.

When to use it

Reach for it when

  • Multiple, independently-owned parts of the system need to react to the same fact without the producer knowing who they are.
  • Producers and consumers must be deployed, scaled, and evolved on separate schedules.
  • The domain is naturally a stream of things that happened — orders placed, payments captured, inventory changed.

Avoid when

  • A handful of services run one synchronous business transaction and the caller needs an immediate, consistent answer.
  • The team can't yet operate and monitor a broker, retries, and dead-letter handling.
  • There is exactly one consumer that will ever care — a direct call is simpler and easier to trace.

Code sketch

TypeScript — a minimal in-process event bus 
type Events = {
  OrderPlaced: { orderId: string; total: number };
};

class EventBus<E extends Record<string, unknown>> {
  private handlers = new Map<keyof E, Set<(payload: any) => void>>();

  on<K extends keyof E>(type: K, handler: (payload: E[K]) => void): () => void {
    const set = this.handlers.get(type) ?? new Set();
    set.add(handler);
    this.handlers.set(type, set);
    return () => set.delete(handler); // unsubscribe
  }

  emit<K extends keyof E>(type: K, payload: E[K]): void {
    // producer never learns who ran, or how many
    for (const handler of this.handlers.get(type) ?? []) handler(payload);
  }
}

const bus = new EventBus<Events>();
bus.on("OrderPlaced", (e) => chargeCard(e.orderId, e.total));
bus.on("OrderPlaced", (e) => notifyWarehouse(e.orderId));

bus.emit("OrderPlaced", { orderId: "o-42", total: 4999 });

In the wild

Apache KafkaA durable, partitioned commit log where many independent consumer groups read the same stream at their own pace; parallelism is bounded by partition count, ordering is guaranteed only within a partition, and consumers can rewind to any retained offset to replay.
AWS EventBridgeRoutes events from producers to any number of subscribed targets using content-based rule matching, with no producer-side knowledge of consumers; failed deliveries can be retried and sent to a dead-letter queue.
RabbitMQBrokers messages through exchanges that fan a published event out to whatever queues have bound to it by routing key; consumers acknowledge messages and unacked ones are redelivered.

In production

Tuning knobs

  • Partition / consumer-group parallelism — Per-topic throughput is capped by partition count; add partitions and consumers to scale out, at the cost of losing per-key ordering across partitions.
  • Delivery semantics and ack mode — At-least-once vs at-most-once, manual vs automatic acknowledgement. Chooses which side of the duplicate-versus-loss tradeoff the system lives on.
  • Retry policy and dead-letter queue — Max attempts, backoff schedule, and the destination where a message that keeps failing is parked instead of blocking the stream.
  • Event retention — How long the broker keeps events (log retention or queue TTL), which bounds how far a new or lagging consumer can rewind and replay.
  • Consumer prefetch / max in-flight — Number of unacknowledged messages a consumer buffers at once — the dial between throughput and memory pressure per consumer.

Signals to watch

  • Consumer lag — Offset gap between the latest produced event and the last one a consumer group has committed. The single best indicator that consumers are falling behind.
  • Dead-letter queue depth — Count of messages that exhausted their retries. A non-zero and rising DLQ is a stuck workflow, not noise.
  • End-to-end latency — Time from an event being produced to it being processed — the number users actually feel through an event-driven flow.
  • Redelivery / duplicate rate — How often the same message is delivered more than once, which tells you how hard your idempotency layer is working.

Failure modes under load

  • Consumer lag grows unbounded — Producers outpace consumers; the backlog climbs, latency stretches, and if it crosses the retention window unread events are silently dropped.
  • Poison message — A message that always fails cycles through retries, either blocking its partition or flooding the dead-letter queue.
  • Duplicate processing — At-least-once redelivery double-applies side effects — a second charge, a second email — whenever a consumer is not idempotent.
  • Out-of-order delivery — Retries and cross-partition fan-out mean events arrive in a different order than they happened, breaking handlers that assumed sequence.

Readiness checklist

  • Consumers are idempotent — a dedup key or processed-id table makes redelivery a no-op.
  • Every subscription has a dead-letter queue with an alert on its depth.
  • Consumer lag is monitored per group with a threshold that pages before retention is breached.
  • Event schemas are versioned with a compatibility policy, and consumers tolerate unknown fields.
  • Retention is set long enough to survive the longest expected consumer outage or replay.
