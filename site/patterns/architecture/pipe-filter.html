Architecture

Pipe-and-Filter

Data streams through a chain of independent filters, each one consuming, transforming, and re-emitting it before handing the result down the pipe to the next stage.

Architecture

What it is

Pipe-and-Filter decomposes a processing task into a sequence of independent filters, each doing one transformation, connected by pipes that carry data from one filter's output to the next filter's input. A filter knows nothing about where its input came from or where its output goes — it only knows the shape of the data it consumes and produces.

The force it resolves is tangled, monolithic processing logic. Without it, one function parses, validates, transforms and formats in a single body, so a change to the validation rules can only be made by reading and re-testing all of it. The same tangle blocks reuse: the cleanup step two other jobs need cannot be lifted out, so it gets copied, and the copies drift.

The pipe is not incidental plumbing. Because it's the only channel between stages, it decouples their execution: filters can run in the same process one after another, in separate threads passing through queues, or on separate machines passing through sockets or a message broker, without any filter's code changing. That same decoupling is what makes the pattern the backbone of the Unix shell, compilers, and stream-processing frameworks alike.

Explained at three levels

Basic

Think of a job that reads a log file, drops the broken lines, looks up each customer's name, and writes a report. Build it as four small steps in a row: each step takes what the one before it produced, does its own single job, and hands the result on. Fix the lookup, add a step, or reuse one of the four in another job, and nothing else in the line has to change — like swapping one station on a factory line while the rest keeps running.

Advanced

The unit of independence is the contract at the seam: a shape of data in, a shape of data out, nothing shared. Keep each filter stateless per record and its copies become interchangeable, which turns throughput work into finding the slowest stage and running more of that one filter rather than scaling the chain as a unit. Order is what you trade away — parallel copies of a stage finish out of sequence, so either every record carries a key you can re-sort on, or the stage that needs order stays single-threaded and sets the ceiling.

Expert

Choose it when the stages have different lifecycles — different owners, different scaling curves, different reuse — because what you are buying is a pipeline that is configuration rather than code, and rearranging it costs no rewrite. Price it at the seams: each boundary crossed pays serialization and a hop of latency, so an in-process chain and a broker-connected one are different systems wearing the same diagram. Two costs come due later. A fault surfaces stages away from its cause, which you pay off with a correlation id on every record and per-stage metrics, put in before the pipeline grows past three stages. Work needing one atomic transaction or a shared request context has no counter-move here at all — that one is a reason to pick something else.

How it works

Variations

Pull (lazy) pipelines
Each filter is an iterator that only computes its next value when downstream asks for one — memory-cheap, and results start flowing before the whole input is read.
Push (batch) pipelines
Each filter runs to completion over its whole input before handing off the full output. Simpler to reason about, but no result until every stage finishes.
Producer-Consumer staging
Adjacent filters are split across threads or processes, connected by a bounded queue instead of a direct call, so each stage runs at its own pace.
Backpressure-aware filters
A slow filter signals upstream to slow down production instead of letting an unbounded queue build up between stages.

Trade-offs

Pros

  • Filters are small, single-purpose, and independently testable.
  • Pipelines are recomposable — reorder, insert, or drop a stage without rewriting the rest.
  • Independent stages can run concurrently, on separate threads or machines.
  • New behavior often means adding a filter, not editing existing ones.

Cons

  • Serializing and moving data between stages adds latency and overhead.
  • An error deep in the pipeline is harder to trace back to its source stage.
  • State that spans the whole request doesn't fit a model of stateless, local filters.
  • Overall throughput is capped by the slowest filter unless stages are buffered or parallelized.
  • A stage that dies usually takes the whole run with it, and restarting it can redo work already done or hand the next stage a record it has already seen — so filters have to be safe to repeat and the pipe has to drop the repeats.

When to use it

Reach for it when

  • Processing naturally decomposes into a sequence of independent transformations.
  • You want stages that can be reordered, reused, or replaced without touching the others.
  • Stages can usefully run concurrently, or scale independently under load.

Avoid when

  • The steps share complex state or must run as one atomic unit.
  • A single straightforward function is clearer than a pipeline of tiny stages.
  • The overhead of pipes and buffering outweighs the benefit for a small, fixed job.

Code sketch

TypeScript — a pipeline of async generator filters 
type Filter<In, Out> = (input: AsyncIterable<In>) => AsyncIterable<Out>;

async function* source(): AsyncIterable<number> {
  for (let i = 1; i <= 5; i++) yield i;
}

const double: Filter<number, number> = async function* (input) {
  for await (const n of input) yield n * 2;
};

const format: Filter<number, string> = async function* (input) {
  for await (const n of input) yield `value=${n}`;
};

// Filters compose: each only knows its own input/output shape.
async function run() {
  const pipeline = format(double(source()));
  for await (const line of pipeline) console.log(line);
}

In the wild

Unix shell pipesThe shell connects programs with anonymous pipes, a fixed kernel buffer of 64 KB by default on Linux. Stages run concurrently, and when the buffer fills the writer blocks, giving the pipeline natural backpressure for free.
java.util.streamIntermediate map and filter operations are lazy and do nothing until a terminal operation runs; calling parallelStream splits the source and runs the pipeline across the shared ForkJoinPool.commonPool.
GStreamerGStreamer links elements through typed pads into a pipeline; inserting a queue element hands the downstream segment its own thread, and a bus carries state-change and error messages back to the application.

In production

Tuning knobs

  • Inter-stage queue bound — Capacity of the bounded buffer between adjacent filters. Too small starves a fast downstream stage; too large hides backpressure and lets memory balloon.
  • Batch / chunk size — How many records a filter reads or emits per hand-off. Larger batches amortize per-item and serialization overhead; smaller batches cut end-to-end latency.
  • Per-stage parallelism — Number of worker threads or instances running one filter, so a slow stage can be scaled independently of the rest of the pipeline.

Signals to watch

  • Per-stage queue depth — Fill level of each inter-stage buffer. A queue that stays near full marks the stage just downstream as the bottleneck.
  • Per-stage throughput — Records per second each filter completes. The slowest stage sets the ceiling for the whole pipeline.
  • End-to-end latency — Time for one record to traverse every stage; it rises sharply once any upstream queue starts backing up.

Failure modes under load

  • Slowest stage caps throughput — The pipeline runs no faster than its slowest filter; buffers ahead of it fill and stages upstream stall waiting to hand off.
  • Unbounded queue exhausts memory — With no bound and no backpressure, a fast producer ahead of a slow filter grows the connecting buffer until the process runs out of memory.
  • Head-of-line blocking — In an ordered stage, one slow or stuck record blocks every record queued behind it, even ones that could run immediately.

Readiness checklist

  • Every inter-stage queue is bounded, with a defined full policy: block, drop, or spill to disk.
  • The slowest stage is identified and can be parallelized or scaled on its own.
  • Backpressure propagates from the slowest consumer back to the source.
  • A stage failure has a defined outcome (retry, skip, or halt) and the failing record is traceable to its stage.
