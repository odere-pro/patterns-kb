Architecture

CQRS

Splits the model that handles writes from the model that serves reads, so each side can be shaped, scaled, and evolved to fit what it actually does.

Architecture

What it is

CQRS (Command Query Responsibility Segregation) splits the model that changes state from the model that answers questions about it. Nothing requires the two to share a schema, a class, or even a database — only that a change made through one becomes visible through the other. Greg Young named it, and the name is built on the older rule of command-query separation — a method either changes state or reports it, never both — lifted from single methods up to whole models and services.

The force it resolves is one model asked to face two directions, and the damage it takes doing so. Read-only helper fields and report methods accrete onto the class that guards your invariants; the normalisation that keeps writes safe gets relaxed a column at a time to make a screen load. Both jobs end up done badly, and the code nobody dares change is the code enforcing correctness.

It also acknowledges an asymmetry most systems have: reads usually outnumber writes by orders of magnitude, and the two scale under entirely different pressures. Splitting the models means each side can be cached, indexed, replicated, or rebuilt on its own schedule, without the write side's transactional guarantees dictating how the read side is shaped or scaled.

Explained at three levels

Basic

One table design is being asked to do two jobs. Saving an order wants the data split across tidy, tightly-checked tables so nothing invalid can ever land; the dashboard that lists those orders wants it all sitting in one row so the page returns in milliseconds. Serve both from the same design and you pick your damage: bolt report-shaped columns onto the thing guarding your rules, or join nine tables on every page load and watch it time out. Keep two designs instead — one for saving, kept strict, and a second copy shaped exactly like the screen, refreshed whenever the first one changes.

Advanced

That refresh is a projection. Each committed write emits an event, or lands in a change feed the store already publishes, and a projector applies it to one read model per query shape — each denormalised until its query is a single lookup. Because the projector runs after the commit, the read side is eventually consistent: a user can write and not see it a second later, and how far behind it may fall is a number you pick rather than a property you inherit. None of this requires storing events as the system of record — the write side can hold current state and still emit what the projector needs.

Expert

Split per bounded context, and only where the asymmetry is real: rich invariants on the write side facing high-volume, divergently shaped reads. On a CRUD domain it is ceremony — a read replica and two indexed views buy most of the win for none of what follows. Staleness becomes a product decision, so show a pending state in the UI or route read-your-own-writes queries straight at the write model. A projection you cannot rebuild is a projection you cannot fix, so keep projectors idempotent and replayable from the write side. And publish the event inside the command's transaction or through an outbox: an event lost between the two leaves the read model wrong permanently rather than merely late. After that it is an operating loop — tune the batch, watch the lag, expect one poison event to stall the stream, and gate release on a rebuild you have timed against real history.

How it works

Variations

Single-store CQRS
Separate command and query model classes, but one shared database — the simplest form, and it avoids managing eventual consistency between two stores.
Materialized View
The read side is a precomputed, denormalized projection held in a store shaped for its query — a dedicated read database or search index.
Event Sourcing
The write side persists a stream of domain events rather than current state; read models are projections built by replaying that stream. A common pairing, not a requirement.
Task-based commands
Commands are named for user intent (ApproveOrder, not UpdateOrder), keeping the write model's invariants explicit instead of exposing raw field setters.

Trade-offs

Pros

  • Read and write sides scale and are optimized independently — vital when reads vastly outnumber writes.
  • Query models are shaped for the screen or report they serve, without compromise joins or ORM gymnastics.
  • The write model stays focused on protecting invariants, not on shaping output for consumers.
  • New read views can be added, or rebuilt from scratch, without touching write-side logic.

Cons

  • Two models — sometimes two stores — to build, deploy, and keep in sync: real added complexity.
  • Sync between write and read side is often eventually consistent, so a read right after a write can be stale.
  • Debugging spans two models instead of one, making it harder to trace a value back to what wrote it.
  • Overkill for a small CRUD app with no meaningful asymmetry between how it's written and how it's read.

When to use it

Reach for it when

  • Read and write workloads have very different shapes, volumes, or scaling needs.
  • Query needs — dashboards, search, reports — don't map cleanly onto the write model's structure.
  • You want to add new read views without destabilizing the code that enforces write-side invariants.

Avoid when

  • The domain is simple CRUD with no real divergence between how it's written and how it's read.
  • The team can't absorb the operational cost of a second model, or of eventual consistency.
  • A single well-designed model plus a couple of read-only projections already covers the need.

Code sketch

TypeScript — split command and query paths 
// Write side: a command mutates state and enforces invariants
interface PlaceOrder { customerId: string; items: string[]; }

class OrderCommandHandler {
  constructor(
    private readonly orders: OrderWriteRepo,
    private readonly bus: EventBus,
  ) {}

  async handle(cmd: PlaceOrder): Promise<void> {
    const order = Order.create(cmd.customerId, cmd.items); // enforces invariants
    await this.orders.save(order);
    await this.bus.publish({ type: "OrderPlaced", orderId: order.id, items: cmd.items });
  }
}

// Read side: a denormalized projection kept up to date by events
class OrderSummaryProjector {
  constructor(private readonly view: OrderSummaryStore) {}

  async on(event: { type: "OrderPlaced"; orderId: string; items: string[] }) {
    await this.view.upsert(event.orderId, { itemCount: event.items.length, status: "placed" });
  }
}

// Query side: reads the shaped view directly, no write model involved
async function getOrderSummary(orderId: string, view: OrderSummaryStore) {
  return view.findById(orderId);
}

In the wild

Axon FrameworkA Java framework built explicitly around CQRS: command handlers on aggregates raise events, while tracking event processors maintain query projections and can be reset to replay the event store and rebuild a projection from scratch.
MartenA .NET library over PostgreSQL that persists events in the write store and maintains read-side projections either inline in the write transaction or asynchronously via a background daemon that can rebuild a projection by replaying the event log.

In production

Tuning knobs

  • Projection batch size & poll interval — How many events a projector applies per pass and how often it wakes to look for more. Larger batches raise throughput but widen the read side's lag behind the write side.
  • Read-model rebuild — The ability to drop a projection and replay it from the write store or event log. Rebuild cost grows with history volume, so it must be planned, not discovered under fire.
  • Staleness budget — The maximum read-after-write lag a query is allowed to show before it must block, retry, or fall back to the write model. Sets the contract the rest of the system is built against.
  • Read-side replicas and indexing — Number of read replicas and the indexes on the query store, scaled and shaped independently of the write store to match the read workload.
  • Command idempotency key — The dedup key that lets a retried command be recognized and applied once, since async projection makes accidental double-submits easy.

Signals to watch

  • Projection lag — Gap between the latest committed write and what the read model reflects — measured as events pending or seconds behind. The core health number for CQRS.
  • Projection backlog depth — Count of events queued for a projector but not yet applied; a rising backlog is lag about to happen.
  • Command-handler p99 latency — Tail latency of the write path, watched separately from read latency since the two scale under different pressure.
  • Rebuild duration — Wall-clock time to replay and rebuild a projection from scratch — the number that decides whether a rebuild is a routine op or an outage.

Failure modes under load

  • Projection lag blows out — The write side races ahead of a slow projector; read models fall arbitrarily behind and users see stale data with no upper bound on how stale.
  • Poison event stalls the projector — One un-applicable event at the head of an ordered stream blocks every projection behind it until it is skipped or dead-lettered.
  • Read-after-write anomaly — A user writes, immediately reads, and does not see their own change — driving confused retries and duplicate submits.
  • Permanent write/read divergence — If the command and its event are not persisted atomically, a crash between them leaves the read model wrong forever, not just late.

Readiness checklist

  • Staleness budget is documented, and eventual consistency is made visible in the UI (a processing state) rather than hidden.
  • Every projection is rebuildable from the write side, and the rebuild has been run and timed against production-scale history.
  • Projectors are idempotent — applying the same event twice leaves the read model identical.
  • Command-to-event persistence is atomic (single transaction or an outbox) so the read model cannot diverge permanently.
  • Projection lag is monitored with an alert threshold, and poison events dead-letter instead of halting the stream.
