Architecture

AI Agent

Give a language model a set of tools and call it in a loop: it picks the next action, your runtime executes it, and the result becomes input to the next turn. You stop deciding the order of the steps and start deciding when the loop is allowed to stop.

Architecture

What it is

Some work cannot be written as a workflow, because the second step depends on what the first one found. Read a failing build, decide what is broken, fix it, run it again: the shape of that job is only known once it is under way. Write it as a fixed pipeline and you spend your life adding branches for cases the last run discovered.

An agent inverts the control. Your program supplies the tools and the model supplies the order. Each turn the model sees everything that has happened so far and either calls a tool or declares the goal met; your runtime executes the call, appends the result, and calls the model again. The pattern is the loop and its stop condition, not the prompt.

That inversion moves the design work somewhere new. You are no longer designing a sequence — you are designing what the model can see, what it is allowed to do, how you know it has finished, and what happens when it is confidently wrong. Everything the model reads is also everything an attacker who controls a tool result can write, so the tool surface is a trust boundary as well as a capability list.

Explained at three levels

Basic

You want a computer to do a job whose steps nobody can list in advance — read the failing build, work out what broke, fix it, run it again. A script has to guess the order, so every new surprise means another branch. Instead, hand the model a short list of things it may do, then call it over and over: it picks one, you carry it out, you show it the result, and it picks again. You are not writing the steps any more. You are deciding what it may touch, and when it has to stop.

Advanced

Each turn re-sends the whole transcript plus the tool schemas, so the model chooses its next call from everything observed so far; the runtime executes it, appends the observation, and calls again until the model answers without a tool call or a budget stops it. The shape has room in it: a planning turn that writes the step list first, a supervisor whose tools are child loops with their own transcripts, retrieval demoted from a fixed pre-step to a call the model makes when it notices a gap, or a single run-this-code tool in place of a menu. All four are the same loop with a different tool surface, and the tool surface is where you spend your design effort.

Expert

Pick the loop over a fixed workflow only when step order is genuinely unknowable in advance and the environment answers back — otherwise you have bought non-determinism and paid for it with re-sent transcripts. The bill has four lines and each has a counter-move. Cost grows super-linearly in turns: compact the transcript and offload bulky tool output to files the model re-reads on demand. Success is self-reported: gate completion on an external check the loop cannot fake, such as a build or a test run. Tool results are untrusted instructions in the same context as your own: sandbox the action surface and keep irreversible actions behind a human. Quality decays across a long transcript: carry the goal in a durable artifact re-read every turn, rather than trusting the first message to survive.

How it works

Variations

Single loop, flat tool list
One model, one transcript, every tool visible at every turn. Cheapest to build and to reason about, and the right starting point. It stops working when the tool list grows past what the model chooses between reliably, or when the transcript outgrows the context window.
Plan then execute
A first turn writes the step list as an artifact; later turns work against it and update it. Re-reading the plan each turn makes drift from the original goal visible instead of gradual. You pay one extra model call, and you inherit any plan that was wrong from the start.
Supervisor and workers
One coordinating loop whose tools are other loops. Each child works in its own transcript and returns a summary, which bounds the parent's context growth and lets sub-goals run in parallel. The parent only ever sees the summary, so a child that quietly did the wrong thing still reports success.
Retrieval as a tool
Instead of a fixed retrieve-then-answer pipeline, retrieval becomes one more call the model makes when it notices a gap. It fetches more precisely and less often — and it will sometimes not notice the gap at all, which the fixed pipeline never fails to do.
Code as the only action
Rather than a menu of tools, the model gets one: run this code. It composes behaviour you never anticipated, which is both the point and the risk. Only run this form inside a sandbox.
Computer use
The tools are a screenshot, a pointer and a keyboard, so the loop drives software that exposes no API at all. It reaches systems nothing else can reach, at a far higher cost per step and a far lower reliability per step.

Trade-offs

Pros

  • Handles work whose step count is unknown in advance, so you do not have to enumerate branches you have not met yet.
  • Corrects itself from real feedback. When the environment answers — a compiler, a test run, an HTTP status — the next turn sees the failure and can act on it.
  • New capability arrives as a new tool, not a new code path, so the routing logic does not change when the tool list does.
  • Absorbs the small judgement calls that would otherwise interrupt a person once per step.
  • Degrades to partial progress rather than a hard failure, provided every action it takes is recoverable.

Cons

  • Non-deterministic. The same goal takes a different route on every run, so a bug reproduces only statistically and regression testing needs an evaluation suite rather than assertions.
  • Cost grows faster than the work does, because every turn re-sends the whole transcript before it.
  • Reports success on its own authority. Without an external check, "done" means the model stopped, not that the goal was met.
  • Every tool result is untrusted input landing in the same context as your instructions, so a hostile document or web page can redirect the loop.
  • Quality falls as the transcript lengthens: instructions given early compete with hundreds of turns of tool output, and the model attends to them less.
  • The action surface is the blast radius. Anything a tool can do, a misled loop can do, at machine speed and without hesitating.
  • Latency is a multi-turn sum of model calls and tool calls, which puts an interactive budget of a few hundred milliseconds permanently out of reach.

When to use it

Reach for it when

  • The number and order of steps depend on what the earlier steps find.
  • The environment answers back, so the loop has something real to correct itself against.
  • A person would otherwise sit between the steps making routine calls that are obvious in context.
  • The task tolerates minutes rather than milliseconds, and a partial result is still worth having.

Avoid when

  • The steps are known and fixed. A workflow is cheaper, faster and reproducible.
  • A wrong action cannot be undone and you are not willing to gate it behind a human.
  • The request has a hard latency budget in the hundreds of milliseconds.
  • You cannot state a stop condition. Without one, the loop runs until it exhausts a budget you never set.

Code sketch

TypeScript — the loop, its budget, and the guard in front of every call 
type Tool = {
  name: string;
  schema: object;                          // what the model must send
  run(args: unknown): Promise<string>;     // the observation it gets back
};

async function runAgent(goal: string, tools: Tool[], limits: { turns: number; tokens: number }) {
  const transcript: Message[] = [{ role: "user", content: goal }];
  let spent = 0;

  for (let turn = 0; turn < limits.turns; turn++) {
    const reply = await model.complete({ messages: transcript, tools: tools.map(t => t.schema) });
    spent += reply.usage.total;
    transcript.push(reply.message);

    if (!reply.toolCall) return { status: "done", answer: reply.text, turns: turn, spent };
    if (spent > limits.tokens) return { status: "budget-exhausted", transcript, turns: turn, spent };

    const tool = tools.find(t => t.name === reply.toolCall.name);
    // A refusal is an observation, not an exception: the model has to see it to change course.
    const observation = !tool
      ? `no such tool: ${reply.toolCall.name}`
      : (await guard(tool, reply.toolCall.args))
        ? await tool.run(reply.toolCall.args).catch(e => `tool failed: ${e.message}`)
        : `refused: ${tool.name} is not permitted here`;

    transcript.push({ role: "tool", callId: reply.toolCall.id, content: observation });
  }
  return { status: "turn-limit", transcript, turns: limits.turns, spent };
}

In production

Tuning knobs

  • Turn limit — The hard ceiling on iterations. Enforce it in the runtime, never in the prompt — a model asked to stop after ten turns will not.
  • Token budget per run — A second ceiling that catches the case a turn limit misses: few turns, each enormous.
  • Per-tool timeout — One slow tool otherwise holds the whole run open past any caller deadline.
  • Compaction threshold — The fraction of the context window at which the transcript is summarised. Too low and you discard what the task needs; too high and the last turns have no room.
  • Sub-agent fan-out — How many child loops a supervisor may run at once. This multiplies spend, so cap it.
  • Model retry policy — Attempts and backoff for provider errors, kept separate from the loop’s own turn count so a retried call is not counted as progress.

Signals to watch

  • Turns per completed task — The distribution, not the mean. A long tail is the loop failing to converge rather than the work being hard.
  • Tokens per task — Track alongside turns: the two diverge when the transcript is growing faster than the work.
  • Stop-reason mix — Shares of final-answer, turn-limit, budget-exhausted and error. Turn-limit rising is the earliest sign of trouble.
  • Tool error rate, per tool — One tool failing repeatedly usually means its description is wrong, not that its implementation is.
  • Externally verified success rate — Whatever a build, a test run or a reviewer says — the only success number that is not the model marking its own work.
  • Repeated identical calls per run — The same call with the same arguments twice in a row is the loop stuck; it is cheap to count and catches a lot.

Failure modes under load

  • Stuck loop — The model repeats one failing call until the turn limit, spending the whole budget on no progress. It looks like normal traffic on every metric except repeated-call count.
  • Context exhaustion mid-task — The transcript reaches the window and compaction drops the goal along with the noise. The loop keeps running and answers a different question.
  • Tool timeout cascade — A dependency slows down, every turn now waits on it, and concurrent runs pile up until the runtime’s own pool is exhausted.
  • Rate-limit thrash — Provider throttling turns each turn into a retry, so wall-clock time and cost both climb while the turn count barely moves.
  • Sub-agent explosion — A supervisor spawns children that spawn children. Spend goes up by a factor nobody predicted, and no single run looks abnormal.
  • Injected redirection — A tool returns text carrying instructions, the loop follows them, and the audit trail shows a well-formed run that did the wrong thing.

Readiness checklist

  • Turn limit and token budget are enforced by the runtime, not requested in the prompt.
  • Every tool is idempotent, or gated behind a confirmation the loop cannot give itself.
  • Any tool that executes code runs inside a filesystem and network boundary.
  • Transcripts are persisted with their stop reason, so a bad run can be read afterwards.
  • Completion is gated on an external check the loop cannot fake.
  • An evaluation suite runs before any prompt, tool or model change ships.
