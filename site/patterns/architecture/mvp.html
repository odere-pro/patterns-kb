Architecture

MVP

A presenter sits between a passive view and the model, pulling data out, pushing formatted results back through explicit calls, and leaving the view with no logic of its own to test.

Architecture

What it is

The Model-View-Presenter pattern splits a screen into three pieces: a model that holds the data, a view that renders it and forwards raw user input, and a presenter that sits between them. The presenter reads and writes the model, decides what the screen should show, and pushes the result into the view through an explicit interface of setters — setTitle(), showError(), setLoading(true). The view itself contains no decision logic; it renders whatever it's told and reports events like clicks straight back to the presenter. The pattern came out of Taligent, the Apple/IBM/Hewlett-Packard venture, early in the 1990s, and spread through Mike Potel's paper and the Dolphin Smalltalk team's version of it. Passive View and Supervising Controller are Fowler's later names for the two directions it took.

The force it resolves is testing UI logic without a real UI. In classic desktop and early mobile toolkits, instantiating a live view in a test runner was slow or flatly impossible, so any decision that lived in the widget class could only be checked by running the app. Depending on the view through a plain interface puts those decisions somewhere a test can reach: substitute a fake that records the calls it receives, and the presenter's whole behavior is exercised with no UI framework loaded.

Screen state lives in the presenter, not in the widgets. The view holds nothing worth asking it for — a test never queries it, it only reads back what it was told — so restoring a screen after a rotation or a rebuild means replaying the presenter's calls rather than reading values out of the view. That is the seam MVVM moves: there the state sits in an object the view reads from, here it sits in an object that writes to the view.

Explained at three levels

Basic

Put the rules of a screen inside the screen's own code and the only way to check them is to run the app: a real window, a real device, half a minute to learn that a button greyed out one tap too early. Hand the deciding to a second object that never touches a pixel. It hears what the user did, works out what should change, and sends back flat instructions — show this title, grey out that button — the way a news anchor reads exactly what the control room feeds them. The deciding can then be tested in milliseconds, with nothing drawn.

Advanced

The view is passive by contract: it exposes an interface the presenter owns, renders exactly what arrives, and forwards raw events without interpreting any of them. The presenter holds the screen state, reads and writes the model, and updates the view imperatively — no observers, no binding engine, so every change on screen is a call you can find in a stack trace. How strict to be is a coverage decision: route every display rule through the interface and a fake view sees all of them, or let the view read simple fields off the model itself and accept that those fields are proven only by a UI test.

Expert

Choose it where the toolkit fights tests and offers no binding engine — legacy desktop, older mobile — and move to MVVM the moment a real one exists, because the synchronisation you are about to write by hand is exactly what an engine deletes. The bill is linear in the size of the screen: a setter per displayable fact, a call per update. Pay the presenter-bloat half by splitting per region or per interaction instead of per screen, so no single presenter owns a whole complex page. Pay the drift half — nothing forces the presenter to push every state change — by rendering the view from one method that sets every field from a state object, which makes a missed call impossible rather than merely rare. Keep the model out of the view even in the looser form, or the interface stops being the seam the tests hang on.

How it works

Variations

Passive View
The strict form: the view holds zero logic, not even simple formatting or visibility rules — every display decision is pushed into the presenter and invoked explicitly.
Supervising Controller
A looser form: the view binds directly to the model for simple, low-risk display, and the presenter only steps in for the non-trivial behavior.
Interface-first view
The presenter is written against a view interface, never a concrete class, so tests substitute a fake that records calls instead of booting a real UI toolkit.
Presenter-per-view vs. shared presenter
Usually one presenter backs one screen, but a single presenter can coordinate several views across a multi-step flow like a wizard.

Trade-offs

Pros

  • Presenter logic is fully unit-testable without booting a real UI toolkit — swap in a fake view.
  • The view stays framework-thin, so swapping the UI layer means writing a new view against the same interface.
  • Clean separation of concerns: the view renders, the presenter decides, the model holds data.
  • Well suited to toolkits where the view layer is awkward or slow to instantiate directly in tests.

Cons

  • Every field the view can show needs an explicit setter — boilerplate grows with the screen.
  • Passive View pushes even trivial formatting into the presenter, which can bloat it.
  • Without further decomposition, a presenter for a complex screen becomes an unstructured catch-all.
  • Purely manual wiring — no observable binding — so view and presenter can drift if calls are missed.

When to use it

Reach for it when

  • Your UI toolkit is slow or awkward to instantiate in tests, and you want the screen's logic covered without one.
  • You need to swap the view technology while keeping the same presentation logic underneath.
  • You want one explicit seam where every display decision for a screen lives and can be unit tested.

Avoid when

  • The platform already gives you solid two-way data binding — MVVM removes most of the setter boilerplate MVP requires.
  • The screen is a couple of static fields; a full presenter and view-interface split is pure ceremony.
  • The codebase is already fluent in MVC and letting the view bind to the model directly is an acceptable trade there.

Code sketch

TypeScript — a presenter over a passive view 
interface TodoView {
  setItems(items: string[]): void;
  setError(message: string | null): void;
}

class TodoPresenter {
  constructor(
    private readonly view: TodoView,
    private readonly model: { load(): Promise<string[]>; add(t: string): Promise<void> },
  ) {}

  async onLoad(): Promise<void> {
    try {
      this.view.setItems(await this.model.load());
    } catch {
      this.view.setError("couldn't load todos");
    }
  }

  async onAddClicked(text: string): Promise<void> {
    if (!text.trim()) return;           // decision lives here, not the view
    await this.model.add(text);
    this.view.setItems(await this.model.load());
  }
}

In the wild

Google Web ToolkitGoogle published MVP as the recommended GWT architecture: presenters talk to the view only through a Display interface and communicate over an EventBus, so presenter logic runs in plain JVM tests without the browser, where instantiating real widgets was prohibitively slow.
Android Architecture BlueprintsThe Android Architecture Blueprints repo shipped a todo-mvp sample: each screen defines a Contract with View and Presenter interfaces, the Fragment implements the passive view, and the presenter is unit-tested against a mocked view.
