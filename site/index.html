Hazards & Antipatterns

0/36

Not to practice, just to recognize on sight. Every one is what the patterns above exist to prevent.

God ObjectOne class knows and does almost everything
Spaghetti CodeControl flow too tangled to follow
Big Ball of MudNo discernible architecture at all
Distributed MonolithSeparate services that still have to be released together
Anemic Domain ModelData objects with no real behavior of their own
Partial ObjectOne class, populated differently by every code path that returns it
Golden HammerOne familiar tool applied to every problem
Boat AnchorDead code or hardware kept around unused
Leaky AbstractionThe abstraction's promise breaks, and the substrate it hid shows through
Cache StampedeA popular key expires and a herd of misses hits the source at once
Hot KeyOne key draws so much traffic it overloads the single node that owns it
Stale CacheReads hit the cache while writes hit the store, so the cache serves old data
No CachingThe same unchanged data is fetched from scratch on every request
Hot PartitionOne shard takes most of the traffic while its peers sit idle
Split-BrainA partition leaves two leaders, both accepting writes that will not merge
Dual-Write InconsistencyTwo systems updated by two calls, and one of them does not land
Race ConditionUnsynchronized concurrent access whose result depends on timing
DeadlockTwo holders each wait for a lock the other holds, forever
StarvationSome work waits without bound while everything else keeps being served
Unbounded QueueA queue with no capacity cap grows until the process runs out of memory
Resource LeakA resource acquired but never released, shrinking capacity until everything blocks
Improper InstantiationRebuilding a shareable, expensive client on every request
Static ClingA static call to something stateful, with no seam to replace it
N+1 QueryOne query per row instead of one batched query — 1 + N round-trips
Chatty I/OMany small I/O calls where a few larger ones would do
Extraneous FetchingReading far more data than the operation actually uses
Busy DatabaseThe database spends its shared capacity running application logic
Monolithic PersistenceEvery kind of data in one store, whatever its access shape
Synchronous I/OA thread sits blocked while I/O completes, doing no work
Busy Front EndBackground work on the threads meant to answer requests
Connection-Pool ExhaustionEvery pool slot is held by a slow call, so requests hang instead of failing
Host Header RewritingA proxy replaces the requested host name, so the backend builds links, cookies and redirects for the wrong domain
Retry StormClients retry in unison, multiplying load on a service already failing
Thundering HerdOne event releases every waiter at once and they all rush the same resource
Cascading FailureOne failure's load lands on its peers and takes them down in turn
Noisy NeighbourOne tenant's load degrades everyone sharing the same pool

IX

Principles — how to do it well

0/27

A principle is a rule of thumb you check a decision against. They come at two altitudes — the maxims that keep a codebase simple, decoupled and cheap to change, and the maxims that keep a running system available, scalable and operable. Each page cross-links to the patterns that embody it and the hazards it guards against.

Writing the code 0/15

Maxims that hold inside a single codebase — what keeps it simple, decoupled and cheap to change.

Don't Repeat Yourself (DRY)Every piece of knowledge has one authoritative home in the system
Keep It Simple (KISS)Prefer the simplest design that actually meets the requirement
You Aren't Gonna Need It (YAGNI)Build capability only when a real present requirement demands it
Principle of Least AstonishmentBehave the way the people using your code already expect
Fail FastStop at the first broken assumption instead of running on with bad state
Single Responsibility PrincipleA class should have one reason to change — one actor it answers to
Open/Closed PrincipleOpen for extension, closed for modification — add behavior by adding code, not editing it
Liskov Substitution PrincipleA subtype must stand in for its base type without breaking the caller
Interface Segregation PrincipleMany small, client-specific interfaces beat one fat general-purpose one
Dependency Inversion PrincipleHigh-level policy and low-level detail both depend on an abstraction the policy owns
Composition over InheritanceBuild behavior by assembling small objects, not by inheriting a deep class hierarchy
Law of DemeterA method should talk only to its immediate collaborators, never reach through them
Separation of ConcernsDivide a system so each part addresses one distinct concern, understood in isolation
EncapsulationKeep state private so its invariants have exactly one owner
Postel's LawSend strictly to the spec, accept anything you can read unambiguously

Building the system 0/12

Maxims that hold across processes, machines and regions — what keeps a running system available, scalable and operable.

Design for Self-HealingBuild the recovery in, so a fault clears without an operator
Make Everything RedundantTwo of everything, failing independently, with a rule for who decides
Analyse Failure ModesEnumerate how each part can fail, and decide the response first
Minimize CoordinationWork that needs no agreement is the only work that scales
Design to Scale OutGrow by adding machines, and never depend on any one of them
Partition Around LimitsName the ceiling you will hit first, then split before you reach it
Design for OperationsOperators are users of your system, and their needs are requirements
Prefer Managed ServicesRun only what your users pay you for; rent the rest
Identity Is the PerimeterA verified identity grants access; where the packet came from does not
Design for EvolutionExpect every part to change, and keep each change local
Build for the Needs of the BusinessThe non-functional numbers are requirements, and the business owns them
Record Architecture DecisionsWrite down the decision and its reasoning at the moment you make it
