Object stores

Amazon S3, Azure Blob Storage and Google Cloud Storage against MinIO, Ceph and SeaweedFS: who operates the disks, which license you inherit, and what it costs to read your data back out.

Comparison

What this compares

An object store keeps immutable blobs in one flat namespace, addressed by key and reached over HTTP. This page compares the three stores you rent from a cloud provider with the three open-source servers you run yourself, on the axes that decide it: API compatibility, who carries the operational load, the license you inherit, and what leaving costs.

Decide whether you want an object store elsewhere. The object storage pattern argues why blobs leave the application tier, and the storage capability page places object next to block, file and database storage.

One behaviour is common to all six, so it decides nothing: bytes never stream through your service. You mint a time-limited signed URL and the client talks to the store directly — the Valet Key pattern, on every contender below.

Explained at three levels

Basic

Your application writes uploaded files to the server's own disk. Add a second server and half the downloads fail, because the file exists only on the machine that received it; lose that machine and the files go with it. An object store is one shared bucket every server reads and writes over HTTP, holding several copies of each file. Your choice is whether to rent that bucket or run the software yourself.

Advanced

Amazon's S3 API became the wire protocol most of the field implements, so the decision is where the bytes physically sit, not which client library you write against. A managed store bills per gigabyte stored, per request and per gigabyte leaving the region; a self-hosted one converts that into drives, racks and the engineer who replaces a failed disk. Durability comes from two different mechanisms — replication copies whole objects, erasure coding splits each object into data and parity shards — and only erasure coding holds raw-capacity overhead well under 2x.

Expert

Self-host when the constraint is physical — data that may not leave the building, a site with no dependable uplink, or an egress bill large enough to fund a storage team. The bill you take on is capacity planning, drive replacement and an upgrade path nobody else owns. Pay it by sizing erasure-coded pools to survive a whole node, and by keeping the S3 API as the only contract your applications know, so the store underneath stays replaceable.

The contenders

Amazon S3
The store whose API the rest of the field implements, operated by AWS and billed per gigabyte, per request and per gigabyte of egress. Storage classes run from hot down to archive, and a read after a write returns the new object rather than the old one.
MinIO
A single S3-compatible binary you run yourself, erasure-coding across the drives you hand it, licensed AGPLv3. It is the shortest path to an S3 endpoint on your own hardware — and in 2025 the community edition's web console lost most of its management features, which tells you the vendor's attention sits with the commercial AIStor build.
Azure Blob Storage
Microsoft's object store, operated by Azure, speaking its own API rather than an S3-compatible one. That costs portability: code that must run on both clouds needs an abstraction layer over the two. Access tiers cover hot through archive.
Google Cloud Storage
Google's object store, operated by Google, with an S3-interoperable XML API alongside its native one, so many existing S3 clients can be pointed at it. Multi-region buckets serve one bucket from several regions without you building the replication.
Ceph with the RADOS Gateway
A full distributed storage platform under LGPL, serving block volumes, a POSIX filesystem and S3-compatible objects from one cluster. It backs many private clouds at petabyte scale, and it is heavy to operate: the cost is people, not disks.
SeaweedFS
An Apache-2.0 store built for very large numbers of small files, with an S3-compatible gateway in front of it. It stands up faster than Ceph, and it earns its place when what you outgrew was a filesystem's per-directory and per-inode limits rather than raw capacity.

Choosing between them

In a public cloud, use the native store. Running your own object store on rented instances buys the same disks twice and adds a service to your on-call rotation, in exchange for nothing the platform was not already giving you.

Choose MinIO when you need the S3 API on-premises or at the edge and one team can own the cluster. Two conditions come with it: check how far AGPLv3 reaches into what you distribute, and read the 2025 console change as a statement about where the vendor invests.

Choose Ceph when object is one facet of a larger private-cloud need — the same cluster handing block volumes to virtual machines and a filesystem to a compute grid. It repays a dedicated operations team and punishes a part-time one.

Choose SeaweedFS when the workload is millions of small files and what you outgrew was a filesystem rather than a disk.

Before any of them, do less: a directory and a table of paths carries a single service a long way. Move to an object store when a second service needs the same blobs, or when the disk is what you are trying to scale.
