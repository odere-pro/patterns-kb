Comparison

Infrastructure as Code

Four genuinely different approaches to describing infrastructure in a file: a declarative language with a state file, the same thing written in a programming language you already use, an agentless tool that configures machines rather than creating them, and the templates your cloud ships for free.

Comparison

The decision

The first thing to settle is not which tool but which of two jobs you are doing. Provisioning creates and destroys resources that do not exist yet — networks, clusters, databases — and needs to know what it created last time so it can work out the difference. Configuration management takes machines that already exist and brings their contents into line — packages, files, services — and needs to reach them over the network. Tools built for one do the other badly, and most arguments about them are two people doing different jobs.

Inside provisioning, the real split is what the description is written in. A purpose-built declarative language can only describe resources, which is limiting and also the point: the file is diffable, reviewable, and hard to make clever. A general-purpose programming language gives you loops, types, tests and package management, and gives you the freedom to write infrastructure nobody can read.

Both approaches keep state: a record of what was created, mapping the names in your files to real resource ids. That file is the most operationally significant thing in this whole area — it must be stored somewhere durable, locked so two runs cannot race, and treated as a secret, because it contains attribute values from everything it made.

The licensing history matters here more than in most comparisons. HashiCorp moved Terraform from Mozilla Public License to the Business Source License in August 2023; the Linux Foundation forked the last MPL version as OpenTofu, and IBM subsequently acquired HashiCorp. The practical consequence is that "Terraform" now names two compatible-but-diverging tools under different licences, and which one you mean is a decision rather than a detail — check the current terms yourself before committing, because this is the fastest-moving fact on the page.

Explained at three levels

Basic

Someone clicked through a console to create the servers, and now nobody can say exactly what exists, nobody can rebuild it, and the second environment is subtly different from the first. Write the infrastructure down in files instead, keep them in version control, and let a tool make reality match the files. The tools split into two families that get confused for each other: ones that create resources, and ones that configure machines that already exist.

Advanced

The provisioning tools work by keeping state — a record mapping the names in your files to the real resource ids — and diffing your description against it to produce a plan you approve before anything changes. That state file is the operationally significant part: it needs durable storage, locking so two runs cannot race, and treating as a secret. The choice inside provisioning is a purpose-built configuration language against a general-purpose one: the first is limited and therefore reviewable, the second brings loops, types and packages along with the ability to write infrastructure nobody can read.

Expert

Take the provider's own templates when you are on one cloud and expect to stay — free, supported, no state file to operate — and treat multi-cloud or lagging service support as the trigger to leave. Otherwise the declarative tool wins on provider ecosystem rather than on language, and the choice between the original and its fork is a licence decision after the 2023 relicensing. Three costs worth naming. State is a single point of failure and a secret: pay that with remote state, locking and restricted access from day one. A general-purpose language buys expressiveness and spends reviewability: pay that by keeping the generated plan as the review artifact rather than the source. And configuration management cannot tell you what it will change before it changes it: pay that by not using it as a provisioner, and preferably by replacing instances from an image rather than converging them at all.

The contenders

Terraform
The declarative baseline, from HashiCorp — now part of IBM. Resources are described in its own configuration language, a plan shows the difference between the description and the recorded state, and an apply makes it so. Its provider ecosystem is the largest of any tool here, which is the actual reason it wins most of the time. Licensed under the Business Source License since 2023, not open source in the OSI sense. Rent the workflow as HashiCorp Cloud Platform Terraform, or run it in your own pipeline.
OpenTofu
The Linux Foundation fork of the last Mozilla-Public-Licensed Terraform release, created in response to that licence change. It reads the same configuration language and the same providers, so adoption is largely a matter of changing the binary — and the two have been diverging in features since the fork, so "compatible" is a shrinking claim rather than a permanent one. Choose it when the licence is the deciding constraint.
Pulumi
The same declarative model expressed in a general-purpose language — TypeScript, Python, Go, C# and others — so infrastructure is ordinary code with the tests, types, editor support and package manager that come with it. It keeps state and produces a preview exactly as the declarative tools do; what changes is who can read the source. Available as a managed backend or self-hosted state.
Ansible
A different job, included because it is constantly compared to the others. Agentless configuration management from Red Hat under GPL-3.0: it connects over SSH or WinRM and runs tasks against machines that already exist. It keeps no state file, because it does not need one — it inspects each machine and converges it. It can create cloud resources through modules, and doing so gives you provisioning without the difference-detection the others are built around.
The cloud's own templates
AWS CloudFormation, Azure Resource Manager templates and Bicep, and Google Cloud's Infrastructure Manager. Free, supported by the provider, and state is kept for you as part of the deployment — which removes the whole class of state-file operations. The cost is that they describe one cloud, and they typically support a new service on the provider's own schedule rather than the community's.
Typed configuration languages
CUE, Dhall, Jsonnet and similar sit between the two provisioning styles: more expressive than a fixed configuration syntax, more constrained than a full programming language, and usually used to generate input for one of the tools above rather than to talk to a cloud directly. Reach for one when the problem is template sprawl across many similar environments rather than the provisioning itself.

Choosing

Consider the null option first. If you are on one cloud, expect to stay, and your infrastructure is small, that provider's own templates cost nothing, need no state file operated by you, and are supported by the people who run the services. The reason most teams outgrow them is multi-cloud or the pace of provider support, and neither may ever apply to you.

Otherwise the declarative tool is the default, and the honest reason is the provider ecosystem rather than the language. Nearly everything you will want to manage — including things that are not cloud resources at all, like DNS registrars, identity providers and monitoring backends — already has a provider. Between the two, choose on licence: pick OpenTofu when a permissive licence is a requirement, and the original when it is not and you want the vendor's own managed workflow.

Reach for the programming-language option when the infrastructure itself is genuinely programmatic — many near-identical environments generated from a specification, or a platform team publishing reusable components as versioned packages to teams who consume them as libraries. The condition that should stop you is a team whose reviewers are not programmers, because the review of a plan is worth more than the expressiveness of the source.

Reach for the configuration-management tool when the thing you are changing is inside a machine you already have. It is also the pragmatic answer for anything with no API — an appliance, a legacy server, a network device reachable only over SSH. What it should not be is your provisioner: without recorded state it cannot tell you what it will change before it changes it, and losing the plan step is losing the main safety property of the whole practice.

The two are frequently used together, and the split is worth stating explicitly: provision the machine with one, configure its contents with the other. Where you can avoid the second half entirely, do — building an immutable image and replacing instances rather than converging them removes the drift that configuration management exists to correct. That is why this comparison matters less than it used to on container platforms, where the image is the configuration and the only thing left to provision is the cluster.
