Comparison

Key-value & cache stores

Redis, Valkey, Memcached, Dragonfly, DynamoDB and Cassandra side by side — which of them you may lose without consequence, what each license commits you to, and who will run it for you.

Comparison

What this compares

Every store here answers the same question fast: give me the value filed under this key. They buy that speed by giving up the query power of a relational database — no joins, no ad-hoc filters, and often no way in except the key you wrote.

One line splits the field, and you pick a side before you pick a product. An in-memory cache store holds a copy of something you can compute again, so losing all of it costs a slow hour rather than a customer's data. A durable key-value database is the record itself, so losing it is an incident. Redis, Valkey, Memcached and Dragonfly sit on the first side; DynamoDB and Cassandra on the second.

Two questions decide the rest: what the license commits you to, which turned real in 2024 and has not settled, and who gets paged when the node fills up. What follows compares the six on durability, data model, scaling shape, license and who operates them, so a distributed cache and a system of record never get chosen the same way.

Explained at three levels

Basic

Your page asks the database the same expensive question on every request, and under load the database is what falls over. So you keep the answer in memory beside the app under a key, and the next visitor gets it without touching the database. The catch is what happens when that memory restarts. If the contents were only ever a copy, you shrug and recompute; if they were the only place a customer's cart lived, the cart is gone. Decide which of the two you are building first, because the answer rules out half the products.

Advanced

The two sides differ in how they spend a machine. Redis and Valkey run commands on a single core, so you shard or replicate to grow; in exchange their data structures turn a leaderboard or a rate limiter into two commands. Memcached is multithreaded and holds opaque bytes, with no persistence and no replication, so a lost node is lost keys. Dragonfly keeps the Redis command surface and spreads it across cores, pushing one large machine further before you shard. DynamoDB partitions your keyspace across storage it manages and replicates each write across availability zones before acknowledging it, which is what makes it safe to hold the record itself.

Expert

Choose on the exit door, then on the bill. A managed service running an open engine — Valkey under BSD-3-Clause on ElastiCache or Memorystore — costs nothing today and leaves you able to run the same binary yourself if the terms move again; that is the counter-move to the 2024 relicense. Redis earns its terms when you use the depth: sorted-set ranges, streams and server-side scripting are capability, not preference. The durable side inverts the arithmetic. DynamoDB charges per request, so a hot read path costs more than the same data behind a cache, and its single-digit-millisecond figure says nothing about what a badly chosen partition key does to your tail. Cassandra buys multi-region writes and charges for them in nodes you operate and repairs you schedule. Every store here punishes the same mistake — a hot spot in the key distribution — and no license or provider saves you from it.

The contenders

Redis
Rich in-memory data structures — hashes, sorted sets, streams — on a single-threaded command core, with optional snapshot or append-only persistence. Since Redis 8 (May 2025) it is tri-licensed under RSALv2, SSPLv1 or AGPLv3; the AGPLv3 option returned it to OSI-approved open source after the 2024 move to source-available. Amazon ElastiCache, Azure Cache for Redis, Azure Managed Redis and Google Memorystore run it for you.
Valkey
The community fork of Redis 7.2.4, created after the 2024 relicense and hosted by the Linux Foundation with its own contributors and roadmap. BSD-3-Clause and drop-in compatible, so existing clients keep working. ElastiCache and Memorystore both sell a Valkey engine, which makes it the cheapest way to keep a permissive license without running the server.
Memcached
A multithreaded cache and nothing more: no persistence, no replication, no data structures past an opaque value under a key. BSD-3-Clause. The missing features are the product — less to configure, less to go wrong — and ElastiCache runs it for you.
Amazon DynamoDB
A partitioned key-value and document store AWS runs and you cannot: proprietary, managed only, single-digit-millisecond reads, autoscaling partitions, pay-per-request billing. Writes replicate across availability zones before they are acknowledged, so this holds the record itself rather than a copy.
Dragonfly
A multithreaded engine speaking the Redis API, built to get more out of one large machine before you take on sharding. Business Source License 1.1 — source-available, not open source — so put it past your legal team before you depend on it. No major cloud sells it as an engine, so you operate it.
Apache Cassandra
A wide-column store with leaderless replication and a write-optimised engine, so every replica takes the write and multi-region is the design rather than a bolt-on. Apache-2.0. Amazon Keyspaces and Azure Managed Instance for Apache Cassandra run compatible services.

Choosing between them

Default to a managed cache running an open engine: ElastiCache or Memorystore with the Valkey engine gives you cache-aside today and leaves the exit door open, because the same BSD-3-Clause binary runs on your own machines if the terms or the bill change. Take Redis instead when you use its depth — sorted-set ranges, streams, server-side scripting — and your legal team has read the terms it now ships under. Take Memcached when a plain multithreaded cache is the whole job, and treat its missing features as one less thing to operate.

Cross to the durable side the moment the store becomes the record. Choose DynamoDB when you want zero operations and can accept one vendor, and budget on requests rather than memory. Choose Cassandra when write volume and multi-region writes dominate, and staff for the nodes and repairs that come with it.

Do less first. If one node's memory holds the working set and each node may keep its own copy, an in-process map with a TTL needs no service, no network hop and no failover plan. Move to a shared store when the copies disagree in ways users notice, or when the working set stops fitting.
