Hazard

Stale Cache

Because most systems read from the cache but write to the store, every write opens a window in which the cache still holds — and keeps serving — the value the source of truth has already moved past.

Hazard

What it is

A stale cache is the standing tension in every read cache: the cache and the source of truth can disagree, and the cache wins the read. The cause is structural — most systems read from the cache but write to the store — so the moment a write lands in the store, any cached copy of that data is out of date and stays that way until it is invalidated or expires. Every request served from the entry in between gets the old value.

The classic picture: a user updates their profile photo. The new image is written to the database, but the old one is still sitting in the cache, so everyone else keeps seeing the previous photo until that entry is evicted. Nothing is broken — the write succeeded, the cache is serving fast, the read returns a real value. It's just the wrong value, for as long as the window lasts. This is one half of the adage that the two hard problems in computing are naming things and cache invalidation.

Explained at three levels

Basic

Someone updates their profile photo. The new one is saved in the database, but the copy the cache is handing out is still the old one, so everybody else keeps seeing the previous picture until that copy is thrown away. Nothing failed: the save worked, the read was fast, the answer was real. It was just out of date, and nobody could tell.

Advanced

Reads go to the cache and writes go to the store, so unless something invalidates the key, a completed write leaves a copy serving the old value until its TTL runs out. Long TTLs chosen for hit rate widen that window, and a client cache, a CDN and a shared cache each hold their own copy on their own schedule, so two readers legitimately disagree. The moves are invalidate-on-write with cache-aside, a short TTL to cap the lag, write-through to close the window at the cost of write latency, or refresh-ahead to keep the entry near its source.

Expert

The defining fact is that this is a purchased trade-off, not a defect: the cache exists because serving truth on every read is too expensive, so the question is never whether a copy can be wrong but how wrong this particular datum tolerates being. Decide that per datum and write it down — a feed may lag minutes, a price or a permission may not — because one global TTL prices every value the same. The second-order case is the invalidation race, where a delete crossing a concurrent read repopulates the entry with the value just removed, and a fix applied to one layer leaves the CDN and client copies untouched. Freshness is bought with hit rate, write latency, or both.

How it happens

  • Read-cache, write-store asymmetry: reads and writes take different paths, so a write never touches the cached copy unless something explicitly invalidates it.
  • No invalidation on write: the store is updated but the cache key is left in place, so it keeps serving the old value until its TTL runs out.
  • Long TTLs chosen for hit rate: the longer an entry is allowed to live, the wider the window in which it can be wrong.
  • Multiple cache layers or replicas: a client cache, a CDN, and a shared cache each hold their own copy, and they expire on their own schedules.

What it costs

  • Users see the wrong thing, confidently. A stale read looks exactly like a fresh one — there's no error, so a user acts on data that's already changed underneath them.
  • The impact scales with how much staleness hurts. A slightly old profile photo is harmless; a stale price, permission, or account balance can be a correctness or safety problem.
  • It's inconsistent across readers. One user hits a freshly-invalidated key and sees the new value while another still hits a cached copy and sees the old one, which is confusing and hard to reproduce.
  • Tightening it isn't free. Cutting the window means invalidating aggressively or shortening TTLs, both of which trade away the hit rate the cache was there to provide.

How to avoid it

There's no perfect fix — how much staleness is acceptable is a per-datum judgment. The strongest option is to invalidate on write: when the store changes, delete (or update) the cached key in the same path, so the next read misses and reloads the current value. Where a bounded lag is fine, a short TTL caps how long any entry can be wrong. And in many cases the honest answer is to accept eventual consistency — decide the stale window is harmless for this data (a feed, a metric, a profile image) and document it — rather than pay for a guarantee the use case doesn't need. Writing through the cache synchronously removes the window entirely at the cost of write latency.
