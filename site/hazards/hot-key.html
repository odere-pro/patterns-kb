Hazard

Hot Key

One cache key is so much more popular than the rest that the single node or shard holding it is swamped — even when the overall hit rate is excellent and the rest of the cluster sits nearly idle.

Hazard

What it is

A hot key — also called the celebrity problem — is a single cache entry that draws wildly disproportionate traffic. Think of a social platform where everyone is loading the same superstar's profile: the key for that one record can field millions of reads per second while the millions of other keys see a handful each. Caching is doing its job — the value is served from memory, not the database — and yet one entry alone can be more than a single cache node can handle.

The distinction from a cache stampede matters, because from a dashboard the two look alike. A stampede is transient: it happens in the gap when a key is absent, and it ends the moment the key is repopulated. A hot key is a standing condition — the entry is present and served correctly, and the load stays exactly where it is until you change how that key is read.

A hot partition is the storage-tier version of the same skew, and the two names get traded freely enough that an incident channel will use them for each other. Separate them by what saturates: a hot key overloads the one node holding a single entry, a hot partition overloads a shard holding a whole slice of the keyspace. The fixes follow that split — replicate the entry, or repartition the key.

Explained at three levels

Basic

One entry is wanted by nearly everybody — the live scoreboard, the pinned announcement, the post the whole internet is sharing today. Millions of reads a second land on the single machine that happens to hold it, and that machine saturates while the rest of the fleet sits close to idle. Buying more machines changes nothing, because the popular entry still lives on exactly one of them. The fix is to keep more than one copy of that entry and read from all the copies.

Advanced

Placement is popularity-blind. A consistent-hashing ring gives each key exactly one owner and never asks how often that key is read, so demand that follows a power law meets a layout that assumes uniformity. Find the key before its shard tips, with per-key request counts sampled at the client or throughput compared node by node. Then size the spread from what you measured: N replicas divide the read rate by N, so the replica count follows the ratio between the key's request rate and what a single node can actually serve.

Expert

The skew belongs to the workload, not to the code, so capacity added anywhere but the read path never sees the traffic. That makes the read path the only lever, and it is priced in staleness — every replica is another copy to invalidate, and an in-process copy is stale for its whole TTL on every instance at once. A write-hot key inverts the deal: replicas multiply invalidation work instead of dividing read load, so a counter everyone increments wants sharded counters or a queue in front of it, not copies. Watch the expiry too, because letting the hot entry lapse converts a hot key into a stampede — refresh the copies on a schedule rather than letting them expire.

How it happens

  • Naturally skewed popularity: real-world access follows a power law — a celebrity, a viral post, a trending product — where a handful of keys dwarf the rest.
  • Key-to-node placement by hashing: a consistent-hashing ring or a sharded cache assigns each key to one owner, and popularity isn't part of that assignment.
  • Scaling out doesn't dilute it: adding cache nodes rebalances the key count, but the hot key still lives on exactly one of them, so its load doesn't spread.
  • A single logical entity that everyone needs at once — a global config, a live scoreboard, the pinned announcement — read on nearly every request.

What it costs

  • One node becomes the bottleneck. The node owning the hot key saturates its CPU or network while the rest of the cluster is nearly idle — capacity that can't be brought to bear on the problem.
  • The blast radius is wider than the key. A saturated node also serves every other key that hashes to it, so unrelated data behind the same node gets slow or unavailable too.
  • It hides behind good averages. Cluster-wide hit rate and average latency look healthy; the damage is a tail concentrated on one shard, easy to miss until that shard tips over.
  • Caching alone can't scale past it. The usual read-scaling move — add cache nodes — does nothing here, so the hot key quietly caps the throughput of an otherwise horizontally-scalable design.

How to avoid it

The fix is to stop routing all of the hot key's traffic to one place. Replicate the hot entry across several cache nodes and spread reads over the copies, so the load is shared instead of concentrated. And keep an in-process local cache in front of the shared cache for the very hottest values, so repeated reads are answered from the application's own memory and never leave it. Note that consistent hashing, which keeps hit rates high across a changing pool, does not help here — it still sends every request for one key to the same node; spreading the key itself is the move.
