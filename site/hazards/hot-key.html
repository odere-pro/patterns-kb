Hazard

Hot Key

One cache key is so much more popular than the rest that the single node or shard holding it is swamped — even when the overall hit rate is excellent and the rest of the cluster sits nearly idle.

Hazard

What it is

A hot key — also called the celebrity problem or a hot partition — is a single cache entry that draws wildly disproportionate traffic. Think of a social platform where everyone is loading the same superstar's profile: the key for that one record can field millions of reads per second while the millions of other keys see a handful each. Caching is doing its job — the value is served from memory, not the database — and yet one entry alone can be more than a single cache node can handle.

The distinction from a cache stampede matters. A stampede is transient: it happens in the gap when a key is absent. A hot key is a standing condition: the entry is present and served correctly, but the sheer request rate for that one key concentrates on whichever node owns it. Because a cache cluster spreads keys across nodes by hashing, every request for the hot key routes to the same single node — so adding more cache nodes doesn't help, since the extra nodes never see the hot key's traffic.

Explained at three levels

Basic

One entry is wanted by nearly everybody — the superstar profile, the live scoreboard, the pinned announcement. Millions of reads a second all land on the single machine that happens to hold it, and that machine saturates while the rest of the fleet sits close to idle. Adding more machines changes nothing: the popular entry still lives on exactly one of them.

Advanced

Power-law popularity meets placement by hashing: a consistent-hashing ring gives each key one owner and knows nothing about how often it is read, so all the traffic for one key lands on one node. That node saturates CPU or network, every unrelated key hashing to it degrades alongside, and cluster-wide hit rate and average latency stay reassuringly healthy. Adding nodes rebalances key counts, not this key's load. The mitigations spread the key itself: replicate the entry across nodes and read from the copies, with an in-process cache in front for the very hottest values.

Expert

The defining property is that skew belongs to the workload, not to the code: one key's demand is unbounded while one node's throughput is not, so a shard tips over long before the cluster does. Defence has to live in how the value is read — several replicas plus a local copy in the application — because capacity added anywhere else never sees the traffic. The second-order case is a write-hot key, where replicas multiply invalidation work instead of dividing read load, and where an expiry on the hot entry turns into a stampede. Every copy added is another window of staleness and another slice of memory.

How it happens

  • Naturally skewed popularity: real-world access follows a power law — a celebrity, a viral post, a trending product — where a handful of keys dwarf the rest.
  • Key-to-node placement by hashing: a consistent-hashing ring or a sharded cache assigns each key to one owner, and popularity isn't part of that assignment.
  • Scaling out doesn't dilute it: adding cache nodes rebalances the key count, but the hot key still lives on exactly one of them, so its load doesn't spread.
  • A single logical entity that everyone needs at once — a global config, a live scoreboard, the pinned announcement — read on nearly every request.

What it costs

  • One node becomes the bottleneck. The node owning the hot key saturates its CPU or network while the rest of the cluster is nearly idle — capacity that can't be brought to bear on the problem.
  • The blast radius is wider than the key. A saturated node also serves every other key that hashes to it, so unrelated data behind the same node gets slow or unavailable too.
  • It hides behind good averages. Cluster-wide hit rate and average latency look healthy; the damage is a tail concentrated on one shard, easy to miss until that shard tips over.
  • Caching alone can't scale past it. The usual read-scaling move — add cache nodes — does nothing here, so the hot key quietly caps the throughput of an otherwise horizontally-scalable design.

How to avoid it

The fix is to stop routing all of the hot key's traffic to one place. Replicate the hot entry across several cache nodes and spread reads over the copies, so the load is shared instead of concentrated. And keep an in-process local cache in front of the shared cache for the very hottest values, so repeated reads are answered from the application's own memory and never leave it. Note that consistent hashing, which keeps hit rates high across a changing pool, does not help here — it still sends every request for one key to the same node; spreading the key itself is the move.
