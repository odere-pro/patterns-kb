Twelve-Factor

The application side of the bargain: keep configuration outside the build, keep state out of the process, expose a health signal something else can act on, and make a release an immutable thing that can be replaced — so that a platform is able to move, restart and duplicate your process without asking you.

Theme

The question

A platform can only do things to a process it is allowed to move. If the config is baked into the build, a new environment means a new build. If a session lives in memory, killing an instance loses a user's work. If nothing reports readiness, a restart takes traffic with it. Every one of those is the application refusing a capability the platform was ready to provide.

So this theme reads as a list of properties the application must hold, not a list of tools it must adopt. Configuration comes from the environment. Processes hold no durable local state. Long work is a separate process type rather than a thread borrowed from the request path. Health is a signal, not an inference. Logs are a stream someone else collects. A release is immutable and replaceable.

None of it is free — externalising configuration and state means running a store for each — and none of it is optional if you want the platform to do the work. The two halves are one bargain read from opposite sides.

Explained at three levels

Basic

A platform can only move, restart or duplicate a process if the process lets it. Bake the settings into the build and a new environment means a new build. Keep a user’s session in memory and killing an instance loses their work. Report nothing about readiness and a restart takes live traffic down with it. So this is a list of properties the application has to hold — settings from outside, no local state, a health signal, background work in its own process — each one a capability you are handing to whatever runs you.

Advanced

Read it as a contract rather than a toolkit. Configuration lives in a store read at start-up, so one artifact is promoted between environments unchanged. No request depends on which instance served the last one, so any instance can be destroyed. Readiness and liveness are reported explicitly, so a rollout knows when to send traffic and when to stop. Long work runs as its own process type, scaled and restarted separately from the request path. Telemetry is emitted as a stream and correlated elsewhere, because anything written locally dies with the instance. A release is immutable, so replacing it and reverting are the same operation.

Expert

The list was written for interchangeable web processes, so apply it to the parts of a system that should be disposable and not to the database — for stateful workloads it argues against itself. Four costs and their counter-moves. Externalising configuration and state buys replaceability and adds start-up dependencies: cache config after first read, degrade to the last known-good value, and treat the store as a tier-one service. The health endpoint carries most of the judgement in this theme — check too little and a broken instance keeps traffic, check too much and one downstream blip drains the fleet: separate liveness from readiness and keep dependency checks out of liveness. These properties decay silently, since one in-memory cache breaks nothing until a reschedule at 3am: test it by killing instances on purpose. And nothing enforces the list, so put the parts that can be checked — no writes outside a temp path, config absent from the image — into the build rather than into a document.

The tradespace

The first axis is what externalising costs. Configuration outside the build needs a store that is available at start-up, versioned, and secured — so an outage there is an outage everywhere, and the config becomes a deploy artifact nobody reviews. State outside the process needs a session store or a database on a path that used to be a memory read. You are trading local simplicity for the ability to be replaced, and that trade is only worth it if something is actually replacing you.

The second is the honesty of the health signal. A liveness check that only proves the process is running will keep a broken instance in rotation; one that checks every dependency will take the whole fleet out when a downstream service blinks. The interesting design work in this theme is almost all in that one endpoint.

The third is discipline over time. These properties decay silently: someone caches "just this one thing" in memory, someone reads a file the image happened to have, and nothing fails until an instance is rescheduled at three in the morning. Nothing enforces this list, which is why it is a set of habits rather than a framework.

The fourth is scope. The original list was written for stateless web processes on a managed platform, and it does not have opinions about data-heavy or latency-critical workloads. Read it as the contract for the parts of your system that should be interchangeable, not as an architecture for all of them.

The tour

External Configuration Store

The first factor and the one everything else depends on. If the same artifact cannot be promoted between environments unchanged, nothing further on this list is reachable — and the store you move it into is now a start-up dependency of every process.

Stateless Service

The property that makes an instance disposable. Once no request depends on which instance served the last one, the platform is free to add, move and kill processes — which is the entire capability you were trying to buy.

Health Endpoint

Fast start-up and clean shutdown only help if something can tell the difference between starting and ready. This is the smallest piece of this theme and where its judgement is most concentrated: check too little and a broken instance keeps traffic, check too much and one dependency takes the fleet.

Web-Queue-Worker

Background work belongs in a process that can be scaled and restarted on its own, not on a thread borrowed from the request path. Splitting the two is what lets a slow job stop being a source of request latency and failed health checks.

Distributed Tracing

Once a process is disposable, anything it wrote locally is gone with it. Emit a stream and let something else aggregate it — and once a request crosses several such processes, a correlated trace is the only thing that reassembles it.

Blue-Green Deployment

Where the whole list pays off. When config is external, state is elsewhere and readiness is reported, a release becomes an immutable thing you can stand up beside the current one and switch to — and switch back from.
