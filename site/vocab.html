Vocabulary

Every page in this knowledge base describes itself in machine-readable terms, and every tool that reads it speaks the same set. This is what those terms mean. The namespace is https://odere-pro.github.io/patterns-kb/vocab.html# — each term below is the fragment it resolves to.

How a page describes itself

Data lives in data-kb-* attributes; class is presentation and carries no meaning. The two never touch, so restyling cannot damage knowledge and re-authoring prose cannot damage structure.

A page carries metadata at three levels. The root declares identity and the facts that apply to the whole page. Each section declares which block it is, and its id is the same string, so the anchor and the semantic key never drift apart. Individual elements declare their own facts — a relationship, which side of a trade-off they argue, the reading level they appear from. Every attribute is listed below, with where it goes and what it holds.

The <script type="application/ld+json"> block in every page's <head> is projected from those attributes. It is generated, never hand-written — which is what keeps it honest. make check fails if any term it emits has no definition on this page.

Read this page either way: grouped by topic, or as one A–Z index of all 206 terms. The filter narrows both, and searches the rest of the knowledge base at the same time. Press / or ⌘K to reach it.

Page kinds

Seven kinds, and the choice decides two things at once: which blocks the page must carry, and which folder it lives in. A page's kind never changes after it is written — a pattern that turns out to be a hazard is a new page, not a retyped one.

patternpage kind11 blocksA reusable solution to a recurring problem, filed at one rung of the elevation ladder or under one lens. The largest kind, and the one the other six point at.
hazardpage kind6 blocksA failure mode with a name — what goes wrong, what it costs, and which patterns keep it from happening. A hazard names the problem rather than fixing it; the fix is a mitigated-by hop away.
themepage kind8 blocksA guided tour through the patterns that answer one recurring question. A theme owns its membership: its tour steps are the source of truth, and each pattern names the theme back.
principlepage kind6 blocksA design maxim — SOLID, DRY, KISS, YAGNI. Not a mechanism you build but a rule you honour, which is why it carries a mandatory block on how it fails when taken too far.
designpage kind11 blocksA worked case study — a system-design or low-level-design kata argued end to end, from requirements through the hard sub-problems. It joins the graph through demonstrates.
capabilitypage kind7 blocksOne category of managed cloud service, taking the capability as its subject and the vendors' products as evidence. It joins the graph through implements.
comparisonpage kind6 blocksOne product decision: the managed services and open-source contenders for a single capability area, side by side, compared on the conditions that decide the choice.

Blocks

Each kind of page carries the same blocks in the same order, so the same question is answered in the same place on every page — and a reader can fetch one block instead of a whole document. Every kind extends one skeleton: it opens with description and closes with relationships, and only the middle is kind-specific. A block marked ? is optional, and a page may honestly leave it out; every other block is mandatory and make check fails on a missing, unknown or out-of-order one.

structureblockpatternHow the happy path crosses the components, as a numbered topology walk. On an implementation pattern a sequence diagram carrying timing and the failure branches follows it one lens up; a conceptual band keeps its class-style diagram and stops there.

causesblockhazardWhat produces the hazard — the decisions and pressures that end in this failure mode.

architectureblocktheme, designThe primary diagram and the walk through it. On a theme it maps a concrete system; on a design it is the board plus the trace from every functional requirement to the component that satisfies it.
tradespaceblockthemeThe axes the theme's decision moves along, and what trading one for another actually costs.

rationaleblockprincipleWhy the principle helps — the mechanism behind the maxim, not a restatement of it.
applyingblockprincipleHow to honour it in practice, at the grain of a decision someone actually makes.
overreachblockprincipleHow it fails when taken too far. Mandatory on every principle, because a maxim with no stated limit is advice nobody can argue with.
requirementsblockdesignWhat the system must do (functional) and how well (non-functional). Everything downstream argues from here.
sizingblockdesignoptionalRight-sizing: the interaction shape, the numbers run, and each candidate technology adopted, rejected or deferred with a reason.
entitiesblockdesignThe core entities and their data design — each with its role, a one-line description and a trimmed schema.
interfaceblockdesignoptionalThe API surface, grouped by caller, each endpoint with its method, path and contract.

capabilitiesblockcapabilityThe provider-neutral taxonomy of what this category of service does. No product names — those are evidence, and they live in the mapping.

Authored attributes

What an author writes, by hand or through kb.mjs. Distinct from the JSON-LD properties: those are what a page emits, these are what someone wrote. A json-array shape is JSON-valued because its contents are whole sentences, and a comma-delimited attribute would break on the first comma in the prose. make check fails if the corpus carries an attribute missing from this list.

data-kb-idattributePage rootRequiredtextThe page's stable identifier, and the target every relationship and citation names. It must match the file name and the page's place on disk.
data-kb-kindattributePage rootRequiredclosedOne of the seven page kinds. It fixes which blocks the page must carry and which folder it lives in.
data-kb-bandattributePage rootRequiredclosedOn a pattern, the elevation band or lens it belongs to, which is also its folder — make check fails if the two disagree. Every other kind repeats its own kind here, because those pages are filed by kind rather than by band; hazard is a placeholder, not a fourteenth band.
data-kb-groupattributePage rootRequiredclosedThe subdivision within a band, on the two bands that have one. Everywhere else it repeats the band, which is the encoding of “not subdivided”. Usually part of the path, but not always: a group carrying a folder alias shares another group's directory.
data-kb-orderattributePage rootRequiredtextEditorial sort key within the band or kind. It drives hub order and the prev/next links, so it is pedagogical rather than alphabetical.
data-kb-essenceattributePage rootRequiredtextThe terse one-liner the hub chip and the index render. Distinct from the page's longer p.doc-essence, which reads as a definition; both exist and neither replaces the other.
data-kb-tagsattributePage rootRequiredjson-arrayTwo to five tags from the closed set below. JSON-valued so the attribute survives a comma.
data-kb-solvesattributePage rootOptionaljson-arrayThree to five symptoms in the reader's own words — what someone types who has the problem and does not yet know this page exists. Never the page's own name or jargon. Themes carry none; their essence takes the search weight instead.
data-kb-aliasesattributePage rootOptionaljson-arrayGenuinely used alternate names, so a search for one finds the page. An empty list is a good answer; invented nicknames are not.
data-kb-favouriteattributePage rootOptionalbooleanMarks an editorial pick — a ★ chip on the hub and a filter that collapses the map to the picks. It is the authored default only: a visitor's own stars are stored locally and win.
data-kb-blockattributeSectionRequiredclosedWhich block this section is. The section's id is the same string, so the anchor and the semantic key never drift apart.
data-kb-relattributeElementRequiredclosedThe relation verb this item declares, from the 17 above. Every edge is declared on both pages it joins.
data-kb-toattributeElementRequiredid-refThe page id at the other end of the relation. A target that names no page fails the build.
data-kb-levelattributeElementOptionalclosedThe reading level this element is visible from — the lenses are cumulative, so a higher one shows it and everything below. Absent means the element is part of the basic core every reader sees.
data-kb-registerattributeElementOptionalclosedThe single lens an element renders at, replacing its simpler sibling instead of adding to it. A rare tool, for the few places where showing both versions at once would be wrong; data-kb-level is the default. An element carries at most one of the two.
data-kb-polarityattributeElementOptionalclosedWhich side of a multi-sided block an item argues. A closed set of eight, across the three blocks that have sides — listed above.
data-kb-exampleattributeElementOptionaltextIdentifies one real-world implementation in the “In the wild” block, so it can be cited and lens-tagged individually.
data-kb-langattributeElementRequiredclosedThe language of a code sketch, which selects the highlighter. Required on every sketch.
data-kb-roleattributeElementRequiredtextWhat a pattern does in the service of one theme, written on the theme's tour step.
data-kb-memberattributeElementRequiredid-refThe pattern a theme's tour step visits. This is the source of truth for theme membership, and the build projects it both ways.
data-kb-themeattributeElementRequiredid-refThe theme a pattern's “Where it shows up” item claims. Hand-authored, so it can drift from the tour that owns it — make check fails either half alone.
data-kb-mapsattributeElementOptionalid-refPins an implements edge to one row of this page's own mapping or matrix table, so the stack index can show the services that package the pattern rather than link a whole table. Optional; when present it must name a real row.

Polarity values

Three blocks argue from more than one side, and data-kb-polarity says which side an item is on. It is what lets a reader ask for the case against something without reading the case for it, and what puts the two in separate columns.

A closed set of eight. kb.mjs validate rejects anything outside it as the page is written, rather than letting a typo ship as a silently unstyled item.

propolaritytradeoffsAn argument for adopting the page's subject — what it buys you.
conpolaritytradeoffsAn argument against — what it costs, stated as a fact rather than hedged.
whenpolarityusageA situation that calls for the pattern, written as the reader's circumstance.
avoidpolarityusageA situation where reaching for it makes things worse.
knobpolarityproductionA configuration surface you actually turn — a named parameter, or a dial described without attributing it to a product.
signalpolarityproductionAn observable quantity worth watching: queue depth, replication lag, p99 latency.
failurepolarityproductionWhat breaks first under load, and how it looks when it does.
checkpolarityproductionA gate to clear before shipping.

Reading levels

A closed vocabulary of three, and the lenses are cumulative: a higher one never replaces what a lower one said, it adds under the same headings. Every block shows at every lens — the skeleton never changes, the depth adapts inside it. Nothing may render empty at any lens, which is what forces at least one basic-visible item into every list.

Two attributes carry a level, and an element may use only one of them. data-kb-level means visible from this level up, and is the default tool; untagged content is the basic core everyone sees. data-kb-register means rendered at exactly this lens, replacing the simpler version, and is rare — reach for it only where showing both at once would be wrong.

Basicreading levelA short, complete page in the register of a cloud-provider doc. Everything untagged is here, and this is what a reader new to the topic gets end to end.
Advancedreading levelBasic plus enough detail to run a system design — the mechanics, the second-order tradeoffs, the sequence diagram.
Expertreading levelBasic plus advanced plus the deep dives: limitations, cost bills, and the sharp edges you only meet in production.

Relation verbs

A closed vocabulary. Every relationship is declared on both pages it joins, and make check fails on any that is one-way, dangling, or contradictory. Schema.org has nothing this precise — isRelatedTo is the closest and says almost nothing — so these are the KB's own.

Each description reads from the side the edge is authored on. Two verbs render under a label that does not echo their id, and say so.

kb:often-confused-withrelation verbOften confused withsymmetricThe two get mistaken for each other; know the difference before you pick one. Symmetric — it means the same read from either end.

JSON-LD properties

Beyond the relation verbs, these are the kb: terms a page's JSON-LD emits. The list is complete: make check reads every page's structured data and fails on any term that does not resolve to a fragment here. Three of them are projected rather than authored — kb:note comes from a relationship's own note, and kb:in-theme and kb:tours are the two directions of theme membership.

kb:kindJSON-LD propertyWhich of the seven page kinds this is — pattern, hazard, theme, principle, design (a worked case study), capability (a category of managed cloud service), or comparison (a product decision: managed services and open-source contenders side by side).
kb:bandJSON-LD propertyThe band the page declares. On a pattern that is one of the thirteen elevation bands or lenses, and also its folder; on every other kind it repeats kb:kind, because those pages are filed by kind.
kb:groupJSON-LD propertyThe subdivision within a band, on the two bands that have one; elsewhere it repeats kb:band. It names the folder except where a group carries an alias and shares another's.
kb:noteJSON-LD propertyWhy two things relate, from this side. Each side may phrase it its own way; only the edge and its verb must agree.
kb:roleJSON-LD propertyWhat a pattern does in the service of one particular theme.
kb:in-themeJSON-LD propertyA theme whose tour visits this pattern. The inverse of kb:tours.
kb:toursJSON-LD propertyA pattern this theme's tour visits. The inverse of kb:in-theme.

Bands

Thirteen: four elevation rungs, numbered I to IV, which are a ladder from a single object up to a network of services; and nine lenses, which cut across that ladder rather than sitting on it. A band is also a folder — a page whose data-kb-band disagrees with its path fails the build.

Three rules, all enforced by make check: every tag on a page comes from this set; every page carries two to five of them; every tag here is used on three or more pages. Adding one is deliberate — put it in the set first, and only if it will honestly apply to three pages that already exist.

Search expansion

Every vocabulary above is closed: a value outside the set fails the build. One more is not, and it is the reason a search for a word this knowledge base never uses can still find the right page. A bridge maps a word a reader types to one or more words the corpus actually says — resiliency to resilience, qps to throughput. Both scorers substring-match, so a word the corpus already contains retrieves itself; a bridge pays only where the reader's word and the corpus's word differ.

Two layers, and the curated one wins outright. SYNONYMS in scripts/lib/model.mjs is hand-written and small; scripts/data/expansion-synonyms.json is the authored bulk. A key in both takes the curated value whole, so any target only the table names is dead. Expansion hits score at half weight, which keeps the author's own vocabulary winning ties.

Structure is enforced even though the vocabulary is open: a key is a lowercase word of three or more letters and not a stopword, it carries one to four targets, every target is a word the corpus really uses, and no target may contain its own key. make check fails on any of those. The two rules a machine cannot check are the author's — do not bridge to a word so common it reaches a tenth of the corpus, and do not add a bridge nobody would type. Growing or retiring the table is the kb-vocab skill.

The reader and writer

The one vocabulary here that is not page metadata: scripts/kb.mjs, which is how anything reads or writes this knowledge base without opening the HTML. The corpus runs to millions of tokens and over half of any page is markup, so a grounded answer costs a couple of thousand tokens through these commands instead of hundreds of thousands.

Reading is safe; writing goes through the validated writers so the data stays well-formed, and wild, production and explain each replace their whole block. Two flags apply everywhere: --json — structured output instead of text; --diagrams — keep the mermaid source, omitted by default as noise.

kb.mjs findcommandreads--tag <t>--band <b>--kind <k>--level <l>Search names, essences, aliases, tags and symptoms. The way in from a symptom you can describe but cannot name.
kb.mjs getcommandreads--block <b>--level <l>--diagramsOne page, cleaned of styles, scripts and navigation chrome — or one block of it. On the wild and production blocks, --json also dumps items in the writers' own shape — edit one entry and hand the lot back, rather than re-typing the neighbours from rendered prose and dropping their level tags and inline <code>.
kb.mjs briefcommandreads--theme <id>--tag <t>--band <b>--kind <k>--n <5>One-call scout bundle: the find hits, the governing theme's decide table, and the typed neighbours of the top hits. Replaces the three to six calls an agent otherwise spends re-deriving exactly this sequence.
kb.mjs relatedcommandreadsThe typed neighbours — what it combines with, what replaces it, what it gets confused for.
kb.mjs backlinkscommandreadsWhat points here: typed inbound edges plus the prose mentions that never became edges.
kb.mjs refscommandreads--file <path>What this page points AT, read live off the page rather than off the build: relations, prose links, theme members, mermaid clicks. Read live, so an edit that changed what a page uses can be reconciled before the build sees it.
kb.mjs lscommandreads--band <b>--kind <k>List pages, filtered.
kb.mjs validatecommandreads--file <path>Structural lint against the data contract. No argument validates every page.
kb.mjs setcommandwrites--aliases '["CB"]'--tags '[…]'--solves '[…]'--essence "…"--favourite true|falseSet the page's root metadata. Each flag takes JSON where the value is a list, so the attribute survives a comma inside a sentence.
kb.mjs wildcommandwrites--items '[{"id":"envoy","name":"Envoy","note":"…"}]'Replace the “In the wild” block — real, well-known implementations only. Replaces the WHOLE block, so re-supply every item. Dump the current one with get --block wild --json, which returns exactly this shape. Each item takes an optional level; text may carry <code> and all other markup is escaped.
kb.mjs productioncommandwrites--knobs '[{"label":…,"note":…}]'--signals '[…]'--failures '[…]'--checklist '["…"]'Replace the production block: what it takes to run the pattern. Replaces the whole block, same as wild. Any list may be empty and its card is simply omitted — but each of the four is checked by name at every lens, so tagging every knob up a lens leaves a basic reader looking at an empty heading.
kb.mjs explaincommandwrites--basic "…"--advanced "…"--expert "…"Write the three-rung ladder. All three rungs are required, and they stack — the reader at expert sees all three. A sentence repeated across rungs is a defect. All three empty removes the block.
kb.mjs levelcommandwritesTHE lens mechanism — accretion: visible from this level up. Untagged content is the basic core every reader sees.
kb.mjs registercommandwritesRARE — replacement: rendered at exactly this lens, instead of its simpler sibling. For the few places where showing both versions at once would be wrong. Elements only: sections always show, at every lens. An element carries at most one of level and register.
kb.mjs linkcommandwrites--note "…"--note-back "…"Declare a relationship. Writes both sides at once, which is what keeps the graph bidirectional. Each side may phrase its note its own way; only the edge and its verb must agree.
kb.mjs unlinkcommandwritesDrop the edge from both pages, whatever verb each side declared. Re-typing an edge is unlink then link.
kb.mjs newcommandwrites--kind <k>--band <b>--group <g>--name "…"--order <n>--tags '[…]'Scaffold a page with every block its kind requires, in order. The other writers report an unknown id until build.mjs has run, because they resolve ids through the built graph. Scaffold, build, then set.
